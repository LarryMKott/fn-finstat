## 二、总体评价

工程质量**明显高于一般个人项目**，重构方向正确，以下判断有据可查：

**做得好的地方**

1. **错误体系分层干净**：`app/core/errors.py` 定义 `BizError` 族 + 分段错误码，路由层零 `try/except`，由 `handlers.py` 全局统一转 `{code, msg, data}`。前端 `api/client.js` 同步适配（含旧 `detail` 结构兼容），契约前后端一致。
2. **`base.py` 拆分手法专业**：拆出 `engine.py` / `migrations.py` 后用 `__all__` 门面再导出，既有 `from app.db.base import X` 调用方无需改动，是标准的渐进式重构。
3. **迁移幂等性处理到位**：跨三方言的 `_add_column_if_missing` 分别用 PG `IF NOT EXISTS`、MySQL `information_schema`、SQLite `pragma_table_info` 保证幂等；且把 `_add_column_if_missing` 的表名从硬编码 `"bills"` 改为参数传入（原先只支持 bills 表，是潜在 bug，本次修掉了）。
4. **调度器设计有四态闭环**：认领 → 成功清零重排 → 失败 1/2/4 退避 → 连续 5 次自动停用；软锁超时（`LOCK_TIMEOUT`）防死锁；停机补跑合并为一次（不逐周期补跑）。测试对这四种行为都有独立用例。
5. **目录监听判重逻辑严谨**：以**内容 sha256** 而非文件名判重，覆盖「同名文件重新导出覆盖」场景；失败文件也登记指纹，避免失败文件被无限重试。
6. **测试覆盖真实有效**：`test_scheduler.py` 验证了退避倍数序列 `[10, 20, 40, 40]`、锁超时可重抢、停用后不再调度等边界，不是凑数测试。
7. **前端重构有节制**：`useConfirm.js` 用 reactive 单例 + Promise，处理了「旧弹窗未决时按取消结掉」，避免 Promise 悬挂；`client.js` 用 `AbortSignal.timeout` 统一超时并按语义区分 `TimeoutError`。

## 三、问题清单

### 【严重】S-1 构建产物与 `index.html` 引用不一致，且产物被 git 跟踪

**现象（已实测复现）**

工作区 `app/static/index.html` 引用：

```
assets/index-Bin4vxGR.js     ← 未跟踪（?? 状态）
assets/index-D-dfNjPX.css    ← 未跟踪（?? 状态）
assets/echarts-CwC4iLS7.js
```

而 `git HEAD` 版本引用 `index-CSFFKaqI.js` / `index-BaZkHSWa.css`（本次已 `D` 删除）。

同时，`git HEAD` 中**仍跟踪**一个 v0.4.0 遗留产物 `app/static/assets/index-DYcOIkYL.js`（36.6 kB），该文件在当前工作区依然物理存在，且内容与 HEAD 完全一致（`git diff HEAD` 为空）——即重新构建会**再次生成**它，属于永久孤儿文件。

**根因**

`app/static/assets/` 目录下产物**从未加入 `.gitignore`**（`.gitignore` 仅忽略 `*.fpk`、`frontend/dist/`，无任何 `static`/`assets` 规则）。而 `vite.config.js` 的 `outDir` 是 `../app/static`。

**后果**

1. 每次构建产生的新哈希产物都会成为 untracked 文件，与已跟踪的旧产物**并存堆叠**，仓库体积持续膨胀（本次构建后 untracked 总数已达 50）。
2. 提交时极易漏提交产物（本次即如此：`index-Bin4vxGR.js` / `index-D-dfNjPX.css` 至今未提交），导致 **`app/static/index.html` 引用了仓库中不存在的 JS/CSS → 部署后用户端白屏**。
3. `scripts/fpk_selfcheck.py` 的 `PKG_DIRS` 含 `static`，会把 `assets/` 下**全部**文件（含过期孤儿）打进 FPK，进一步放大包体。

**建议**

- 二选一并统一：
  - **方案 A（推荐）**：把产物移出 git 跟踪（`git rm -r --cached app/static/assets`），改为构建时生成，`.gitignore` 增加 `app/static/assets/`；CI 的 `scripts/ci_build.sh` 已会跑构建，FPK 从构建产物打包。需同步确认 `app/static/index.html`（源文件，含防闪烁内联脚本）不应被 vite 覆盖，只覆盖 `assets/` 与 `sw.js`。
  - **方案 B**：保留产物入库，但构建前先清空 `app/static/assets/` 旧文件（`emptyOutDir` 已开启但 `outDir` 在项目根之外，需核实 vite 是否只清理自身产物），并严格每 build 必提交产物。
- 无论如何，**删除当前孤儿文件 `app/static/assets/index-DYcOIkYL.js`**（对应 HEAD 已删除的入口产物）。
- 在 CI 增加门禁：构建后校验 `app/static/index.html` 中引用的每个 `assets/*` 文件均存在（可加进 `fpk_selfcheck.py`）。

### 【一般】M-1 `record_failure` 的失败计数存在丢失更新风险

`app/db/dao/task_dao.py:137` 采用「先 SELECT 读 `failure_count`，Python 加一，再 UPDATE 写回」：

```python
task = session.scalar(select(ScheduledTask).where(...))
failure_count = task.failure_count + 1
```

而同一文件的 `try_claim`（第 97 行）刻意用了原子 `UPDATE ... WHERE` 来保证并发安全。两处风格不一致——若同一任务被并发触发（手动「立即执行」与调度 tick 撞上），`record_failure` 可能丢失计数，使「连续 5 次自动停用」失效。

不过 `try_claim` 的软锁事实上已把并发收敛为串行（拿不到锁就跳过），**实际触发概率低**，故定为「一般」。`record_success`（第 113 行）同样先读后写，但写入的是常量值，无此问题。

**建议**：改用原子自增表达式，与 `try_claim` 保持一致：

```python
session.execute(
    update(ScheduledTask)
    .where(ScheduledTask.task_key == task_key)
    .values(failure_count=ScheduledTask.failure_count + 1, ...)
)
```

并注意 `disable` 判断需基于返回的新值（可先 `UPDATE` 再 `SELECT` 同事务读回）。

### 【一般】M-2 `recent_runs` 返回结构易误用

`app/db/dao/task_dao.py:203` 返回 `[{"total": total}, *runs]` —— 把总数字典塞进列表首位，调用方必须约定 `rows[0]` 是元信息、`rows[1:]` 才是数据。`app/api/automation.py:87` 正是这么解包的。这种「列表首位放异类元素」的结构很脆弱：任何按直觉遍历 `rows` 的新调用方都会把 `{"total": ...}` 当成一条运行记录。

**建议**：改为返回元组 `(total, runs)`，或返回 `{"total": total, "runs": runs}`，消除隐式约定。

### 【一般】M-3 「成功」状态复用了支出语义色

`frontend/src/components/settings/AutomationCard.vue:298` 与 `:364` 用 `--color-expense` 表示任务执行**成功**：

```css
.auto-item__status--ok { color: var(--color-expense); }
```

但项目设计系统约定（见 `.workbuddy/memory/MEMORY.md`，本机文件不入库）中 `--color-expense` = **苔绿，语义为「支出」**，与 `--color-income`（暖红，收入）配对使用；`--color-danger` = 暖红，表示危险。

当前代码里「成功」用绿、「失败」用 `--color-danger`（暖红）。从纯视觉看绿=通过、红=失败符合直觉，但**借用了收支语义令牌**，违反了「组件内只允许引用 `--color-*` 语义层」背后的真正意图——语义令牌应按语义使用。后续若调整收支配色（例如把支出改为蓝色），任务状态色会跟着意外变色。

**建议**：在 `style.css` 语义层补 `--color-success` / `--color-success-soft`（可映射到与 `--color-expense` 相同的绿色值），组件改用 `--color-success`。同理检查 `style.css:1739` 附近是否属同类误用。

### 【建议】L-1 构建产物目录纳入自检门禁

承接 S-1，建议在 `scripts/fpk_selfcheck.py` 或 CI 增加一条：解析 `app/static/index.html` 中的 `assets/*` 引用，断言文件真实存在。这条检查成本极低，却能直接拦住「白屏」这类最严重的事故。

### 【建议】L-2 `ScheduledTask` 未提交的 `updated_at` 字段

`app/db/models.py:175` 定义 `updated_at`，`as_dict()` 也返回它，但 `app/schemas/automation.py` 的 `AutomationTask` 未声明该字段。Pydantic 构建时会忽略多余键（`AutomationTask(**t)` 不报错），但前端拿不到该字段。属无害冗余，若前端有用到时补上。

### 【建议】L-3 调度器单进程前提应在部署层面兜底

`scheduler.py` 顶部已诚实声明「仅单进程单实例下成立」，`cmd/` 未用 `--workers`，当前成立。但 `locked_by` / `locked_until` 字段已预留却**未真正参与** `try_claim` 判定（硬编码 `"local"`）。建议在 `manifest` 或启动日志中显式提示「勿以多 worker 启动」，避免后人改 uvicorn 参数时无声踩坑。

### 【建议】L-4 `asyncio.sleep` 循环退出时的任务取消语义

`scheduler._loop()` 在 `await asyncio.to_thread(run_due_tasks)` 执行期间若被 `stop_loop()` 取消，`to_thread` 的底层线程**不会被真正中断**，会继续跑完当前任务。`shutdown` 时若该任务正在写库，可能出现「进程退出但线程仍在写」的短暂窗口。对单机应用影响很小，仅作记录；如需严谨可在取消后 `await asyncio.wait_for` 加超时。

## 四、结论

**重构本身是成功的**：分层清晰、契约统一、测试扎实，269 例全绿，前端导入路径迁移干净无残留。`app/core/` 的引入和 `base.py` 的门面拆分都是正确的架构演进方向。

**但存在一项必须先处理的仓库卫生问题**：S-1（产物未 gitignore + 产物与 `index.html` 引用不一致）是**当前状态下会直接导致部署白屏**的问题，且在提交本次改动时极可能被带进去。建议**先修 S-1 再提交**，其余问题可按 M → L 顺序择期处理。

M-1 / M-2 / M-3 均为「实际影响可控但有明确改进路径」的问题，其中 M-3 涉及设计系统约定，建议与 `style.css` 令牌体系一并整理。
