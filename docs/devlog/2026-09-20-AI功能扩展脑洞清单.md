## 1. 为什么现在做这个清单

### 1.1 现状：AI 能力已成型，但形态单一

v0.6 ~ v1.0 已交付的 AI 能力可归为四层（均为「用户主动触发 → AI 被动响应」）：

| 层 | 已交付能力 | 实现位置 |
| --- | --- | --- |
| 数据入 | 导入时 AI 归类（关键词未命中才调用）、分类规则自学习、存量批量重归类 | `services/ai_service.py`、`services/learned_rule_service.py` |
| 理解 | NL 查账意图翻译层（规则优先 + LLM 白名单兜底）、对话式查账（3 轮追问） | `services/nl_query.py` |
| 解释 | 周期消费报告（月/季/半年/年 + 归档）、AI 财务教练、报告精细级追溯 | `services/ai_service.py`、`services/coach_service.py` |
| 输出 | MCP Server（4 个只读工具）、开放 API Token | `services/mcp_service.py`、`services/token_service.py` |

**共性缺口：全部依赖用户主动打开应用**。项目的调度底座（T-5.1）、通知中心（T-5.4）、
预测计算（T-6.4）、健康评分（T-1.3）都已就绪，但没有任何一条把「AI 结论」主动推到用户面前。

### 1.2 必须遵守的既有红线（脑洞不得违反）

本清单所有条目均以下列约束为前提，违反者直接淘汰：

| 红线 | 出处 |
| --- | --- |
| 所有数字由后端计算，模型只做解释，**模型不参与任何算术** | T-6.5 设计理由 |
| 原始流水永不外传，上下文只含**结构化聚合摘要** | `coach_service.py` 隐私红线 |
| 零新增运行时依赖（`app/requirements.txt` 当前 7 个包，为离线安装服务） | 开发计划 §3.1 T-5.1 |

| AI 调用须有配额上限 | v0.6 出口标准 |

## 2. 脑洞清单

按「与现有底座的距离」分为三档：A 档复用即可（改动最小），B 档需新增接口/小表，
C 档偏实验性。每条给出复用点、改动量、AI 成本与风险。

### 2.1 A 档：复用现有底座，改动最小

#### AI-1 异常自检通知（把「查账」变成「报账」）★推荐

| 项 | 内容 |
| --- | --- |
| 复用 | `forecast_service`（固定项识别 / P50·P90 分位线 / 一次性大额剔除）、`scheduler`（T-5.1）、`notify_service`（T-5.4） |
| 新增 | 一个周期性检查函数 + 新通知事件类型（如 `anomaly_alert`，需在逐类开关中登记） |
| schema | 无变更 |
| AI 成本 | **零**（纯规则计算，不调 LLM） |
| 改动量 | M |

**要推送的异常类型（全部可用现有计算得出）**

| 异常 | 判定方式（复用点） |
| --- | --- |
| 分类支出异常抬高 | 当月某分类支出 > 近 6 个月同分类月中位数 × 阈值 |
| 一次性大额 | 单笔 > 该分类月度中位数 × 3（`OUTLIER_FACTOR` 现成） |
| 越悲观线 | 当月累计支出 > 预测 P90 线（`ForecastService` 现成） |
| 固定项断供/突变 | 固定项商户本月缺失或金额偏离带宽（`FIXED_AMOUNT_BAND` 现成） |

**价值**：这是本清单里**投入产出比最高**的一条——应用的调度、通知、计算三块底座都已交付，
缺的只是「把计算结果按周期算一次并推出去」。产品形态从「我打开才工作」变为「有事主动告诉我」。

**风险**：通知疲劳。缓解：低频（周级）+ 单周期同类异常合并 + 逐类可关。

#### AI-2 记账体检向导

| 项 | 内容 |
| --- | --- |
| 复用 | 各 DAO 只读方法、`billsFilterHandoff` 交接机制（T-6.2 已建） |
| 新增 | `GET /api/stat/data-check` + 前端体检卡片 |
| schema | 无变更 |
| AI 成本 | **零** |
| 改动量 | S |

**体检项**：未分类流水 N 条、商户名为空的流水、金额为 0 的异常记录、
长期未记账的月份、未归属账本的历史数据、疑似重复导入（同商户同金额同日期）。

**价值**：不调 AI 却直接改善 AI 效果——未分类与脏数据是分类准确率的最大噪声源。
每条体检项一键跳转到对应筛选（复用 T-6.2 的交接机制）。
原开发计划将类似条目（A12）列为 Backlog「可随手做」，本清单认为其价值被低估。

#### AI-3 AI 教练接入已算好但未喂的数据

| 项 | 内容 |
| --- | --- |
| 复用 | `coach_service._build_context`（单函数）、`stat_service.health_score`、`forecast_service.expense_structure` / `cash_flow`、`loan_service`、`reimb_service` |
| 新增 | 无新接口，仅扩充上下文 |
| schema | 无变更 |
| AI 成本 | 不增加调用次数（提示词变长，费用微增） |
| 改动量 | **S（仅改一个函数）** |

**现状缺口**：`coach_service._build_context()` 目前只喂五项——评估窗口、月均收支与储蓄率、
分类 TOP5、当月预算进度、储蓄目标。而下列**已经算好、只差接进来**的数据全部缺席：

| 未喂入的现成数据 | 来源 |
| --- | --- |
| 财务健康评分三分项（储蓄率/负债率/应急金月数） | `stat_service.health_score`（T-1.3） |
| 固定 vs 弹性支出占比与清单 | `forecast_service.expense_structure`（T-1.5） |
| 现金流预测 P50 / P90 与固定项明细 | `forecast_service.cash_flow`（T-6.4） |
| 借贷台账未结项的应收 / 应付汇总 | `loan_service`（T-7.5） |
| 报销未到账金额 | `reimb_service`（T-7.4） |

**价值**：投入产出比最高的一条——**只改一个函数**，教练的回答质量立刻上一个台阶。
尤其是「负债率」「应急金月数」「未到账报销」这三类，直接决定建议是否贴合用户真实处境。

**风险**：上下文变长可能稀释关键信息。缓解：按问题意图裁剪上下文（教练问题里的
关键词命中「负债/欠」时才带借贷数据），而非无脑全塞。

### 2.2 B 档：新能力，需新增接口或小表

#### AI-4 报告主动推送（周报 / 月报）

| 项 | 内容 |
| --- | --- |
| 复用 | `ai_service.generate_report`、`notify_service.notify_report_ready`（事件类型已存在）、`scheduler` |
| 新增 | 调度任务定义「月初自动生成上月报告并归档」 |
| schema | 无变更 |
| AI 成本 | 每月 1 次（可忽略） |
| 改动量 | S |

**价值**：现在报告必须用户手点，且生成需数十秒（用户可能已切走）。改成调度触发后，
用户只看通知即可。`notify_report_ready` 事件已在通知中心注册，**链路几乎现成**。

**风险**：自动生成会消耗 API 费用（即使用户不看）。缓解：可在设置页开关，默认关。

#### AI-5 订阅侦探

| 项 | 内容 |
| --- | --- |
| 复用 | `forecast_service._identify_fixed_items`（固定项识别已实现） |
| 新增 | `GET /api/forecast/subscriptions` + 前端订阅列表卡片 |
| schema | 无变更（纯只读统计） |
| AI 成本 | **零** |
| 改动量 | S/M |

**输出内容**（超出「固定项列表」的价值增量在此）：

1. 固定项按商户聚合成**订阅时间线**：连续扣费月数、月均金额、首次出现时间；
2. **涨价检测**：同商户金额在某月发生台阶式上调 → 单独标出（这是真痛点）；
3. **疑似僵尸订阅**：金额长期不变但连续 > 12 个月 → 提示复核；
4. 月合计与占收入比。

**价值**：固定项识别代码已跑在现金流预测里，差的只是「换一种聚合与展示方式」。
订阅涨价与僵尸订阅是财务场景的高频真实痛点。

#### AI-6 场景化预算模板（LLM 只做「选」不做「算」）

| 项 | 内容 |
| --- | --- |
| 复用 | `budget_service` 建议链路（T-6.4 已交付统计口径） |
| 新增 | 模板库（硬编码系数表）+ LLM 选择层 |
| schema | 无变更 |
| AI 成本 | 每次推荐 1 次调用 |
| 改动量 | M |

**设计**：现有预算建议是纯统计中位数。新增一层——把结构化摘要交给 LLM，
让它从**预置模板库**中选一个最贴合的（如「学生党」「三口之家」「通勤族」「还贷期」），
模板本身是硬编码系数表，**数字仍由后端按模板系数计算**。LLM 只做分类判断，不产数字。

**风险**：模板库的维护成本与「削足适履」。定位为**建议的补充而非替代**——
保留纯统计建议，模板作为第二种可选口径。

#### AI-7 MCP 工具集扩展

| 项 | 内容 |
| --- | --- |
| 复用 | `mcp_service` 的 `@tool` 注册装饰器（架构干净，加工具成本低） |
| 新增 | 4 个只读工具 |
| schema | 无变更 |
| AI 成本 | **零**（工具由外部 Agent 调用，本项目不产生 LLM 费用） |
| 改动量 | S |

**建议补的工具**（复用既有 service，与开放 API 同一份查询口径）：

| 工具名 | 复用 |
| --- | --- |
| `query_forecast` | `forecast_service.cash_flow` |
| `query_health` | `stat_service.health_score` |
| `query_expense_structure` | `forecast_service.expense_structure` |
| `query_loans` | `loan_service` 汇总 |

**价值**：当前只有 4 个只读工具（查流水/汇总/预算/储蓄目标），外部 Agent 能问的面很窄。
补完后覆盖「收支 + 预测 + 健康 + 借贷」，才算真正的对外集成入口。

### 2.3 C 档：偏实验性，看是否需要

#### AI-8 流水备注语义检索

**目标**：支持「上次给家里人买东西花了多少」这类模糊问法，突破关键词精确匹配。

**两条路线（已验证，见 §7.4）**

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| 引入本地向量模型 | 本地 embedding + 向量索引 | **违背零依赖红线**（≈1.5GB 含 torch），NAS 安装不可控 |
| **零依赖 TF-IDF** | 纯标准库词频统计 + 余弦相似度 | **零依赖、零费用**；实测 Top10 命中 1 → **9** |
| LLM 打标落库 | LLM 打语义标签落库，检索走标签 | API 费用 + 词表维护；模拟值 18，但词表缺口（「看病→就医」）会漏 |

**实测结论（2026-09-20，`scripts/verify_note_search.py`）**：
关键词检索在该场景**基本失效**（Top10 命中仅 1），需求成立；
但**收益大头在「从字面到词频统计」这一步**——纯标准库 TF-IDF 就能从 1 提到 9，
**不需要 1.5GB 的本地模型**。

**建议**：**先做零依赖 TF-IDF**，真实数据上仍不足时再叠加 LLM 打标 + 词表。
详见 §7.4。

#### AI-9 反事实模拟（What-if）

**目标**：「如果把餐饮砍到 800/月，年底能多存多少？」——可拖动滑块，实时出结果。

**实现**：纯本地四则运算 + 复用现有预测模型，**不调 LLM**。

**取舍**：体验好、技术简单，但**商业价值一般**，属「好玩」而非「有用」。
若做，建议与储蓄目标（T-1.4）联动，让它服务于「能不能达成目标」这个真实问题。

#### AI-10 家庭月度 AI 复盘

**目标**：家庭空间已落地，但家庭页只有汇总数字。生成「家庭月度复盘」——
谁支出占比高、哪个分类是全家共同开销、家庭预算执行情况。

**强约束（安全）**：必须**只基于聚合值**，不得泄露成员明细。
项目已有 `allow_detail_view` 门控（T-7.2），**AI 生成链路必须把该门控前移**——
即在组装上下文时就按门控裁剪，而不是靠提示词约束模型「别输出明细」。
**提示词约束不是安全边界**，这一点必须写进实现要求。

## 4. 优先级建议

若只做三件，推荐 **AI-1 + AI-3 + AI-5**：

| 建议 | 排序理由 |
| --- | --- |
| **AI-1 异常自检通知** | 复用度最高、零 AI 成本、把应用从被动变主动，是本清单最大的产品价值跃迁 |
| **AI-3 教练接入真实数据** | 只改一个函数，投入产出比最高，立刻让现有功能变好 |
| **AI-5 订阅侦探** | 固定项识别已就绪，差一层聚合展示；订阅涨价是真痛点，数据已在库里 |

次选：**AI-7（MCP 扩工具）** 改动小、对外集成价值明确；**AI-2（体检向导）** 零 AI 成本且改善 AI 效果。

暂缓：AI-4（等通知疲劳度实测后再开）、AI-6（模板库需先有内容沉淀）、
AI-8 ~ AI-10（待拍板路线或收益不明确）。

### 4.1 前置建议：T-1.7 隐私加密应先于 AI 扩展 ✅ 已采纳

**结论（2026-09-20 落定）**：**T-1.7 隐私加密先于 AI 扩展**。

**理由**：AI 功能每扩展一步，就多一条数据外传路径（提示词变长、上下文字段变多）。
当前 API Key / 邮箱授权码 / 数据库口令仍为明文存储，T-1.7 未开工。
在加密落地前持续扩大 AI 外传面，等于**持续放大明文密钥的风险敞口**。

**执行顺序**：**T-1.7 隐私加密 → AI-1 / AI-3 → 其余**。
T-1.7 完成前不新增扩大外传面的功能（尤其 AI-6，会引入新的 LLM 调用路径与配置项）。

### 7.1 决策 1：隐私加密先于 AI 扩展 ✅ 采纳

**结论**：**同意**。开工顺序为 **T-1.7 隐私加密 → AI-1 / AI-3 → 其余**。

**落地要求**：
- T-1.7 先完成「API Key / 邮箱授权码 / 数据库口令统一加密存储」+ 存量明文升级迁移；
- 在 T-1.7 完成前，**不新增任何会扩大数据外传面的 AI 功能**
  （尤其 AI-6 场景化预算模板会引入新的 LLM 调用路径与配置项，须排在其后）。

### 7.2 决策 2：异常阈值与推送频率 ✅ 落定

**结论**：**分类抬高倍数 1.5×，推送频率周级**。

**口径细化（供实现直接采用）**：

| 异常类型 | 判定阈值 | 与已有常量的关系 |
| --- | --- | --- |
| 分类支出抬高 | 当月某分类支出 > 近 6 个月同分类**月中位数 × 1.5** | 新常量 `ANOMALY_CATEGORY_FACTOR = 1.5` |
| 一次性大额 | 单笔 > 该分类月度中位数 × **3** | **复用** `forecast_service.OUTLIER_FACTOR = 3.0`，不重定义 |
| 越悲观线 | 当月累计支出 > 预测 **P90** 线 | 复用 `forecast_service.cash_flow` |
| 固定项突变 | 本月金额偏离各月合计带宽 | **复用** `FIXED_AMOUNT_BAND = 1.25` |

**为什么分类抬高用 1.5× 而不用 3×**：这两个是不同性质的异常——
一次性大额是「单笔离群」，用 3× 拦截的是极端值；分类抬高是「**趋势异常**」，
用户想知道的是「这个月怎么花多了」，1.5× 才能捕捉到苗头，3× 时已经太晚。
两者独立存在，互不替代。

**推送频率**：**周级**（每周一次合并推送）。
单周期内同类异常**合并为一条通知**（按分类分组），避免逐条推送造成通知疲劳。

### 7.3 决策 3：自动生成报告默认开 ✅ 落定

**结论**：**默认开启**。

**落地要求**：
- 调度任务在**每月 1 日**自动生成上月报告 → 落归档 → 发通知（复用
  `notify_service.notify_report_ready`，事件类型已注册）；
- 设置页**必须提供关闭开关**（默认开 ≠ 不可关），关闭后不再自动生成；
- 生成失败**只写日志 + 发 `task_failed` 通知**，不影响其他功能（沿用调度底座约定）；
- **需评估费用可见性**：建议在设置页 AI 卡片展示「本月自动报告已生成 N 次」，
  让被动产生的费用对用户透明。

### 7.4 决策 4：AI-8 技术路线 ⚠️ 修正为「零依赖 TF-IDF」

**用户原意**：引入向量。
**实测结论**：**「向量检索」这个方向是对的，但不需要引入 1.5GB 的模型。**

#### 验证方法与数据

新增 `scripts/verify_note_search.py`（**零新增依赖，纯标准库**），
用 5 组真实模糊查询对比三条路线的 Top10 命中数：

| 方案 | Top10 命中合计 | 依赖代价 |
| --- | --- | --- |
| 关键词包含（现有能力下限） | **1** | — |
| **TF-IDF 向量（纯标准库）** | **9** | **零新增依赖** |
| LLM 打标签（规则模拟，离线估算） | 18 | 零依赖，需 API 费用 |

逐查询对照：

| 查询 | 关键词 | TF-IDF | 标签（模拟） |
| --- | --- | --- | --- |
| 给家里人买东西 | 0 | 2 | 3 |
| 学习提升的花销 | 0 | 1 | 4 |
| 看病买药 | 0 | 2 | **0** |
| 送礼人情 | 0 | 2 | 6 |
| 出行交通 | 1 | 2 | 5 |

#### 结论与理由

1. **关键词检索在该场景基本失效**（1/9）——「给家里人买东西」与备注
   「给老妈买的按摩仪」无任何字面重叠，这正是语义检索要解决的问题，需求成立。
2. **TF-IDF 用零依赖把命中从 1 提到 9**——收益的大头在「从字面到词频统计」这一步，
   而非「从 TF-IDF 到深度向量」这一步。**引入 1.5GB 模型换取的增量收益与代价不成比例**。
3. **标签方案（模拟 18）表面最高，但暴露了软肋**：`看病买药` 一条得 **0**——
   标签词「就医」与查询词「看病」无字面交集。这说明**标签方案的效果强依赖标签词表
   的设计质量**，且需要额外的词表维护成本。**真实 LLM 打标会优于模拟值**，
   但引入的是一笔持续的 API 费用 + 一个词表维护负担。

#### 建议方案（待用户最终确认）

**分两步，先零依赖再做增强**：

| 阶段 | 做法 | 代价 |
| --- | --- | --- |
| 第一步 | **纯标准库 TF-IDF 检索**（复用 `verify_note_search.py` 的 `TfIdfIndex`，生产化改造） | 零依赖、零 API 费用 |
| 第二步（可选） | 若 TF-IDF 在真实数据上仍不够，再叠加 **LLM 打标 + 词表**（含反查机制解决「看病→就医」这类词表缺口） | API 费用 + 词表维护 |

**明确不做**：引入 `sentence-transformers` / torch 等本地模型依赖（≈1.5GB），
违背项目零依赖红线，且 NAS 安装体积与首次启动下载均不可控。

## 8. 验证脚本使用说明

```bash
# 纯离线（默认）：只跑关键词基线与 TF-IDF，零 API 费用
./app/venv/Scripts/python.exe scripts/verify_note_search.py

# 加上 LLM 打标的规则模拟（离线估算，明确标注非真实值）
./app/venv/Scripts/python.exe scripts/verify_note_search.py --simulate-llm

# 真实 LLM 打标对比（需配置 DeepSeek API Key，会产生费用）
./app/venv/Scripts/python.exe scripts/verify_note_search.py --with-llm

# 指定真实数据库；样本 < 60 条时自动切内置评测语料
./app/venv/Scripts/python.exe scripts/verify_note_search.py \
    --db .local_data/finance/bill.db --corpus real
```

**脚本行为说明**：
- **只读数据库**（`mode=ro`），不写入任何业务数据；
- 真实库样本 < 60 条时自动切用**内置评测语料**（35 条贴近真实记账的备注样本），
  保证任何环境都能跑出结论；
- `--simulate-llm` 的标签值是**规则近似**，仅供量级参考，
  真实 LLM 能覆盖规则表外的表达，故真实命中率只会更高。
