## 1. 做了什么

给「流水 / 预算 / 资产快照」三个业务实体加上**账本维度**，让数据从「一本账」变成
「多本账可归集」。本批只做数据模型与迁移，**不做界面**——界面与家庭空间属 T-7.2。

| 交付物 | 位置 |

| `bills.ledger_id` / `budgets.ledger_id` / `asset_snapshots.ledger_id` | 同上（三张表均 `NOT NULL DEFAULT 1` + 索引） |
| `budgets` 唯一键扩展为 `(user_id, ledger_id, month, category)` | 同上 `uq_budget_scope` |

## 2. 关键设计决策

### 2.1 升级等价性靠「默认账本 + 列级默认值」，不靠改调用点

v0.7 是破坏性变更，但**升级前后行为必须完全等价**。做法是：

1. 迁移中先建「默认账本」，再用它的 id 作为 `ledger_id` 列的 DDL 默认值与回充值；
2. 历史流水 / 预算 / 资产快照自动全部挂到默认账本；
3. 所有旧调用点不传 `ledger_id` → 写路径落到默认账本、读路径不按账本过滤。

升级前全库只有默认账本，两种语义（`DEFAULT` 与「全部」）在升级瞬间完全重合，
因此**旧调用无需任何改动**。这是本批最核心的安全底线。

列级 `server_default` 不是可选项：解析器导入走 `insert_ignore_rows` 的**核心插入**，
不含 `ledger_id` 列，只有 DDL 默认值能让这批写入落在默认账本上。

### 2.2 读写两侧对 `ledger_id=None` 的语义不同（已在各层 docstring 写明）

| 场景 | `ledger_id=None` 的含义 | 理由 |
| --- | --- | --- |
| 读（列表 / 统计 / 导出） | **不按账本过滤** | 旧调用返回全量，语义不变；T-7.2 的「全部账本」视图直接复用 |
| 写（新增 / upsert） | **落到默认账本** | 与升级前唯一账本等价，旧调用写入位置不变 |

两条语义在「只有一个账本」时完全一致，因此混用不会造成升级期的行为差异。

### 2.3 过滤条件与 `user_id` 同策略：DAO 层强制注入

`build_criteria()` 新增 `ledger_id` 参数，与 `user_id` 一样**由 DAO 强制注入**，
禁止在 service 层拼装筛选条件（沿用开发计划 4.5 的隔离约定）。

### 2.4 删除账本 ≠ 删除数据

`LedgerDAO.delete()` 在删除前把该账本的流水 / 资产快照整体改挂默认账本，预算按唯一键
判冲突（目标已有同键预算则保留目标、丢弃被删账本的那条——预算是设置不是事实数据，
不允许合并累加）。默认账本拒绝删除。

## 3. 迁移实现（三方言差异是本次最大风险点）

`_v8_add_ledger_dimension` 的执行顺序：

1. `ensure_default_ledger()` —— 建默认账本（幂等：先按 `is_default` 找、再按默认名找、都没有才新建）；
2. 三张表 `ADD COLUMN ledger_id INTEGER NOT NULL DEFAULT <默认账本 id>`（跨方言幂等）+ 显式回填兜底 + 建索引；
3. `budgets` 唯一键升级（三方言分路）。

### 3.1 budgets 唯一键：SQLite 必须重建表

| 方言 | 做法 |
| --- | --- |
| SQLite | 不支持改约束 → 建 `budgets_new`（DDL 由 ORM 模型按方言 `CreateTable` 编译）→ 搬数据（**保留 id**）→ 删旧表 → 改名 → 按模型的 Index 对象补建索引 |
| MySQL | `DROP INDEX uq_budget_scope` + `ADD UNIQUE KEY`（DDL 隐式提交，靠存在性检查保证幂等） |
| PostgreSQL | `DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT`（语句自带幂等） |

两个实现细节（都是踩过的坑）：

- **新表 DDL 由 ORM 编译而非手写**：手写 DDL 会随模型演进漂移（列类型、约束、默认值）；
- **补建索引必须复用会话自身的连接**：另开连接会在会话写事务未提交时撞 SQLite 库锁
  （`database is locked`），初版就是这么失败的；
- **SQLite 的 UNIQUE 约束落在自动索引上且不保留约束名**（恒为
  `sqlite_autoindex_budgets_N`），因此幂等判定不能按约束名查，只能按
  「唯一索引覆盖的列」查（`pragma_index_list` JOIN `pragma_index_info`）。

### 3.2 全新安装不走迁移，需要单独补建默认账本

`init_db` 对全新库直接把版本记为最新（不跑任何迁移），因此默认账本必须由
`init_db` 在建表后调用 `ensure_default_ledger()` 补建——与预置默认分类同一位置。
老库升级时 v8 已建过，该调用幂等跳过。

### 3.3 默认账本原语独立成 `app/db/ledgers.py`

迁移要用它创建默认账本，而迁移被 `app.db.base` 导入；放进依赖 `base` 的 DAO 层就会
形成 `base → migrations → dao → base` 循环导入。故独立成只依赖模型与 config 的模块。

## 4. 备份恢复与跨库搬移

- **备份**：新增 `ledgers` 节，流水/预算/快照带 `ledger_id`，`format_version` 升到 2。
- **恢复**：账本先按名落库（id 由目标库分配），再按名把 `ledger_id` 重映射到新 id；
  映射不到（含**旧备份无 ledger_id**）一律落到默认账本 → 旧备份可直接恢复，无需转换。
- **跨库搬移**（`copy.py`）：同样按名重映射；源库是 v7 老库（无账本表）时全部落到目标默认账本；
  PG 序列同步补上 `ledgers` 表。

## 5. 接口与权限

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/ledgers` | 公开 | 默认账本排最前，含各账本流水条数 |
| POST | `/api/ledgers` | 管理员 | 账本名全局唯一 |
| PUT | `/api/ledgers/{id}` | 管理员 | 改名 / 改备注 |
| DELETE | `/api/ledgers/{id}` | 管理员 | 数据并入默认账本；默认账本拒绝删除（400） |

账本与分类同性质（全局共享维度，改动影响所有账号），故复用分类的权限口径：
写操作同时进入 `core/permissions.ADMIN_RULES` 策略表与路由守卫 `require_admin`。

账单 / 预算 / 资产 / 统计接口均新增可选 `ledger_id` 查询参数（写接口为请求体字段），
不传即旧行为。

`AttributeError`。改为 `from app.db.engine import _STATE`。

## 8. 已知边界与下一步

- **界面未做**：本批只有模型与接口，账本切换 / 新建的 UI 属 T-7.2；
- `ledgers.owner_id` 恒为空串（应用级共享）。成员账本归属要等 T-7.2 家庭空间确定语义；
