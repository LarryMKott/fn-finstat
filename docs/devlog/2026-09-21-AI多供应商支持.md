## 设计

现有通道本就是 OpenAI 兼容协议（`{base_url}/chat/completions` + Bearer，
标准库 urllib），因此多供应商 = **供应商注册表 + 设置流**，调用层零改动。
classify / 报告 / 教练 / NL 查询 / 测试连接五个消费方经 `ai_service.chat`
单收口自动获益，SSRF 防线（禁重定向）原样生效。

### 供应商注册表（`file_settings.AI_PROVIDERS`）

deepseek（默认）· moonshot（Kimi）· zhipu（GLM）· dashscope（通义百炼兼容
模式）· siliconflow · openai · custom（自部署/任意兼容端点，地址与模型必填）。
`models` 仅为快捷预置，模型名恒可手填——各家上新模型不应等应用发版跟进。

### 配置流

- `AISettings.provider` 新字段，持久化进 ai_config.json（历史配置缺省
  deepseek，向后兼容）；读取时未知 provider 按 deepseek 兜底，显式存过的
  base_url 不因兜底被丢弃；
- `load_ai_settings`：base_url/model 缺省时回填所配供应商的预置默认值；
- API `PUT /api/ai/config` 接受 `provider`（白名单校验，未知 400）；切换
  供应商且未显式带地址/模型时回填预置默认，杜绝「供应商=智谱、地址仍是
  DeepSeek」的错配；`GET /api/ai/config` 的 `providers` 注册表仅随管理员
  视图下发（普通账号用不到，收敛面）；
- 错误文案跟随供应商（「智谱 GLM 接口返回 401」而非硬编码 DeepSeek）。

### 前端（AICard）

供应商下拉 → 切换即回填预置地址与首个模型（与后端同规则，可改）；有预置
模型走下拉、custom 手填；标题与文案去掉 DeepSeek 硬编码；测试/保存流程不变。

## 测试

- 预置默认回填 + 落盘持久化 + 显式地址优先（client 级）；
- 未知供应商 400；配置文件手改未知 provider 读取兜底（file_settings 级）；
- 既有配置往返用例更新（新增字段、文案去 DeepSeek）。

## 已知边界

- `response_format: json_object` 为 DeepSeek/OpenAI 语义，个别兼容端点不支持时
  可能报 4xx——属端点能力差异，报错信息会带供应商名便于定位；后续可按
  provider 降级省略该参数（未做，当前预置供应商均支持或忽略该字段）。
