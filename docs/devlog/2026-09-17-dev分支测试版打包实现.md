## Context

此前只有 `main` 分支有构建链路：push 即打包并发正式 Release。`dev` 分支没有任何
打包能力，验证中的功能想上真机测，只能本地打包——而本地产物名为 `fn-finstat.fpk`，
**与正式包完全同名**：

- 传到设备上分不清这是测试包还是正式包，装错了不会有人提醒
- 应用「关于」页显示的版本号与正式版一模一样
- 无法并行保留测试包与正式包，容易误当作正式产物分发

本任务为 `dev` 分支建立打包构建链路，并让**测试版标识贯穿产物全链路**。

## 交付内容

### 1. 构建渠道抽象（release / dev）

新增渠道概念，渠道决定产物版本号的形态：

| 渠道 | 版本号 | 来源 |
| --- | --- | --- |
| `release` | `0.7.1` | `VERSION` 原值 |
| `dev` | `0.7.1-dev.42.g1a2b3c4` | `VERSION` + semver 预发布段 |

实现集中在 `scripts/sync_version.py::derive_version` 一处，并配单元测试。
派生规则：`{base}-dev.{构建号}.g{短sha}`，两段均可缺省（本地无构建号时形如
`0.7.1-dev.geb01922`）；片段内的非法字符主动净化（CI 环境变量不完全可控）；
**渠道拼写错误直接抛错**，不允许静默产出正式版包。

新增 CLI：

```bash
sync_version.py --print --channel dev --build-number 42 --short-sha 1a2b3c4   # → 0.7.1-dev.42.g1a2b3c4
sync_version.py <stage> --version 0.7.1-dev.42.g1a2b3c4 --channel dev         # 打包时直接指定
```

`--print` 只把版本号打到 stdout（供 shell `$(...)` 捕获），诊断信息一律走 stderr。

### 2. 产物命名与测试版标识

同一渠道产出三个文件（内容相同、用途不同）：

| 文件 | release 渠道 | dev 渠道 | 用途 |
| --- | --- | --- | --- |
| 裸名 | `fn-finstat.fpk` | `fn-finstat.fpk` | fnpack 原始输出，仅作流水线制品与构建证明，不挂 Release 附件 |
| 渠道别名 | `fn-finstat-latest.fpk` | `fn-finstat-dev.fpk` | **稳定下载入口**，同名覆盖，链接可长期不变 |
| 带版本号副本 | `fn-finstat-v0.7.1.fpk` | `fn-finstat-v0.7.1-dev.42.g1a2b3c4.fpk` | 回答"这是哪一次构建" |
| MD5 校验 | `MD5SUMS.txt` | `MD5SUMS.txt` | 上面**两个交付产物**的 MD5，`md5sum -c` 可校验下载完整性 |

**MD5 校验文件**由 `scripts/gen_checksums.py`（零依赖，标准库 `hashlib`）生成，
GNU coreutils 格式（`<md5><两空格><文件名>`），三条约束各有原因：

- **只列交付产物**，不列裸名——裸名不上传，列它等于让用户对着一个下载不到的文件发愁
- **任一产物缺失即失败**，不产出"部分校验"文件——残缺清单会让用户误判成自己下载坏了
- **固定 LF 换行**——Windows 下写 CRLF 会让 `md5sum -c` 把 `\r` 当成文件名的一部分，
  于是每个文件都报 `No such file or directory`（这个坑有单元测试锁着）

> 之所以不塞进 `releaseNode.txt`：那份日志允许"生成失败就降级成原始提交列表"，
> 而校验文件缺一行就必须失败——两者的容错策略正好相反。
> MD5 只保证**传输完整性**（下载残缺），防篡改仍看 Release 日志里的 SHA-256。

**随发布同步**（校验文件不只是本地产物，它整条链路都要能到用户手上）：

| 环节 | 落点 |
| --- | --- |
| 生成 | `build_fpk.sh` 第 8 步；`build_fpk.bat` 同步；`ci_build.sh` 在兜底 `cp` 之后**无条件重算** |
| 流水线制品 | 两条 yml 的 `artifacts.path` 都含 `./MD5SUMS.txt`（否则传不到 release 阶段） |
| Release 附件 | 两条 yml 的 `assertFiles` 都含 `MD5SUMS.txt` |
| 构建门禁 | build step 断言文件非空，并把内容打印进构建日志 |
| 发布说明 | `gen_release_notes.py --alias` 在正文末尾固定输出「下载哪个附件 + `md5sum -c` 怎么跑」 |

> 最后一格是补做的：`artifacts` / `assertFiles` 只保证文件躺在附件列表里，
> 而用户对着一堆附件并不知道那个 `MD5SUMS.txt` 是干什么的、该用哪条命令跑它。
> **发布了校验文件却不告诉用户怎么用，等于没发**——所以校验指引写进了 Release 描述正文。
> 同一处还把安装说明改成先指渠道别名（`fn-finstat-latest.fpk` / `fn-finstat-dev.fpk`），
> 用户不必再自己挑具体版本。

> 别名由 `sync_version.py::channel_alias()` 统一给出（`CHANNEL_ALIASES` 单一来源），
> 本地脚本与 CI 都走 `--print-alias` 取值，不在任何脚本里硬编 `latest` / `dev` 字符串。
> **别名只进文件名、绝不进版本号**：semver 里 `0.7.1-latest` 属于预发布段，排序上小于 `0.7.1`，
> 设备会把它当成比正式版更旧的版本而拒绝升级——这一点有单元测试锁死。

测试版标识因此落在五处，拿到包的人在任何环节都能识别：

| 位置 | dev 渠道取值 |
| --- | --- |
| 渠道别名文件名 | `fn-finstat-dev.fpk` |
| 带版本号副本名 | `fn-finstat-v0.7.1-dev.42.g1a2b3c4.fpk` |
| 包内 `manifest` 的 `version=` | `0.7.1-dev.42.g1a2b3c4` |
| 包内 `app/config.py` 的 `APP_VERSION`（「关于」页） | `0.7.1-dev.42.g1a2b3c4` |
| Gitee Release | tag `v0.7.1-dev.42.g1a2b3c4`，`prerelease: true`，描述顶部加「🧪 测试版本」声明 |

> `frontend/package.json` **始终只跟随 `VERSION` 原值**——它不在打包暂存目录内，
> 若写入派生版本会在源码树里留下脏版本号，并与 `sync_version.py --check` 门禁冲突。

选 `-dev` 预发布段而非 `+` 构建元数据的两个理由：semver 规定预发布版本小于同号
正式版，设备端从 `0.7.1-dev.x` 能正常升级到正式 `0.7.1`；且 `+` 在文件名与 URL
中需转义，会污染 Release 下载链接与 tag 名。

### 3. 本地打包支持渠道

`build_fpk.sh` / `build_fpk.bat` 均接受 `BUILD_CHANNEL`（默认 `release`）：

```bash
BUILD_CHANNEL=dev bash scripts/build_fpk.sh
```

两个脚本现在都会产出「渠道别名 + 带版本号副本」两个交付文件（此前只有裸名，带版本号副本仅 CI 产出），
并在 dev 渠道结束时打印「这是测试版本」提示。`BUILD_VERSION` / `CHANNEL_ALIAS` 已由环境变量给出时
直接采用，不重复派生——CI 用它们保证「包内版本」「产物别名」与「Release tag」三者同源。

### 4. CI 拆两条流水线

| 流水线 | 触发 | 渠道 | Release |
| --- | --- | --- | --- |
| `.workflow/build-fpk.yml` | `main` | `release` | 正式 |
| `.workflow/build-fpk-dev.yml` | `dev`（正则 `^dev$`） | `dev` | 预发布 |

两条流水线共用 `ci_build.sh`，各自在 build step 里**显式传渠道**，不依赖分支名推断。
`ci_build.sh` 新增第 2 步「渠道判定」，把版本号落盘到 `.local_tmp/build-version.txt`
供 yml 读取——**yml 不再自己 `cat VERSION`**，否则 dev 渠道下两处算法必然漂移
（产物名带 `-dev`、tag 不带）。dev 流水线额外断言版本号必须含 `-dev` 才继续。

### 5. 顺带修掉的两个既有问题

- **`gen_release_notes.py` 基线会把 dev tag 当发版基线**：`SEMVER_TAG_RE` 原为
  `^v\d+\.\d+\.\d+`（前缀匹配），`v0.7.1-dev.42` 也能命中。dev 每次推送都打 tag，
  正式版日志的起点会被"最后一次测试构建"截断，中间合入 main 的变更凭空消失。
  改为 `^v\d+\.\d+\.\d+$` 锚定，并加测试锁死。
- **`build_fpk.sh` 在 Git Bash 下必然失败**：`STAGE="$ROOT/..."` 里的 `$ROOT` 是
  MSYS 风格路径（`/d/pj/...`），交给原生 `python.exe` 会被解析成 drive-relative
  `\d\pj\...`，`sync_version.py` 报 `FileNotFoundError`。改用相对路径 `.local_tmp/fpk-stage`
  （脚本已 `cd "$ROOT"`），Linux CI 与 Git Bash 行为一致。

## 验证

- 新增 25 例测试：`derive_version` / CLI / `channel_alias`（`tests/test_sync_version.py`）、
  渠道与附件说明相关的 Release 日志测试（`tests/test_release_notes.py`）、
  校验文件生成（`tests/test_gen_checksums.py`）
- 全量 pytest **579 例**通过；`ruff check --select F,E9` 与 `black --check` 通过
- **实际打包实测**（本机 Git Bash + fnpack 1.2.3）：
  - `BUILD_CHANNEL=dev` → `fn-finstat-dev.fpk` + `fn-finstat-v0.7.1-dev.geb01922.fpk`，
    包内 `manifest.version` 与 `app/config.py` 的 `APP_VERSION` 均为 `0.7.1-dev.geb01922`，
    `frontend/package.json` 仍为 `0.7.1`（未被污染）
  - `BUILD_CHANNEL=release` → `fn-finstat-latest.fpk` + `fn-finstat-v0.7.1.fpk`，
    包内版本号 `0.7.1`，无回归
  - 两个渠道的 `MD5SUMS.txt` 各 2 行、无 CR 字节，逐行重算 md5 与实际文件一致；
    切渠道重打包后校验文件随之更新（两渠道 fpk 的 MD5 不同，dev `78e2b0b0…` / release `90c998d2…`）
  - 两条流水线 yml 经 `yaml.safe_load` 解析校验，`prerelease` 分别为 `false` / `true`，
    artifacts 与 assertFiles 中的渠道别名、`MD5SUMS.txt` 各自正确
  - `gen_release_notes.py --alias fn-finstat-dev.fpk` 实测输出：描述正文末尾固定含
    「**安装**：下载附件 `fn-finstat-dev.fpk`（该渠道的固定入口）或 `fn-finstat-v…fpk`」与
    「**校验（MD5）**：… `md5sum -c MD5SUMS.txt`」两行，用户拿到附件就知道怎么用

## 边界与后续

- **fnpack 不校验版本号格式**：实测 1.2.3 接受 `0.7.1-dev.42`、`0.7.1-dev.42+gsha`、
  `0.7.1.dev42` 等写法并原样写进包内。也就是说没有打包门禁能拦住格式错误的版本号，
  正确性完全依赖 `derive_version` + 单元测试这条链（规范已写入 §1.1）
- **设备端是否接受带 `-dev` 的 `manifest.version` 未在真机验证**：fnpack 侧已放行，
  飞牛应用中心侧的校验规则未知。若真机拒装，降级方案是 `manifest` 保持纯数字、
  只在文件名与「关于」页标注测试版
- **dev tag 会随提交堆积**：每个 push 产生一个 tag。当前以可追溯性优先接受该代价；
  若要收敛可改固定 tag + `allowUpdate`，代价是 tag 不再对应实际构建内容（已写入发布流程文档）
- 从正式版降级到同号测试版（`0.7.1` → `0.7.1-dev.x`）会被设备判为降级，需先卸载
