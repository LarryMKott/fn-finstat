## 1. 评审范围与总体结论

对两份架构设计方案做全栈评审，从**安全、数据模型、接口契约、前后端交互、性能、Vue 架构**六个维度逐项核对实现代码。共发现 **13 个问题：1 高、4 中、8 低**，无阻断性设计缺陷，方案总体合理、可继续作为演进基线。

**评审确认的设计亮点**（本次核实无问题，保持现状）：

- AI 密钥不回传明文，仅 `has_api_key` + 尾号提示（`app/api/ai.py:40-44`）；
- NAS 目录路径按角色回显，普通账号只见目录名（`app/api/nas.py:37-40`）；
- AI 报告 Markdown 渲染先整体转义 HTML 再做有限语法替换，无链接/图片语法，`v-html` 无注入面（`frontend/src/components/AIReportModal.vue:189-202`）；
- 备份导出在单事务内完成四节读取，快照一致（`app/services/backup_service.py:73`）；
- `RESTORE_LOCK` 由恢复/迁移/导入三方复用，导入侧 `acquire(blocking=False)` 快速失败；
- `bills` 表 `user_id/tx_time/tx_type/category` 均有索引，覆盖主要筛选路径；
- 管理面策略表 `_ADMIN_RULES` 与路由守卫双层防御，权限拦截返回统一响应体。

## 2. 问题清单

风险等级定义：**高**＝信任边界/数据正确性缺陷，条件具备即造成实际损害；**中**＝特定场景下的功能或安全缺陷，需要修但可排期；**低**＝健壮性/可维护性改进。

### 🔴 高

#### H-1（安全/身份）「无身份头即管理员」的全量放行不区分运行形态 ✅ 已修复（2026-09-16 P0 批次）

> **修复记录**：`core/permissions.py::access_rejection` 与 `deps.require_admin` 按运行形态区分——fnOS 模式缺失身份头一律 401（新增 `ErrorCode.UNAUTHORIZED=10006`，文案「请通过飞牛桌面访问本应用」）；独立部署保留放行。逃生开关 `FNOS_ALLOW_HEADERLESS=1`（默认关闭）供设备排障。测试见 `tests/test_permissions.py`。

- **现象**：`app/core/permissions.py::permits` 中 `return not user.user_id or user.is_admin`——`user_id` 为空串一律按本地单机用户全量放行，**在 fnOS 网关模式下同样生效**，不区分 `IS_FNOS`。身份头的唯一防线是「外部流量到不了应用」（uds socket / 127.0.0.1）。
- **影响**：信任链单点依赖网关行为与网络隔离。网关配置变更（如反代路径透传、新接入方式）导致请求未携带 `X-Trim-*` 头到达应用时，任何匿名请求即获得管理员权限（可导出全量备份、覆盖恢复、改数据库配置）。方案文档第 1/8 节已声明此前提，但代码层没有按形态收紧。
- **建议**：利用已有的 `config.IS_FNOS` 区分形态——fnOS 模式下身份头缺失返回 401（或 403），仅独立部署模式保留「空身份 = 单机唯一用户」放行；同时在 `deps.py` 与权限中间件两处同步该判定并补测试（无头 + fnOS 模式 → 拒绝）。

### 🟡 中

#### M-1（安全）独立部署模式无 Host/Origin 校验，存在 DNS rebinding 与跨站触发面 ✅ 已修复（2026-09-16 P0 批次）

> **修复记录**：新增 `core/middleware.py::SourceGuardMiddleware`（仅独立部署生效）：Host 白名单（`config.ALLOWED_HOSTS` = 回环集合 ∪ 具体绑定 HOST；`HOST` 为通配地址时白名单关闭、保留 Origin 校验）；POST/PUT/DELETE/PATCH 校验 Origin 与请求 Host 同源（缺失放行、非同源 403）。`HOST` 非回环时 `main.py` 启动告警。测试见 `tests/test_source_guard.py`。

- **现象**：应用不校验 `Host` 头，也不校验变更类请求的 `Origin`/`Sec-Fetch-Site`。独立部署（127.0.0.1:8090）场景下：恶意页面可通过 DNS rebinding 将域名解析到 127.0.0.1，绕过同源策略**读取**响应（如 `GET /api/settings/backup` 全量账单）；普通跨站表单 POST（无预检）可触发无请求体/表单体端点（如 `POST /api/settings/automation/{key}/run`、multipart 上传 `/api/upload/*`），配合 H-1 空身份放行即可成功。
- **建议**：非 fnOS 模式增加 Host 白名单中间件（仅允许 `127.0.0.1:8090`/`localhost:PORT`，`config.HOST` 已有值可复用）；变更类请求（非 GET/HEAD）校验 `Origin` 为空或在白名单。落点：`app/core/middleware.py` 新增一个纯 ASGI 中间件，置于权限中间件外层。

#### M-2（数据模型）`tx_id` 全局唯一 + 去重不区分用户，多账号互相「吞」账单

- **现象**：`app/db/models.py:44` 中 `tx_id` 为**表级全局唯一**；导入去重 `BillDAO.existing_tx_ids`（`app/db/dao/bill_dao.py:177`）查询不带 `user_id`，`insert_many` 的 `OR IGNORE` 也作用于全局约束。
- **影响**：家庭场景下两个账号导入同一份账单（夫妻共用微信/亲情卡/同一云闪付卡导出）时，后导入方全部被静默计为「重复跳过」，**该用户永远看不到这批流水**——与「数据按 `user_id` 隔离」的隔离原则自相矛盾。
- **建议**：唯一约束改为 `(user_id, tx_id)` 联合唯一（迁移 v6：删旧唯一索引、建新联合索引；`tx_id` 为可空，注意 NULL 不参与唯一语义符合预期）；`existing_tx_ids` 增加 `user_id` 过滤；`imported_files.content_hash` 判重同步按 owner 维度复查。补跨账号导入测试（`USER_A` 导入后 `USER_B` 导入同流水应各自入库）。

#### M-3（前后端交互/接口）长耗时操作无任务状态查询，前端超时后进度「失联」

- **现象**：数据库迁移（前端 300s 超时，大数据量后端可能更久）、AI 存量重分类（后端预算 240s/1000 条）、AI 报告生成等长任务为同步端点。前端 fetch 中断**不会取消后端执行**，也无任何查询进度/结果的接口；用户重试会撞上 `RESTORE_LOCK`/`_CLASSIFY_LOCK` 收到互斥报错，无法区分「还在跑」和「失败了」。
- **建议**：短期（低成本）：前端超时文案明确「后台仍在处理，请稍后刷新查看」，设置页迁移卡片轮询 `/api/settings/database` 概览状态。中期：沉淀通用任务查询——调度器已有 `task_runs` 表与软锁机制，可为迁移/重分类登记运行记录并暴露 `GET` 状态端点，前端改为提交任务 + 轮询。

#### M-4（数据模型/备份）「全量备份」不含 AI 报告与自动化配置，跨库迁移同样遗漏

- **现象**：`export_backup`（`app/services/backup_service.py:65`）只导出 categories/bills/budgets/assets 四节；`copy_database` 搬移的也是同四张表。`ai_reports`（用户已归档的 AI 报告）、`scheduled_tasks`（自动化任务定义与启停状态）、`imported_files`（导入登记）均不在内。
- **影响**：UI 以「全量备份」表述（`settings/BackupCard`），但恢复/换库后 AI 报告清空、自动化任务回到默认，用户感知为数据丢失；备份文件 `format_version=1` 的契约也未给这些表留位置。
- **建议**：备份扩充 `ai_reports`、`scheduled_tasks` 两节（`task_runs`/`imported_files` 可选，建议至少登记变更于 `docs/发布流程与Release日志.md` 同级的说明），`format_version` 升为 2 并保持对 v1 的兼容读取；`copy_database` 同步扩充搬移清单；`fpk_selfcheck`/测试同步更新。

### 🟢 低

#### L-1（接口）`GET /api/ai/config` 未纳入管理面

普通账号可读 base_url、model、是否已配密钥及尾号（`app/api/ai.py:36-44`）。信息敏感度低，但「配置详情」与「配置修改」（PUT 已在 `_ADMIN_RULES`）读权限不一致。建议：GET 一并纳入管理面，或响应瘦身至 `enabled/has_api_key`。注意 `_ADMIN_RULES` 与路由守卫两处同步 + 补测试。

#### L-2（性能）统计月分组 `substr(tx_time,1,7)` 无法走索引

`stat_dao` 各聚合对 `bills` 按字符串月份分组，`tx_time` 索引对 `substr` 分组无效，为全表扫描。家庭量级（数万条）无感；若未来迁 MySQL/PG 且数据到十万级，建议：新增冗余 `month` 生成列（迁移时回填）或改用范围条件 + `GROUP BY` 可用索引的写法。当前量级**无需立即处理**，记录在案。

#### L-3（Vue 架构）`BillsPanel.vue` 777 行巨石组件

筛选、表格、回收站、批量操作、AI 归类、导出全在一个文件。建议按既有子域惯例拆分：`BillFilterBar`、`BillTable`/`BillCardList`、`BillBatchBar` 子组件 + `composables/useBillQuery.js`（筛选状态与 load/isCurrent 序号逻辑），`BillsPanel` 只做编排。不改行为，纯结构重构，可趁下次功能迭代顺带做。

#### L-4（前后端交互）`runTask` latest 模式不 abort 在途请求

latest 只作废旧任务的 HUD 状态写入，旧 fetch 仍跑完浪费带宽与服务端算力（快速翻页/切换筛选时成倍请求）。`client.js` 已有 `AbortController` 信号合并能力，建议 `runTask` 在 latest 接管时对旧任务的 signal 调用 `abort()`（业务无感知：`isCurrent()` 已先行拦截），并在 `tests/loading.test.mjs` 补「旧请求被 abort」用例。

#### L-5（Vue 架构）首屏主题判定逻辑双份维护，一致性校验未进门禁

`frontend/index.html` 内联 IIFE 与 `theme.js`/`fnos.js` 各自实现同一套优先级链，存在漂移风险；现有 `tests/verify_theme_parity.py` 为手工脚本，不在 CI 门禁。建议：将该校验改写为 Node 原生测试（对两处逻辑做同输入同输出断言）随 `npm test` 进门禁；或至少在两处代码头部互相注明「修改必须同步」。

#### L-6（性能/可靠性）SQLite `busy_timeout=5000` 在并发写下偏紧

NAS 定时导入（批量 insert，WAL 写事务）与用户编辑操作并发时，写锁等待上限 5 秒，超限抛 `SQLITE_BUSY`。发生概率低且 `insert_many` 分批，但一旦发生表现为偶发导入失败。建议：观察 `app.log` 是否有 busy 记录，必要时上调至 15s；批量导入每批之间让出调度（已有分批结构，加 `time.sleep(0)` 级别让出即可）。

#### L-7（Vue 架构/交互）刷新后回到看板，页签状态不进 URL

`store.tab` 不持久化、不进 hash，刷新/分享链接都回到 dashboard。无 router 也可低成本解决：`watch(tab)` 同步 `location.hash`，启动时读初始 hash，并监听 `hashchange` 支持前进后退。建议作为独立小改动落地（注意与 SW 网络优先策略无冲突）。

#### L-8（后端并发）同步长任务占用线程池

FastAPI 同步端点运行于线程池（默认约 40 线程），迁移/重分类单次可占 5 分钟。家庭量级并发极低，实际风险小；若做 M-3 的任务化改造，可顺势把这些端点改为「提交即返回 + 后台线程执行 + 状态查询」，同时消除线程占用与超时失联两个问题。

## 3. 修复优先级建议

| 批次 | 内容 | 理由 |
| --- | --- | --- |
| P0（尽快）✅ **已完成（2026-09-16）** | H-1、M-1 | 均为信任边界问题，改动小（形态判定 + Host/Origin 中间件），收益大 |
| P1（下个迭代） | M-2、M-4 | 数据正确性与备份完整性，涉及一次 schema 迁移（v6）与备份契约 v2，宜早不宜迟 |

| P3（记录在案） | L-2、L-6、L-7、L-8 | 当前量级无感，触发条件明确（数据量/并发/用户反馈）后再做 |

## 4. 评审方法说明

结论均对照 0.7.0 实际代码逐条核实（`app/core/permissions.py`、`app/db/models.py`、`app/db/dao/bill_dao.py`、`app/services/backup_service.py`、`app/api/ai.py`、`app/api/nas.py`、`frontend/src/components/AIReportModal.vue` 等），非仅基于文档推演。方案文档中与代码不符之处（如《前端开发规范》8.3 节收支色彩方向与 `style.css:83-86` 相反）另行记录，不在本报告问题清单内重复展开。
