## 1. 需求原文与拆解

> 分类关键词 AI 自动生成（包括可自动细分子类），自动添加分类可人工开启关闭

拆成三条能力：

| 编号 | 能力 | 一句话定义 |
| --- | --- | --- |
| **CAP-1** | 关键词 AI 生成 | 让模型代替人工维护关键词表：给定分类名 + 脱敏商户样本，产出关键词候选，人工确认后入库并参与匹配 |
| **CAP-2** | 自动细分子类 | 分类支持两级层级，AI 依据该分类下的真实商户分布建议子类，并同步产出每个子类的关键词 |
| **CAP-3** | 自动建分类开关 | AI 归类流水时可提出候选白名单之外的新分类名；是否允许它**自动写入**分类表由开关控制，默认关闭 |

三条共享同一套底座：**一张持久化的关键词表 + 分类层级 + 一组 AI 生成任务 + 一组开关**。

## 2. 现状盘点（代码证据）

### 2.1 归类三级串链

| 优先级 | 通道 | 落点 |
| --- | --- | --- |
| 1 | 已学习规则 | `app/services/learned_rule_service.py`（`_effective_rules` 要求 `hits >= 2`），表 `learned_rules`（`app/db/models.py:671`） |
| 2 | 内置关键词 | `app/utils/category_matcher.py` —— **硬编码 Python 字典** `RULES`，10 个分类约 200 词；`match_category` 按字典序遍历，首个子串命中即返回 |
| 3 | LLM 逐条归类 | `app/services/ai_service.py:227` `classify_records` → `_parse_assignments`（`:200`） |

**CAP-1 的痛点就在第 2 条**：`RULES` 是代码常量，加一个关键词要改文件发版；且它**只能通过子串命中**命中，词面没覆盖到的商户一律漏到「其他」。

### 2.2 AI 归类为什么今天建不了新分类

`_parse_assignments`（`ai_service.py:200`）签名带 `allowed: set[str]`，逐条过滤：

```python
if name in allowed:
    result[idx] = name
```

候选集来自 `CategoryDAO.list_all()`（`enhance_import_records` `:291`）。所以模型即使认定某笔消费属于一个新类目，也只能被迫塞进已有的某个分类或留在「其他」。**CAP-3 就是放开这个 `allowed` 约束，且必须是 opt-in。**

### 2.3 分类为什么今天分不了层

`Category`（`app/db/models.py:99`）只有 `id` / `name`，`name` 全局唯一。没有 `parent_id`，没有来源标记。**CAP-2 必须先做 schema 变更。**

### 2.4 配置存放

AI 走 `app/file_settings.py` 的 `AISettings` dataclass，落盘 `DATA_DIR/ai_config.json`（密钥加密）。现有唯一开关 `enabled`（控制导入时是否自动二次归类）。**CAP-3 的开关就在 `AISettings` 上加字段，`load_ai_settings` 用 `data.get(..., 默认)` 读，天然向后兼容老配置文件。**

### 2.5 现状 schema 版本

`app/db/migrations.py:21` → `LATEST_SCHEMA_VERSION = 15`，注册表 `_MIGRATIONS` 到 `14: _v15_add_api_tokens`。本次需 **v15 → v16**。

## 3. 目标与非目标

**目标**

- 关键词从「写死在代码里」变成「表里的数据」，界面可见、可增删改、可停用。
- AI 只做**候选生成**，最终入库一律经「预览 → 人工勾选确认」两段式（成本与质量双闸门）。
- 全自动行为（归类时自动建分类）默认关闭，逐步可选开启，且带配额护栏。
- 零新增运行时依赖，全部复用现有 `_chat` 单通道（`ai_service.chat`）。

**非目标**

- 不做三级以上分类树（两级父子足够，`String(64)` 名称 + 面包屑即可表达）。
- 不改动现有 `learned_rules` 语义（它继续走「手动纠正 + 2 次门槛」，与本方案的 `category_keywords` 并列而非合并）。
- 不自动迁移既有流水到子类（见 D-1，默认行为零变化）。
- 不引入 embedding / 向量检索（仍违反「零新增运行时依赖」红线）。

## 4. 数据模型改造（schema v16）

### 4.1 `categories` 加列

| 列 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `parent_id` | INTEGER NULL | NULL | 父分类 id；NULL = 顶层。两级为限（子分类不可再有子） |
| `source` | VARCHAR(16) NOT NULL | `'manual'` | 取值 `builtin` / `manual` / `ai`；仅影响界面徽标，不参与匹配 |
| `created_at` | FLOAT NOT NULL | 0 | epoch 秒，排序用 |

三列均为「可空或带默认值」的新列，SQLite / MySQL / PostgreSQL 都用 `ALTER TABLE ... ADD COLUMN` 即可，**不需要重建表**（对比 v8 `budgets` 因改唯一键才走了 SQLite 建新表搬数据那条重路径）。

名称唯一约束保持不变 —— 子类名也全局唯一。这是**有意为之**：`bills.category` 是 `String(64)` 存分类名的，名字唯一才能保证任何位置的改名同步（`CategoryDAO.rename` `:49` 的 `update(Bill).where(Bill.category == old)`）不出二义。

### 4.2 新表 `category_keywords`

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | PK | |
| `category_id` | INT NOT NULL, INDEX | 指向 `categories.id` |
| `keyword` | VARCHAR(64) NOT NULL | 参与子串匹配 |
| `source` | VARCHAR(16) NOT NULL | `builtin` / `ai` / `manual` |
| `enabled` | BOOL NOT NULL DEFAULT TRUE | 单条停用（不删除，保留证据） |
| `created_at` | FLOAT NOT NULL | |

唯一约束 `(category_id, keyword)`。删除分类时级联清理该分类的关键词（DAO 层显式删，与 `CategoryDAO.delete` 同事务）。

### 4.3 为什么新建表而不是塞进 `learned_rules`

| 维度 | `learned_rules` | 新建 `category_keywords` |
| --- | --- | --- |
| 语义 | 「用户手动纠正沉淀」 | 「这个分类由哪些词表征」 |
| 生效门槛 | `hits >= 2` 才参与匹配 | 入库即生效（可单条停用） |
| 版本演进 | 改门槛会动摇自学习语义 | 独立演进，互不影响 |
| 可扩展性 | 一行只存一个 pattern，无来源 / 停用之外的属性 | 可扩权重、命中计数等 |

把 AI 词塞进 `learned_rules` 只能伪造 `hits=2`，是脏数据。**结论：新建表。**

### 4.4 内置 RULES 播种

迁移 `_v16_add_category_keywords` 里一次性把 `category_matcher.RULES` 灌进 `category_keywords`（`source='builtin'`），并置位 `app_meta` 的 `keywords_seeded=1` 防重跑。播种后：

- `category_matcher.match_category` **退出匹配链**（改为仅作为 seed 数据源保留），统一走新的 `keyword_service.match()` 读表；
- 好处：界面能完整展示「某分类为什么命中某商户」，内置词也一样可停用；
- 风险：老用户行为完全不变（种子词与 RULES 逐字一致），**行为等价**。

> 待决策 **D-3**：是否播种。备选是保留 RULES 双通道匹配（表里只见增量词），实现更简单但界面无法呈现全貌。本方案推荐播种。

## 5. 匹配链（改造后）

```
1. learned_rules   （用户纠正·hits≥2·最长优先）
        ↓ 未命中
2. category_keywords（AI 生成 + 手工录入 + builtin 播种；按 keyword 长度降序，长者优先）
        ↓ 未命中
3. LLM 逐条归类    （ai_service.classify_records；CAP-3 开启时才可产出新分类）
```

第 2 层的排序规则沿用 `learned_rule_service._effective_rules` 已验证的口径（`-len(pattern), -hits, id`）：**更具体的长词优先于宽泛词**，避免「美团」被「购」之类短词抢先。

新增服务 `app/services/keyword_service.py` 承载这张表的 CRUD + `match()`；`app/utils/category_matcher.py` 降级为纯 seed 数据源（保留向后 import 兼容）。

## 6. AI 生成任务设计

三条任务都走 `ai_service.chat`（已把 SSRF 防线与超时策略收口在这条唯一通道上），都要求 `response_format: json_object`，都不带任何金额明细。

### 6.1 T-A 关键词生成（CAP-1）

输入：分类名、`parent_id` 路径（若有）、**该分类下商户名去重 Top 30**（脱敏：只有商户字符串，无日期 / 无金额 / 无备注）。
输出：`{"keywords": ["外卖", "美团外卖", ...]}`，目标 30–40 条。
清洗：去掉与已存在词重复、长度 < 2、包含特殊符号、命中其它分类已有词的（冲突词标记出来交由人工裁决）。

### 6.2 T-B 子类生成（CAP-2）

输入：分类名 + 同上脱敏商户 Top 50 + 该分类流水数（**只给条数，不给金额**）。
输出：

```json
{"children": [{"name": "外卖", "keywords": [...], "reason": "商户名集中在美团/饿了么"}]}
```

约束写进 system prompt：子类名 ≤ 6 字、数量 ≤ 5、不得与已有分类重名、每个子类至少 5 个关键词。返回后服务端做二次过滤（重名剔除、超长截断、数量上限截断），**不信任模型的结构承诺**。

### 6.3 T-C 归类时自动建分类（CAP-3）

改造 `_parse_assignments`：增加一个 `allow_create: bool` 分支。

- `allow_create=False`（默认）：与今天完全一致，非白名单结果丢弃。
- `allow_create=True`：白名单之外的结果先进入候选队列，**同一批中被 ≥2 笔流水选中的新类目才创建**（抗单次幻觉），且**单批最多创建 2 个**（配额护栏，防模型批量发明 20 个分类把界面搞烂）。新建分类 `source='ai'`，写入审计日志 `category.auto_create`。落表名长度截断到 `CATEGORY_NAME_MAX_LENGTH`（20）。

### 6.4 隐私红线（沿用既有，不放松）

- 送给模型的**只有商户名去重列表与计数**，绝不含日期、备注、个人账户、金额。
- 所有入参与返回值走 `logger.debug`，不落 INFO。
- 开关关闭时**不发任何额外请求**（零成本、零外发）。

## 7. 开关设计

`AISettings`（`app/file_settings.py:98`）新增三个字段，全部默认 `False`：

| 字段 | 控制 | 默认 |
| --- | --- | --- |
| `auto_keyword_enabled` | 导入 / 批量重归类时，AI 顺带回填它识别出的高频关键词（走 T-A 的批内变体） | False |
| `auto_category_enabled` | **CAP-3**：允许 AI 归类时创建新分类 | False |
| `auto_subcategory_enabled` | 允许 AI 在新建分类时直接建为某个现有分类的子类（需 `auto_category_enabled` 同时为真） | False |

`load_ai_settings` 用 `bool(data.get("auto_category_enabled", False))` 读取 —— 老配置文件缺字段自动得到 `False`，**升级即安全**。

配置回显 `AIConfigOut` 增加同名字段；前端设置页 AI 卡片加三个 Toggle。**注意 `AIConfigUpdate` 的合入语义**（`_apply_form`）：`None` 表示不变，所以开关要显式传 `bool` 不能省略。

> `enabled`（导入自动二次归类）继续独立存在，语义不变：它管「要不要调用 LLM 逐条归类」，新开的三个开关管「LLM 能不能动你的分类体系」。

## 8. API 契约

### 8.1 分类（扩展既有）

| 方法 | 路径 | 变更 |
| --- | --- | --- |
| GET | `/api/category` | `CategoryOut` 增 `parent_id` / `source` / `children: list[int]`；列表按父子折叠输出 |
| GET | `/api/category/tree` | **新增**：树结构 + 每节点 rollup（含子孙）流水数与金额，供改造后的分类管理页使用 |
| POST | `/api/category` | `CategoryCreate` 增可选 `parent_id` |
| PUT | `/api/category/{id}` | 不变 |
| DELETE | `/api/category/{id}` | **契约变更**：有子分类时拒绝删除（400 + 明确文案），要求先移走或删除子分类。防止孤儿层级 |

### 8.2 关键词（新增）

```
GET    /api/category/{id}/keywords            列出（含 source / enabled）
POST   /api/category/{id}/keywords            手工新增（body: {keywords: [...]}, 支持批量）
PUT    /api/category/keyword/{keyword_id}     {enabled} 停启用
DELETE /api/category/keyword/{keyword_id}     删除
```

写操作按既有口径收口到 `AdminUser`（分类全局共享，与 `app/api/category.py` 现有写权限一致），读操作公开。

### 8.3 AI 生成（新增，**均为两段式**）

```
POST /api/ai/category/keywords          {category_id, hint?}  → 候选词列表（不落库）
POST /api/ai/category/keywords/apply    {category_id, keywords:[...]} → 实际入库条数

POST /api/ai/category/children          {category_id}  → 子类方案预览（含每子类关键词）
POST /api/ai/category/children/apply    {category_id, children:[{name, keywords}], migrate_bills:false} 
                                        → 建子分类 + 落关键词；migrate_bills=true 时把父分类下命中的流水迁到子类
```

拆分「生成」与「落库」是刻意的：**生成一次要花 token，用户可能只想要其中一半的词**，预览态勾选可重复应用而无需重新计费。

## 11. 安全与成本护栏

| 风险 | 护栏 |
| --- | --- |
| 模型幻觉批量发明垃圾分类 | 单批新建 ≤2 个、需 ≥2 笔流水共同提名、名字 ≤20 字符、`source='ai'` 可溯源 |
| 关键词污染全库（一个"购"字命中所有消费） | 最小长度 2、同名唯一约束、单条可停用、新建后不自动重跑存量流水 |
| token 成本失控 | 生成类任务全部人工触发（非后台自动）；`auto_keyword_enabled` 即便开启也只在归类请求里顺带做一次，且有时间预算复用 `classify_batches` 的 `time_budget` |
| 隐私外泄 | 入参仅脱敏商户名；严禁备注 / 金额 / 日期。测试里加断言检查 prompt 内容 |
| 权限绕过 | 关键词写操作与 AI 生成入口统一走 `AdminUser`（与 AI `/config`、`/test` 同口径；`/test` 注释已说明为何必须管理员：任意账号可诱导服务端把共享 Key 发往受控端点） |
| 误删有子类的分类 | 删除前检查 `parent_id` 指向，非零拒绝 |
| 匹配顺序歧义 | 长词优先 + `builtin` 播种后 `RULES` 完全退出，单一数据源 |

## 14. 待决策（需拍板）

| # | 问题 | 推荐 | 另一选项的代价 |
| --- | --- | --- | --- |
| **D-1** | 子类是否参与**自动**归类？`bills.category` 存叶子还是顶层？ | **默认不参与**：AI 只建议子类，是否把流水迁过去由用户一次性点「细分」触发。bills.category 仍是最终所在分类（选中细分后即叶子） | 若默认落到子类，用户原有「餐饮预算」会突然失效（钱记到"咖啡"上），预算/报表/健康评分全部要跟着支持层级 rollup，破坏面极大 |
| **D-2** | 自动建分类的门槛 | 同一批 ≥2 笔提名 + 单批 ≤2 个 + 默认关闭 | 门槛放宽（1 笔即建）会被单次幻觉污染；收紧到 ≥3 笔则几乎不触发，功能形同虚设 |
| **D-3** | 内置 `RULES` 是否播种进关键词表 | **播种，`RULES` 退位为 seed**，单一数据源 | 不播种则双源匹配，界面看不到内置词，也停不掉错误的词 |
| **D-4** | 关键词生成的 token 由谁承担 | 人工显式触发才调用（每次一个分类，成本厘级） | 后台批量自动生成全部分类会一次性跑 10+ 次调用，需引入任务队列与预算上限，收益不匹配复杂度 |
