## 1. 背景与范围

T-6.5 的数据附录（2026-09-15）已保证「所有数字由后端算好喂给模型，模型只做解释」，附录以原始
JSON 折叠区呈现。遗留的精细级目标是「点数字看来源」：报告里的每个汇总数字都能在界面回溯到
来源数据。本轮在 NL 查询（T-6.1/T-6.2）与流水多值筛选上线后完成联动，v0.6「会说话的账本」
出口标准就此全部达成。

## 2. 技术方案

**为什么从附录入手而不是报告正文**：正文数字嵌在模型生成的自然语言里，逐个锚定既脆弱又可能
把模型写错的数字"追溯"成正确口径；附录才是权威数字清单——`report_context_period()` 的全部
字段即模型看到的全部数字，逐项可追溯等价于"每个数字都能回溯"。

**口径映射**（`AIReportModal.vue` 的 `appendixGroups` computed）：附录每个数字确定性映射到
一段流水页筛选口径——

| 附录数字 | 口径 |
| --- | --- |
| 本期 / 上期收入、支出 | 周期起止 + tx_type |
| 分类支出（本期 / 上期） | 周期起止 + expense + 该分类 |
| 商户 TOP | 周期起止 + expense + 该商户关键词 |
| 单日最高支出 | max_expense_day 当日 + expense |

点击即写 `billsFilterHandoff` 并切到流水页（复用 T-6.2 机制），流水页按同口径列出构成该数字
的每一笔，口径 chip 明示筛选来源，可一键清除——用户逐笔核对"这个数字怎么算出来的"。

**前后端口径对齐**：`utils/datetime.js` 新增 `periodRange(type, value)` / `prevPeriod(type, value)`，
与后端 `utils/period.py` 逐位对齐（含闰年与 30/31 天月份）；跳转后看到的流水与报告统计的
必须是同一批，否则追溯就成了误导。对齐性由 `frontend/tests/datetime.test.mjs` 守住
（用例值取自后端测试与日历事实）。

**兼容**：旧归档的 `stats_summary` 缺 `period_type` 时回退 `month` / `ctx.month`；
周期标识异常时不提供追溯入口（`appendixGroups` 为空，仅展示原始 JSON）。

## 4. 已知边界

- 追溯跳转按「单分类 / 单商户关键词」精确复现口径；附录数字本身都是单分类或单商户维度，无损失；
- 报告正文中的数字仍以附录为权威来源（正文数字来自附录，模型被要求不得编造）；
- 归档报告的追溯依赖归档时落库的 `stats_summary`，其口径是生成时点的快照——
  之后修改过流水的，追溯结果会与快照数字不一致，属预期（历史报告不重算）。
