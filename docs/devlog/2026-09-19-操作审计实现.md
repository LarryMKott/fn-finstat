## 1. 设计

- **打点方式**：各 service 写操作成功后显式调用 `audit_service.record(...)`
  （而非 ORM 事件监听）——项目内大量写路径走 Core 语句级批量 UPDATE /
  insert_ignore_rows，事件监听捕获不到；显式打点覆盖完整、能拿到前后差异。
- **best-effort**：record 内部全量捕获异常只记 warning，审计故障绝不影响
  业务主流程；审计写入复用请求级会话，与业务同事务（业务回滚则该条审计
  一并回滚——失败操作不留痕是合理语义）。
- **差异摘要**：`diff_summary(before, after, {字段: 中文标签})` 输出如
  「金额 10.0→99.0；分类 餐饮→交通」，未变化字段不出现。
- **保留窗口 90 天**：写入时顺带清理过期行（与通知中心同模式，`created_at`
  有索引）；**审计表不参与备份导出，replace 恢复也不清空本表**——审计链
  在灾难恢复后依然完整，恢复动作本身会再记一条新审计。
- **权限**：`GET /api/audit` 管理员可查全部账号（可按操作人 / 动作过滤），
  普通账号由服务端强制只看自己的操作（不进 ADMIN_RULES 管理面，与
  get_database_info 的裁剪口径一致）；无网关身份的本地/独立部署视为唯一用户。

## 2. 打点覆盖（按动作前缀）

| 前缀 | 覆盖动作 |
| --- | --- |
| bill.* | create / update（前后 diff）/ delete / restore / purge / recycle_empty / batch（改分类、打标签、报销标记、批量删还原） |
| category.* | create / rename（含同步流水数）/ delete（含并入数）——API 层打点（全局资源，操作人在路由层） |
| ledger.* | create / update / delete（含并入各表条数）——API 层打点 |
| budget.* | upsert / delete / family_upsert / family_delete |
| asset.* | create / update（diff）/ delete |
| family.* | create / join / leave / disband（含自动解散）/ settings / member_remove / invite_regenerate |
| reimb.* | create / update（状态流转与到账）/ delete / attach / detach |
| loan.* | create / update（diff）/ delete / payment_add（含结清提示）/ payment_delete |
| rules.* | update / delete（API 层，全局资源） |
| backup.restore / db.migrate / db.claim | 恢复（覆盖或合并，含迁移统计）/ 数据库迁移并切换 / 历史流水认领 |

## 3. 接口与前端

- `GET /api/audit?limit=&offset=&action=&user_id=`：返回 `{total, items}`，
  items 按时间倒序（user_id / action / created_at 均有索引）。
- 设置页新增「操作审计」卡片：动作 / 操作人过滤、时间倒序表格
  （时间 / 操作人 / 动作中文名 / 摘要）；普通账号打开即只看到自己的操作。
