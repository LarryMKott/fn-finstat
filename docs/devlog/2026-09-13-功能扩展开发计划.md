## 1. 背景与目标

### 1.1 现状基线（作为计划前提）

| 维度 | 现状 |
| --- | --- |
| 功能 | 四平台账单导入（微信 xlsx / 支付宝 csv / 京东 csv / 云闪付 csv）、NAS 目录批量导入、导出、回收站、标签与报销、批量操作 |
| 分析 | 统计看板、月度趋势、分类饼图、商户 TOP、消费日历热力图、年度对比、消费地图（城市气泡） |
| 智能 | DeepSeek 智能分类（导入时二次归类 + 存量重归类）、AI 月度消费报告 |
| 财务 | 预算管理（总/分类）、净资产快照与趋势 |
| 平台 | fnOS FPK 打包、统一网关身份隔离（`X-Trim-Userid`）、PWA、飞牛官方 Web SDK 主题联动、三方言数据库（SQLite/MySQL/PG）+ 运行期迁移、备份恢复、运行日志 |
| 工程 | 单进程 uvicorn（`cmd/main` 以 `--uds` 启动，无 `--workers`）、分层清晰（api / services / db.dao / parsers / schemas）、248 例 pytest、`scripts/verify_*.py` 场景自检、打包与 CI 双重测试门禁 |
| 数据约束 | 业务数据统一写 `TRIM_PKGVAR`，禁止写 `TRIM_APPDEST`；用户数据按 `user_id` 隔离，分类全局共享 |

### 1.2 要解决的核心问题

按痛点强度排序，本计划要解决的三件事：

1. **导入仍是手工动作**——用户每月必须去微信/支付宝手动导出、再手动上传。这是当前产品最大且唯一的"高频摩擦"。
2. **应用是被动的**——它只在用户主动打开时工作；NAS 常年在线这件事，除了省了台服务器的钱，还没有被利用起来。
3. **智能停在"事后归类"**——AI 只用来分类和写月报，没有变成可对话、可预测、可主动提醒的能力。

### 1.3 规划原则

| 原则 | 含义 | 反面案例 |
| --- | --- | --- |
| **底座先行** | 有多个功能依赖的公共能力必须先做 | 先做"月度自动报告"而不是先做定时任务底座 |
| **复用优先** | 优先做能复用现有解析器/DAO/AI 通道/隔离机制的事 | 新写一套统计引擎 |
| **无感优于炫技** | 减少用户操作 > 增加用户操作的新玩法 | 游戏化打卡 vs 自动导入 |
| **拒绝不可维护的依赖** | 不引入需持续对抗外部平台变化的功能 | 抓取电商平台订单 |
| **每版本有出口标准** | 版本必须能用可验证的指标收口，不用"差不多做完了"收口 | — |

## 3. 详细任务分解

### 3.1 v0.5「让它自己跑起来」

**目标**：把「定时任务底座 + 数据自动入库 + 主动通知」打通，让应用从"我打开才工作"变成"一直在替我干活"。
**不做什么**：本版本不碰 AI（除复用现有 DeepSeek 分类外）、不引入账本维度。

#### T-5.1 定时任务底座 ★最高优先

| 项 | 内容 |
| --- | --- |
| 层次 | 后端（service + DAO + schema 迁移） |
| 规模 | M |
| 依赖 | 无（其他任务依赖它） |
| 交付物 | `app/services/scheduler.py`、`app/db/dao/task_dao.py`、设置页「自动化」分区的数据接口；新增表 `scheduled_tasks` / `task_runs`（schema v4） |

**技术方案要点**

- **不引入 APScheduler**。理由：生产是单进程 uvicorn（`cmd/main` 无 `--workers`），进程内 asyncio 循环足够；当前 `requirements.txt` 只有 5 个包，保持依赖极简对离线安装（fnOS 首次启动要联网装依赖）有实际意义；引入调度框架的收益（cron 表达式解析）可用极简实现替代。
- 需要的四项行为，缺一不可：
  1. **错过补跑（catch-up）**：NAS 关机/应用停止期间错过的任务，启动后延迟 60s 补跑**一次**（合并，不逐次补）。
  2. **并发互斥**：同一任务不并发；`scheduled_tasks` 存 `running_at` 作为软锁，超时（如 30 分钟）自动解锁防死锁。
  3. **失败退避**：连续失败按 1/2/4 倍退避，连续 5 次失败自动停用并生成一条通知事件。
  4. **运行历史**：`task_runs` 记录起止时间、结果、错误摘要、影响条数，设置页可查最近 N 次。
- **已知边界（写进文档，不隐瞒）**：进程内调度仅在**单进程单实例**下成立。若未来改多 worker 或多实例部署，需要外部调度或任务锁升级。表结构预留 `locked_by` / `locked_until` 字段作为升级路径。

**验收标准**

- [ ] 手动改系统时间模拟"错过 3 次执行"，启动后 60s 内只补跑 1 次
- [ ] 同一任务并发触发时第二次直接跳过并记录
- [ ] 连续失败 5 次后任务自动停用且产生通知事件
- [ ] 任务执行历史可在设置页查看（含失败原因）
- [ ] 非管理员不可修改任务（复用 `require_admin`）

**测试**：`tests/services/test_scheduler.py`（时区、补跑合并、并发互斥、退避、停用）+ `scripts/verify_scheduler.py` 场景自检

#### T-5.2 邮箱账单自动抓取

| 项 | 内容 |
| --- | --- |
| 层次 | 后端（service + 配置 + 接口） |
| 规模 | L |
| 依赖 | T-5.1（靠调度周期触发）、现有解析器与去重 |
| 交付物 | `app/services/mail_fetch_service.py`、`app/utils/mail_attach.py`、`mail_config.json` 配置与设置页表单 |

**技术方案要点**

- 纯标准库 `imaplib` + `email` 实现 IMAP over SSL，避免新增依赖。
- **已处理集合**：以「邮箱账号 + 邮件 UID」维护已处理记录（新增表 `mail_seen`，schema v4），只处理未见过且白名单发件人的邮件，避免重复下载与重复导入。
- **附件处理**：账单邮件附件常为**带密码的压缩包，密码通常在邮件正文中**（此点在预研阶段需用真实邮件逐一验证，不同平台格式不一）。字符编码、正文 HTML 提取、密码正则都需容错。
- **绝不让失败影响主流程**：抓取异常只写日志 + 生成一条通知事件，不抛出到调度器之外。

**待预研（Spike，先于编码）**

| 待验证问题 | 影响 |
| --- | --- |
| 微信/支付宝/银行账单邮件的实际附件格式与加密方式 | 决定是否需要新增依赖（标准库 `zipfile` 不支持 AES 加密，如需则要 `pyzipper`） |
| QQ/163 邮箱需授权码、Gmail 需应用专用密码的配置引导 | 决定设置页引导文案与校验方式 |
| 邮件正文密码提取的稳定性 | 决定该功能的成败——提取不到密码就等于抓不到账单 |

**验收标准**

- [ ] 配置邮箱后可手动「立即抓取」，结果返回「新增 N 条 / 跳过 M 条 / 失败 K 条」
- [ ] 同一封邮件重复抓取不产生重复流水
- [ ] 抓取全程失败时应用其他功能完全不受影响
- [ ] 日志可追溯每次抓取的邮件 UID 与处理结果

**测试**：`tests/services/test_mail_fetch.py`（IMAP 全 mock）、附件解压与密码提取单元测试、`scripts/verify_mail_fetch.py`

### 3.2 v0.6「会说话的账本」

**目标**：让查询从"会筛会点"降到"会说话"，并让分类准确率随使用时间**自动上升**而非依赖继续加模型。
**不做什么**：不做语音、不做分享长图（归 Backlog）。

#### T-6.1 查询意图翻译层 ★优先做

| 项 | 内容 |
| --- | --- |
| 层次 | 后端 |
| 规模 | M |
| 依赖 | 无（T-6.2 与 v1.0 的 MCP 共用） |
| 交付物 | `app/services/nl_query.py`、`app/schemas/nl_query.py` |

**两段式设计（核心）**

1. **规则优先**：正则/关键词解析高频问法（时间范围 + 分类 + 商户 + 聚合维度），命中即用——零成本、零延迟、零幻觉。
2. **LLM 兜底**：未命中时交模型，用 **JSON Schema 强约束**输出结构化查询对象：
   `{time_range, categories[], merchants[], metric, group_by, order_by, limit}`

**安全红线（不可妥协）**

- 后端**只接受白名单字段与枚举值**，绝不把模型输出拼接为 SQL；
- 查询一律走既有 DAO 的只读方法，并**强制注入 `user_id` 过滤**（隔离不可绕过）；
- 结果集上限 + 查询超时；
- 非法/越权查询拒绝并记录日志。

**验收标准**

- [x] 20 条典型问法命中率 ≥ 90%，其中规则命中占比 ≥ 60%（2026-09-17 交付：
      `tests/services/test_nl_query.py` 20 问表驱动，意图断言全通过，规则命中 18/20 = 90%）
- [x] 越权用例（试图查询其他 user_id 数据）**全部被拒绝**（请求体 extra="forbid"
      → 422；模型输出非白名单字段忽略并记日志；DAO 层强制注入 user_id）

## 4. 横切技术约定（所有版本共同遵守）

### 4.1 Schema 迁移流程

1. 新表 / 新列一律在 `app/db/base.py` 注册迁移函数，`_MIGRATIONS[N] = _vN_xxx`，每个函数只负责 `vN → vN+1`；
2. 每个迁移独立事务并立即写版本戳（中断后可续迁）；
3. SQLite 迁移前自动 checkpoint 并备份 `bill.db.bak-v<N>`（已有机制，继续沿用）；
4. **缺少迁移实现时拒绝启动**——宁服务不可用，不静默损坏数据；
5. 每个版本在 `scripts/verify_migrations.py` 增加「全新安装 / 老库升级 / 模拟迁移 / 类型切换」四场景验证。

### 4.2 版本号四处同步（漏一处就会线上不一致）

`manifest` 的 `version` · `app/config.py` 的 `APP_VERSION` · `frontend/package.json` 的 `version` · `manifest` 的 `changelog`

### 4.3 测试与门禁

| 层级 | 要求 |
| --- | --- |
| 单元测试 | 每个新 service / DAO 必须有对应 `tests/<分层子目录>/test_*.py`（见 tests/README.md）；外部依赖（IMAP / HTTP / LLM）全部 mock，测试不联网 |
| 场景自检 | 复杂机制（调度、迁移、抓取、查询）配套 `scripts/verify_*.py`，输出通过率 |
| 打包门禁 | `scripts/build_fpk.sh` 打包前跑全量测试，失败即中止 |
| CI 门禁 | Gitee Go 构建前二次跑全量测试 |

**已知测试脆弱性（需留意，非回归）**：`tests/api/test_runtime_logs.py` 读仓库根 `app.log`，**跑构建的同时跑测试可能偶发失败**；`pytest` 退出码可能为 1 但用例全绿（safe-delete 拦截临时目录清理），以输出点数为准。

### 4.4 前端约定（沿用现有设计系统）

- 组件内**只引用 `--color-*` 语义层**，禁止硬编码色值；
- 金额一律 `--font-numeric` + `tabular-nums`，统一走 `fmtSignedMoney()`；收支配色走 `amountClass()`；
- 图表取色统一走 `chartTheme.js`，不在组件内硬编码 ECharts 颜色；
- 图标统一用 `components/AppIcon.vue` 的 inline SVG，不使用 emoji；
- 表格与卡片双形态（桌面 `.bill-table-desktop` / 移动 `.bill-cards-mobile`），由 CSS 断点互斥切换。

### 4.5 数据隔离与安全

- `user_id` 过滤**必须在 DAO 层强制注入**，禁止在 service 层拼装筛选条件（v0.7 引入账本维度后同理）；
- 新增写操作接口一律先过 `require_admin`（全局影响类）或身份校验；
- 独立部署场景的 `X-Trim-Userid` 可伪造问题已在 README 声明——新增接口不得放大该风险面。

## 6. 风险登记册

| 风险 | 影响 | 概率 | 缓解措施 |
| --- | --- | --- | --- |
| 飞牛无官方应用推送通道 | 中（通知形态降级） | 高 | v0.5 默认走应用内通知中心 + 用户自配 Webhook；官方通道结论写入文档，不假设其存在 |
| 账单邮件为 AES 加密 ZIP，标准库解不开 | 中（需新增依赖） | 中 | Spike 阶段先取真实邮件验证；必要时引入 `pyzipper`，并评估离线安装可行性（项目一贯保持极简依赖，破例需你确认） |
| 邮件正文密码提取失败率高 | 高（功能失效） | 中 | 保留手动上传作为唯一可靠入口；抓取失败明确提示"需要手动导出" |
| 进程内调度在多实例下重复执行 | 中（重复导入/重复推送） | 低 | 表结构预留 `locked_by`/`locked_until`；文档明确仅支持单进程；导入去重本身是最后防线 |
| v0.7 账本维度为破坏性变更，SQLite 需重建表 | 高（数据丢失风险） | 中 | 迁移前自动备份已有；先在样例库演练三方言；保留回退路径；单独批次专注处理 |
| LLM 幻觉产生错误财务结论 | 高（信任受损） | 中 | 所有数字由后端计算，模型只做解释（T-6.5）；回答必须展示查询口径；禁止模型直接输出金额 |
| AI 调用费用失控 | 低 | 中 | 规则优先（T-6.3）压低调用量 + 单日调用上限 + 费用可估算 |
| NAS 长期关机后集中补跑造成 IO 尖峰 | 低 | 中 | 补跑合并为单次 + 启动后延迟 60s + 任务串行化 |
| 敏感配置明文存储（API Key / 邮箱授权码 / DB 口令） | 中 | 中 | v0.5 沿用现有掩码策略并写入文档；v1.0 的 T-1.7 统一加密迁移 |
| 新增表 / 列破坏三方言语义一致性 | 中 | 中 | 迁移函数必须三方言语义对齐；MySQL/PG 走 SQL 生成断言测试 |
