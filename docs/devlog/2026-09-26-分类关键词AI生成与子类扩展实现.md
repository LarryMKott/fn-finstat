## 关键实现决策

1. **播种两条触发路径共用一个幂等实现**：老库由 v16 迁移调用（categories 已存在）；
   全新库不经过任何迁移，由 `init_db` 在预置默认分类后兜底调用——与
   `ensure_default_ledger` 同模式。
2. **排序放 Python 侧**（`list_enabled_with_category` 长词降序）：三方言字符长度
   函数语义不一（MySQL 的 `LENGTH` 按字节，中文会错排），表量级为百行、每批导入
   只查一次，内存排序行为绝对一致。
3. **关键词表是匹配唯一数据源**（D-3 推荐口径）：播种后内置词同样界面可见、可停用、
   可删除；`RULES` 保留仅为播种新库与表故障兜底，改内置词对已播种库无效（去界面改）。
4. **层级不参与自动归类**（D-1）：`bills.category` 仍是流水实际所在分类；是否迁入
   子类由用户在 T-B apply 时显式勾选 `migrate_bills`（全账号、单事务、长词优先、
   未命中保留）——预算/报表零破坏。
5. **CAP-3 的提名裁决放在解析层之后**：`_parse_result` 只收集候选（含斜杠拆解），
   `_promote_new_categories` 统一计票、配额、建分类、写审计——不信任模型的结构承诺；
   `auto_subcategory_enabled=False` 时斜杠名按顶层处理（与设置页文案一致）。
6. **关键词回填（`auto_keyword_enabled`）是旁路能力**：每次归类请求至多一次额外调用、
   最多 5 个分类 × 10 词，失败只记日志；入参与 prompt 仅商户名 + 分类名（无金额/日期/
   备注），测试断言把关。
7. **备份层级按名重映射**（`parent_name` / `category_name` 导出即换名）：恢复时先插
   全部分类再按名回填 `parent_id`，合并模式本地同名分类保持现状（与 insert_ignore
   语义一致）；v6 老备份 replace 后自动重播种，避免「关键词表被清空 → 全部漏到其他」。

## 顺手修复的存量缺陷

- `_clean_row` 对 v2 及更早备份的**纯字符串分类数组**存在死代码：入口
  `isinstance(raw, dict)` 先行拒绝，导致注释承诺的「两种形态都接受」实际返回 0 行
  （replace 恢复会丢光分类）。已在入口处把字符串升格为 `{"name": raw}`，新增测试锁定。

## 已知边界

- 改 `category_matcher.RULES` 只影响**未播种库**的播种结果；已播种库的内置词请在
  界面维护（模块 docstring 已注明）。
- 关键词匹配为子串口径，跨分类同词的歧义由「长词优先、同长按 id 先到先得」消解；
  冲突词在 AI 候选中以橙色标记交人工裁决，但不强制阻止入库。
- `response_format: json_object` 的端点能力差异与多供应商实现记录同口径（个别兼容
  端点可能 4xx，报错带供应商名）。
