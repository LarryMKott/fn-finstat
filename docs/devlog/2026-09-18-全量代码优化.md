## 1. 背景与范围

对 v0.7.0 代码做一轮跨层优化，目标三类：**魔法值收敛**（收支类型/账户/标签/角色等
散落字面量单一来源化）、**配置整理**（JSON 配置读写样板去重、连接池与日志轮转参数
进 config）、**重复逻辑与死代码清理**（月份平移三份实现、JSON 围栏剥离三份实现、
转发别名等），顺带修两处正确性隐患、做三处小性能优化。不改任何接口契约与行为语义
（除下述两处明确的缺陷修复）。

## 2. 正确性修复

1. **微信 xlsx 金额列脏数据 500 隐患**（`app/parsers/wechat_parser.py`）：原实现
   `normalize_amount(金额文本)` 在文本非数字时原样带回字符串，`amount <= 0` 直接
   `TypeError` → 未处理异常 → 500，外层 `except ValueError` 是死分支。新增
   `app/utils/amount.py::parse_amount`（严格解析，失败返回 `None`），微信/支付宝
   两个解析器统一走「解析失败跳过该行」，`csv_common.clean_amount` 同步收敛到它。
   行为变化仅为「崩溃 → 跳行」，负数/零金额跳过的既有语义保持（测试已钉住）。
2. **分类 DAO 唯一约束误判**（`app/db/dao/category_dao.py::create`）：原裸
   `except IntegrityError → return None` 会把 NOT NULL 等其他完整性故障静默当
   「分类已存在」。现仅 `is_unique_violation` 命中才返回 None，其余原样抛出，与
   同模块 `rename`、notify/task DAO 的风格一致。

另修正两处误导性注释：`AboutInfo.fnos_theme` 与 `get_about_info` 的说明改为
「原样透传原始主题值（"10"/"20"/"light"/"dark"），归一化在前端
`fnos.js::normalizeTheme`」——与 `tests/core/test_theme.py` 的透传契约一致；
后端 `normalize_theme` 保留（`tests/verify_theme_parity.py` 前后端一致性校验依赖）。

## 6. API 层查询参数收敛（新文件 `app/api/params.py`）

`StartQuery / EndQuery / AccountQuery / TxTypeQuery / LedgerIdQuery` 五个
Annotated 别名（约束在 Query、默认值在签名处 `= None`——FastAPI 不允许两处同时给
默认值），stat 六端点、bill 筛选依赖、asset / budget 的账本与区间参数全部改用，

## 7. 查询性能

- `BillDAO.count_in_range`：家庭月度汇总的成员流水计数不再借道
  `list_bills(page_size=1)`（COUNT 之外还多取一页行数据），N 成员 × 1 次纯 COUNT；
- `BillDAO.update_categories`：AI 归类回写从逐条 UPDATE（单轮最多
  `CLASSIFY_LIMIT=1000` 次驱动往返）改为按目标分类分组 + IN 分片（900）批量
  UPDATE，语句数降为 O(分类数 × 分片数)，返回的实际更新条数口径不变；
- `StatDAO.nl_aggregate`：汇总与分组两次查询合并进同一事务（同一逻辑读不再拆成
  两次提交/会话借用）；
- `NotifyDAO.create`：保留窗口清理 DELETE 并入写入同事务，省一次会话借用
  （唯一约束撞车提前返回时跳过本次清理，下次成功写入照常清理，语义不变）。

## 8. 未采纳项（记录理由）

- 备份 `insert_many` 的 COUNT 差值改 `max(id)` 差值：MySQL 下 INSERT IGNORE 仍会
  烧掉自增号，max(id) 差值在多方言下不正确，维持现状；
- 预算/资产写入的「服务层 resolve_write + DAO 内 resolve_ledger_id」双重账本校验：
  多一次索引查询是防御性冗余，DAO 兜底保护直连 DAO 的调用方，保留；
- `X-Trim-*` 网关信任、204 无包装响应等存量契约不动（见《重构说明》§2）。

## 10. 后续：配置模块按「静态 / 运行期」一分为二

首轮优化后 config.py 仍是一个 370 行平铺文件，路径、服务器安全、领域默认值、
数据库解析与三套 JSON 配置混排，DB 相关定义散落三处，不利于人工维护。本轮按
配置的两种形态拆分（与 §4 的配置整理一脉相承）：

- `app/config.py`（约 320 行）：**启动时定型、运行期只读**的静态配置。模块
  docstring 增加编号目录（§1 路径 → §9 数据库连接），按维护动线重排：环境变量
  辅助 `_env` 前置；PORT 并入 HTTP 服务节；NAS 导入限制并入上传限制节；连接池
  参数随数据库节；JSON 读写基建（更名为公开的 `read_json_config` /
  `write_json_config`，因跨模块使用）紧邻其唯一在本模块的使用方 db_config.json。
  每节保留原有全部注释。
- `app/file_settings.py`（新文件，约 190 行）：**运行期界面读写、落盘 JSON、
  写入即生效**的配置，AI / NAS 目录 / 通知三套各按统一「四件套」模式排列
  （文件路径 → 模型 → load → save），docstring 写明新增一套配置的照抄模式与
  两种配置形态的分工。依赖方向单向：file_settings → config。

- 同步更新：8 个 app 模块与 4 个测试文件的导入目标、`tests/conftest.py`
  autouse 隔离夹具的 patch 目标（`app.config.*_CONFIG_FILE` →
  `app.file_settings.*_CONFIG_FILE`，patch 点 = 名字使用点）；README 项目
  结构树补 file_settings.py 一行。
- 不变量：`app.config` 的既有公开符号集合除三个 `_json` 私有助手更名外不变；
  db_config.json 四级优先级与其 10 个测试一字未动；配置文件格式与磁盘布局
  完全不变（老用户升级无感）。

## 11. 收尾两笔（2026-09-19 提交）

- `perf(stat)`：`detect_region` / `detect_city` 加 `lru_cache(maxsize=8192)`。
  消费地图对账单逐行（上限 2 万行）做地域推断，而「商户名+备注」在真实账单里
  高度重复；两个函数是纯文本映射（无 I/O、无全局状态、返回不可变字符串），
  缓存无别名风险，重复商户不再重复正则扫描。
- `refactor(core)`：`REQUEST_ID_SCOPE_KEY` 与 `SECURITY_HEADERS` 从
  middleware 下沉到 context——handlers（500 兜底响应）此前反向依赖 middleware，
  违反 core 内部分层方向；两个常量与 `request_id_var` 同居最底层 context 后，
  中间件与异常处理器各自向下单向引用。无外部调用方，未留兼容别名。

提交切分为 8 个（fix×2 / perf×2 / refactor×4），每个中间快照经独立 worktree
跑全量测试验证可回归（698 passed）。

## 12. 部署后配置防泄漏加固（2026-09-19）

### 12.1 出口面审计结论（大部分已有防线，无需改动）

- AI API Key：`GET /api/ai/config` 只回掩码（`has_api_key` + `****`+尾 4 位），
  原始 Key 不出后端；保存/测试连接仅管理员，测试接口有 SSRF 防线（不跟随重定向
  + base_url scheme 校验，防止任意账号把共享 Key 发往自己控制的服务器）。
- 数据库信息：`GET /api/settings/database` 密码只回 `has_password` 布尔；
  host/port/user/sqlite_path 仅管理员可见。
- 备份导出仅业务数据，不含任何配置文件；打包为白名单复制（`build_fpk.sh` §126-134），
  `.env.dev` / `.local_data` / `app.log` 不进 FPK。
- 日志：无 api_key / password / webhook URL 的日志输出；生命周期脚本只回显
  db_type；前端无敏感信息落 localStorage；wizard 密码控件为 password 类型。

### 12.2 修复项（磁盘权限 + 错误信息脱敏）

飞牛 OS 是多用户系统，配置文件**明文**存数据库密码 / AI Key / Webhook 推送 Key
（Bark/ntfy 的 Key 在 URL 里），此前按默认 umask 落盘 644，同机其他本地用户可读：

1. `config.harden_perms(path, mode)`（新公开助手，尽力而为、失败静默）：
   - `DATA_DIR` / `TMP_DIR` 收敛 0700（已存在的旧目录同样收敛）；
   - `_atomic_write_text` 落盘前对临时文件 chmod 0600（rename 保留 inode 权限）
     —— 四套配置文件都从这里写盘，是唯一收口点；
   - `DB_CONFIG_FILE` 与 file_settings 三套配置在模块导入时对存量旧文件收敛
     0600（覆盖升级场景，不必等下次保存）。
2. SQLite 数据文件（`bill.db` / `-wal` / `-shm`，全部账单明文）在连接事件里
   顺手收敛 0600——WAL/SHM 由 SQLite 按需重建、权限跟随 umask，故每次连接
   重复收敛。
3. 运行日志（含迁移目标库地址与账号操作记录）：`_PrivateRotatingFileHandler`
   在每次打开文件（含轮转重建）时收紧 0600，堵住滚动后权限退回 644 的口子。
4. `send_webhook` 通用异常分支的文案会内嵌完整 URL（含推送 Key），而失败原因
   会落库、进运行日志并展示在通知中心——回传前把配置的 URL 抹为 `<webhook>`。

### 12.3 已知残留（记录不改）

- 向导注入的环境变量（`wizard_db_password`）与 `DEEPSEEK_API_KEY` 对同 UID/
  root 进程经 `/proc/<pid>/environ` 可见——fnOS 向导机制固有，属平台信任边界内。
- 通知设置 API 向管理员回传完整 `webhook_url`（编辑表单需要）；按渠道做掩码
  复杂度高收益低，管理员可见性属预期行为。
- 测试：权限断言仅 POSIX 有意义，Windows 开发机跳过（3 skipped）、CI Linux
  真实执行；全量 699 passed。

验证：全量 698 例通过；black / ruff（F, E9）干净。

## 13. 安全审计修复（2026-09-19，承接独立安全审计会话）

审计结论：1 个中危真缺陷 + 6 条加固建议。本轮修复缺陷并落地其中 3 条，
其余 3 条为文档化残留（见 §12.3 与下文）。

### 13.1 🔴 中危：重定向禁用无效 → API Key 泄漏 / SSRF 防线失效（已修复）

`_NoRedirect` 三处（ai_service / notify_service / update_service）只继承
`HTTPRedirectHandler` 未重写 `redirect_request`（notify 甚至只是直接实例化
基类），urllib 仍按默认策略跟随 3xx——AI 通道的
`Authorization: Bearer <Key>` 会被原样发往跳转目标（审计实测泄漏），
Webhook 可借跳转把携带通知内容的出站请求引向内网。三处统一补上
`redirect_request(...) -> None`（3xx 以 HTTPError 抛出、由各自既有错误分支
转成可读失败），`tests/services/test_no_redirect.py` 起真实本地 302 服务器
回归三通道：302 被拒跟（HTTPError 302）而非被跟进（连接拒绝）。

### 13.2 加固落地

- **update 强制刷新节流**（`REFRESH_MIN_INTERVAL = 60s`）：`refresh` 参数
  对所有登录账号开放且绕过 CACHE_TTL，原实现可被高频点击拿去无限直连
  Gitee 匿名接口；现间隔内的重复刷新直接回缓存结果。`clear_cache()` 同步
  重置节流时间戳（测试夹具逐用例清理，既有用例零改动）。
- **AI 配置对非管理员脱敏**：`GET /api/ai/config` 的 `base_url` 与
  `api_key_hint` 仅管理员可见（普通账号共享 AI 能力但无需知晓配置内容，
  `has_api_key`/`enabled`/`model` 保持可见）；口径与 get_database_info 一致
  （无网关身份的本地/独立部署视为唯一用户）。
- **Unix socket 权限**（`cmd/main`）：就绪探活通过后 `chmod 660 app.sock`——
  网关以应用用户或 root 连接（旧 755 下「其他用户」本就无写权限连不上），
  显式化并收掉读/执行位；chmod 失败不阻塞启动。

### 13.3 文档化残留（有意不改代码）

- **X-Trim-\* 头无条件信任**：仅独立部署显式 `HOST=0.0.0.0` 时可被局域网
  伪造；启动日志已有醒目 WARNING、config 注释与 README 均有说明。引入
  共享密钥会破坏浏览器/PWA 场景（浏览器无法注入自定义头），平台网关模式
  不受此问题影响——维持「文档 + 告警」策略。
- **NAS 导入无逐用户 ACL**：导入目录为管理员配置的共享账单目录，导入结果
  归各账号自有数据、不跨账号；接入 fnOS ACL 属平台能力，先文档标注。
- **依赖未锁哈希**：requirements 只锁下限（当前无已知 CVE）；带哈希锁文件
  会显著改变 NAS 在线安装流程，单独议题处理。

验证：全量 707 passed + 3 skipped（POSIX 权限用例 Windows 跳过）；black /
ruff（F, E9）干净。
