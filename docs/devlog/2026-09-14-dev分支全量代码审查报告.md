## 2. 问题清单

### 2.1 高（H）

#### H-1 网关身份头被无条件信任，独立部署下可提权

- **位置**：`app/api/deps.py:17-31`（`get_gateway_user` 直接读 `X-Trim-Userid` / `X-Trim-Username` / `X-Trim-Isadmin`，无来源或签名校验）、`app/api/deps.py:34-42`（`require_admin` 仅当 `user_id` 非空且 `is_admin != true` 才拒绝）、`app/config.py:83`（`HOST` 默认 `"0.0.0.0"`）
- **前提（已核实）**：飞牛生产启动路径是 `cmd/main:91` 的 `uvicorn app.main:app --uds "$SOCKET_FILE"` —— **只绑 Unix Domain Socket，不监听任何 TCP 端口**。因此**在飞牛网关模式下，本项无法从网络直接利用**。
- **风险场景**：独立部署或本地直跑 uvicorn 时，若绑定 `0.0.0.0` 且所在网络不可信，任何人只要构造 `X-Trim-Userid: <victim>` + `X-Trim-Isadmin: true` 两个头，即可完整获得该身份（含管理员）——可导出全量备份、恢复覆盖数据、改数据库连接、读写 AI Key、下载运行日志。
- **建议**：把「信任 `X-Trim-*`」限定为网关模式（`IS_FNOS` 为真，即 `TRIM_PKGVAR` 存在）；独立部署时要么绑 `127.0.0.1`，要么由启动脚本生成一次性共享密钥并要求请求携带。**不要**把「网关会剥离伪造头」当作唯一防线。

### 2.2 中（M）

#### M-1 全局分类的写接口没有任何身份依赖

- **位置**：`app/api/category.py:36`（POST）、`:45`（PUT）、`:54`（DELETE）
- **证据**：三个写接口签名分别为 `create_category(payload)` / `update_category(category_id, payload)` / `delete_category(category_id)`，**均无 `Depends(get_gateway_user)` 或 `require_admin`**；而同一文件 `:29` 的 `get_category` 是有用户依赖的。模块注释明确「分类为全局共享」，`category_service.update_category` 还会**同步改写所有用户**流水的分类名。
- **影响**：飞牛多账号模式下，任意登录用户（甚至不带身份头的请求）都可新增、重命名、删除全局分类，直接污染所有账号的归类与统计口径。
- **建议**：写操作补 `Depends(get_gateway_user)`；若产品上认为分类是全局配置，则进一步收为 `Depends(require_admin)`。

#### M-2 数据库「迁移并切换」与「备份恢复」使用两把不同的锁

- **位置**：`app/services/settings_service.py:204`（`with _MIGRATE_LOCK:`，锁定义于 `:55`）与 `app/services/backup_service.py:153`（`with RESTORE_LOCK, get_db() as session:`，锁定义于 `:31`）
- **证据**：两条路径各自持独立互斥量，互不感知。迁移流程在锁内执行 `copy_database` → `write_db_config_file` → `activate_engine`（切换全局引擎）→ `write_db_type_marker`；而恢复流程内部 `get_db()` 取自**切换前**的引擎。
- **影响**：管理员并发触发「迁移并切换」与「恢复备份」时，恢复的数据可能提交到已被弃用的旧库，活动库看不到结果 —— 表现为「恢复了但数据没变」。两操作虽都需管理员且低频，但窗口真实存在。
- **附带**：`app/services/import_service.py:81` 会用 `RESTORE_LOCK` 挡住导入与恢复的冲突，而**迁移没有被导入路径挡住**，存在同类缺口。
- **建议**：把迁移纳入 `RESTORE_LOCK`（或抽一把统一的「全局数据操作锁」），使 DDL 切换与数据导入、恢复两两互斥。

#### M-3 NAS 目录浏览把服务器绝对路径回传给前端

- **位置**：`app/services/nas_service.py:148`（`NasDirectory(root=str(root))`）与 `app/schemas/nas.py:34`（`root: str` 未脱敏）
- **影响**：任意登录用户调用目录浏览接口即可获知服务器绝对路径（如 `/vol1/1000/bills`），为后续攻击提供信息。属于信息泄露而非越权（读写仍受 `_resolve_in_root` 边界约束）。
- **建议**：响应中不回传绝对路径，只返回条目名与相对层级；确需展示时按 `scheduler.redact_paths` 同口径脱敏。

#### M-4 Release 版本号与 `manifest` 应用版本脱钩

- **位置**：`.workflow/build-fpk.yml:65-66`（`releaseName: fn-finstat v${GITEE_PIPELINE_BUILD_NUMBER}`、`tagName: v${GITEE_PIPELINE_BUILD_NUMBER}`）与 `manifest` 的 `version`（0.6.0）
- **证据**：流水线触发器接受语义版本 Tag（`:25` 的 `^v\d+\.\d+(\.\d+)?(\.\d+)?$`），但发布插件创建的却是构建号 Tag（如 `v5`）。
- **影响**：用户下载到的 fpk 无法从发行版页面判断对应哪个应用版本；推 `v0.6.0` 却产出 `v5` 的发行版，版本语义断裂。注释称此举是为「免去与 manifest 手动同步」，属有意取舍，但代价是可追溯性。
- **建议**：`tagName`/`releaseName` 改用 manifest 版本（构建号放进标题后缀或 description），或至少在 `description` 中写明应用版本号。

#### M-5 前端产物引用门禁只做存在性检查、只扫入口 HTML

- **位置**：`scripts/check_assets_refs.py:29`（只收集含 `assets/` 的引用）、`:52`（只判断 `is_file()`）；`scripts/fpk_selfcheck.py:79` 同逻辑
- **影响**：`icons/*`、动态 import 产生的 chunk、`manifest.webmanifest` 缺失都不会被拦下；引用带前导 `/` 时会被绝对拼接误判为缺失（当前源码用 `./` 相对路径，未触发）。
- **建议**：校验范围扩到全部 `src`/`href` 引用并纳入 `icons/`；对外链与内联 URL 做排除；补一层内容校验（如非空 + 体积下限）。

#### M-6 CI 前端构建在 `npm ci` 失败时静默回退 `npm install`

- **位置**：`scripts/ci_build.sh:63`（`npm ci --no-fund --no-audit || npm install --no-fund --no-audit`）
- **影响**：锁文件不一致时直接绕开 lockfile 重建依赖树，构建出的前端可能与仓库提交的锁文件长期漂移，且失败被 `||` 吞掉，坏产物一路带到 fpk。
- **建议**：改为 `npm ci` 失败即 `exit 1`，把锁文件不一致暴露为构建错误（依赖升级时先本地更新锁文件）。

## 5. 总体评价

**架构与工程成熟度均高于同类个人项目。** 分层清晰（router → service → DAO），响应体与异常体系统一；并发控制不依赖调用方自觉，而是把持有者凭证写进 SQL 条件，由数据库层强制，这是正确且少见的做法；数据按 `user_id` 严格隔离且经抽查无遗漏；工程链路有双重门禁（关键字 + 产物存在 + `fpk_selfcheck`）兜住两起历史事故；测试 340 项全绿、前端 lint 零告警。

**需要动手的是三块：**

1. **权限边界**（H-1 + M-1）—— 唯一可能被外部利用的一类问题。M-1 是几行代码就能修的真实越权，建议优先；H-1 取决于你是否打算保留「独立部署 + 绑 0.0.0.0」这个组合，若保留则必须收口。
2. **全局状态切换的互斥**（M-2）—— 迁移/恢复/导入三者之间的锁不闭合，属于「低频但后果重」的缺陷，修复成本很低（统一锁即可）。
3. **可追溯性与构建确定性**（M-4 + M-5 + M-6）—— 不修不会立刻出事，但会让「用户拿到的是哪个版本、包是否完整」长期不可验证。

**建议修复顺序**：M-1 → M-2 → M-3 → H-1（定策略）→ M-6 → M-4 → M-5 → L 级择机。

## 6. 明确未发现问题的方向

为避免遗漏被误读为「没查」，以下方向经专项检查**未发现**问题：

- **路径穿越**：`_resolve_in_root` 已 resolve + 祖先校验，覆盖 `..` 与符号链接；`_serve_icon` 的 path 参数天然不含 `/`。
- **SQL 注入**：全 ORM 参数化，无字符串拼接 SQL。
- **资源泄漏**：数据库会话、文件句柄均通过 `with` 释放，异常路径无遗漏。
- **越权读取（IDOR）**：`bill` / `asset` / `budget` / `stat` / `ai` 全部经 `user_id` 过滤。
- **上传限制**：大小（10MB）、扩展名、记录数（50000）均有上限。
- **CORS / 中间件**：未开启跨源，未发现过宽配置。
- **AI Key 脱敏**：仅以掩码形式返回，写操作限管理员。
- **manifest 历史坑**：`disable_authorization_path` 为 `false`，且已有测试锁死。
- **卸载数据保护**：`uninstall_callback` 仅在用户明确选择删除时才清理，并保护 `TRIM_PKGVAR`。
- **向导字段一致性**：`wizard_db_*` / `wizard_purge_data` 等字段名在 wizard、`config.py`、回调脚本三处一致。
- **版本号同步**：`manifest` / `app/config.py` / `frontend/package.json` 均为 0.6.0。
- **前端 XSS**：唯一的 `v-html`（`AIReportModal.vue:324`）内容先经 `escapeHtml` 转义。
- **前端定时器**：无组件内累积定时器，仅 `fnos.js` 一处模块级轮询（已评估，无泄漏）。

### 修复过程中的一条硬教训

**`get_gateway_user` 不是鉴权，只是身份解析。** 它永远不抛异常 —— 无身份头时按「单机唯一用户」放行是设计如此。
任何需要真正拦截的接口，守卫必须落在 `require_admin`（或在 `get_gateway_user` 之上再包一层显式校验）。
第一版修复就栽在这里：加了依赖、测试也绿了，但**一个请求都没拦住**。加完守卫后务必用「有 user_id 但非管理员」的账号头发一次请求验证是否真的 403。
