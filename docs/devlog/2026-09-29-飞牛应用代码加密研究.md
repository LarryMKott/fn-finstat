## 1. 背景与目标

当前 fpk 的组装流程（`scripts/build_fpk.sh`）把 **150 个 `.py` 源文件原样打进 app.tgz**，
而 fpk 通过 Gitee Release（`fn-finstat-latest.fpk`）与应用中心**公开分发**。任何人不需安装应用，
下载 fpk 解包（fpk 本质是 tgz 壳）即可阅读全部后端业务源码：

- AI 提示词工程与上下文裁剪策略（`app/services/ai_service.py`，52 KB，全项目最大单文件）；
- 财务统计口径与算法（预测、健康评分、订阅侦探、What-if 等差异化功能全在 services 层）；
- 安全实现细节（Token 哈希、权限中间件、加密存储的密钥派生），虽然安全设计不依赖保密，
  但源码可读会降低攻击者的成本。

**目标**：把「下载 fpk → 解包 → 直接读源码」的门槛提高到需要付出实质逆向成本。

**非目标（明确不做）**：

- **不防设备 root 用户**。应用以明文形式运行在用户自己的 NAS 上，root 可以 dump 进程内存、
  挂 hook，任何分发形态都拦不住。代码保护提高的是**分发链路上的门槛**，不是安全边界；
- 不改变「数据不出本机」的隐私模型，不新增任何运行时网络依赖。

## 2. 威胁模型与保护等级

| 等级 | 能力画像 | 对应方案 |
| --- | --- | --- |
| L0（现状） | 解包 fpk 直接读 `.py` | — |
| L1 | 会解包，但只会找 `.py` 文件读 | 无源 `.pyc` 分发 |
| L2 | 会用 uncompyle6 等现成工具一键反编译 | PyArmor / Cython（3.12 下传统反编译器已失效） |
| L3 | 会读字节码 / IDA 级逆向 native 代码 | 只能做到抬高成本，无法根除 |

本项目要防的主要是 L1→L2 的「同行直接拿走逻辑/换皮重打包」，L3 不设防（成本收益不成比例）。

## 3. 部署形态约束（决定方案可行性的硬事实）

以下事实来自仓库内 `cmd/*`、`manifest` 与飞牛官方第三方应用文档（LarryMKott/fnnas-docs 镜像）：

1. **设备端 Python 是系统应用 `python312`**（manifest `install_dep_apps=python312`），
   路径 `/var/apps/python312/target/bin`。**应用无法自带解释器**——这直接排除
   Nuitka standalone / PyInstaller onefile 这类「打包自带运行时」的形态；
2. **依赖在设备上现场安装**：`install_callback` 用 `python3 -m venv` 建 venv 后
   `pip install -r requirements.txt`。所以**加密产物不能依赖 pip 包形态**（除非发私源），
   必须直接放进 app 目录随 fpk 分发；
3. **`TRIM_APPDEST` 安装后只读**（`cmd/install_callback` 注释明示，venv 因此建在
   `TRIM_PKGVAR`）→ 不存在「安装时现场编译/解密落地」的空间，产物必须是**最终形态**；
4. **入口固定**：`cmd/main` 用 `nohup $PYTHON_BIN -m uvicorn app.main:app --uds ...` 启动。
   加密方案必须保持 `app` 包可被普通 import 链路加载（uvicorn 无任何特殊 loader）；
5. **架构问题**：manifest `platform=all`，官方文档明确 all 的语义是「**仅当应用包不包含
   特定架构二进制时使用**」；fnOS 以 x86_64 为主，已有 ARM（RK3588）版本，系统架构可经
   `TRIM_SYS_ARCH` 获取。**任何 .so 形态的方案（Cython / PyArmor runtime）都要面对双架构
   构建与分发**，要么双包（改 platform），要么包内双份 + 启动时按架构选择；
6. **分发链路公开**：fpk 从 Release 直接下载 → 保护的起点是「已拿到 fpk」，而不是
   「已拿到设备文件」；

7. **CI 双渠道**（GitHub Actions + Gitee Go，`scripts/ci_build.sh`）产物要求一致，
   加密步骤必须可在这两类 runner 上自动化。

## 4. 候选方案对比

### A. 无源 `.pyc` 分发（字节码形态）★ 推荐第一期

**原理**：构建期用 **CPython 3.12** 把 `app/**/*.py` 编译成 `.pyc`，按原路径平铺
（`app/services/ai_service.pyc`），包内不再有任何 `.py`。CPython 的
`SourcelessFileLoader` 对「同路径 .pyc、无源码」是官方支持的导入形态，uvicorn /
FastAPI / SQLAlchemy 全部无感。

**本项目 PoC 已验证可行**（2026-09-29，见 §5）：

- 150 个模块全部编译，包内 0 个 `.py` 残留；
- `uvicorn app.main:app` 完整启动：`GET / → 200`（前端页面）、`/docs → 200`、
  业务接口走通路由 + pydantic 校验 + 中间件链；
- 全量测试套件在无源包上：**1107 条收集，1072 条通过**；35 条失败全部定性——
  12 条读 `manifest`/`wizard`/`cmd` 等打包文件（PoC 暂存目录没拷这些文件，环境性缺失），
  23 条是 `tests/security/` 里用 `inspect.getsource()`/`read_text()` **静态扫描源码**的
  用例（无源形态下按设计无法工作；CI 门禁本来就在源码树上跑，不受影响）。

**保护强度（L1）**：

- 注释与源码结构消失；字符串常量、docstring、函数名仍可读
  （`strings`/`dis` 即可提取，AI 提示词会暴露——提示词若敏感需另行策略，见 §6 决策点）；
- Python 3.12 字节码的**一键反编译器已断代**：uncompyle6/decompyle3 只支持到 3.8，
  3.12 目前只有 ML 在线工具 pylingual（有大文件限制、逐文件手工操作）与 pycdc 的
  部分输出，批量逆向成本显著。

**成本与风险**：

- 构建期改动小：新增 `scripts/compile_app_pyc.py`（~60 行），`build_fpk.sh` 暂存段把
  `cp app/*.py` 系列换成编译输出；`scripts/fpk_selfcheck.py` 的期望清单从 `.py` 改认
  `.pyc`（清单动态推导逻辑不变）；`build_fpk.bat` 同步；
- **编译解释器版本必须与设备一致（3.12）**：PoC 实测 3.13 编译的 pyc 在 3.12 下
  `ImportError: bad magic number`。CI 需固定 CPython 3.12（actions/setup-python@v5
  指定 3.12 即可；Gitee Go 需确认 runner 的 Python 版本可控）；
- 字节码随 Python 小版本绑定：设备 python312 升级到 3.13 的那天，老 fpk 的 pyc 全部失效
  → 属「新版本需要重新打包」的正常维护范畴，但要在 os_min_version/发布说明里留意；
- 运行时零新依赖、**字节码与 CPU 架构无关**，`platform=all` 语义保持合法。

### B. PyArmor（商业混淆）

**原理**：字节码加密 + 私有运行时（`pyarmor_runtime` 包含平台相关 .so），Pro 版有
RFT（标识符重命名）与 BCC（函数转 C 编译为机器码）。

**结论：不推荐作为首选**：

- **免费试用版对本项目直接不可用**：单代码对象 32 KB 上限，而 `ai_service.py`（52 KB）、
  `backup_service.py`（36 KB）等超限；且试用版混淆产物「非私有」（密钥公开，任何人可解）；
- 正式授权需付费（Basic 历史价 ~$38 / Pro ~$78，以官网现价为准），Pro 才有实质强度的
  RFT/BCC；
- `pyarmor_runtime` 的 .so 是**平台相关二进制** → 触发 §3.5 的双架构问题；
- 公开社区已有针对 PyArmor 的静态脱壳项目，Basic 档（纯字节码加密、无 RFT）的实际强度
  相对其成本与侵入性不占优。

若未来选择它：仅授权一台设备做混淆（license 绑定机器）、构建机需注册、CI 需离线许可
（`pyarmor-registry`），工程复杂度都高于方案 A/C。

### C. Cython 编译 `.so`（AOT 编译）★ 推荐第二期（按需）

**原理**：`*.py → Cython → C → gcc → .so`，业务逻辑变成机器码，字节码层面不存在了。

**保护强度（L2+，纯 Python 可得的最强形态）**：反编译回到二进制逆向问题。

**关键约束与做法**：

- **双架构构建**：目标 Debian 12（glibc 2.36）的 linux-x86_64 与 linux-aarch64。
  CI 上两个方案：GitHub Actions 原生 arm64 runner（公共仓库已免费提供）分别构建；
  或 ubuntu + cargo/`cross` 式 QEMU 交叉编译。产物包内双份
  （`app/services/_native/x86_64/*.so` + `aarch64/*.so`），入口 shim 按
  `platform.machine()`/`TRIM_SYS_ARCH` 挂路径——`platform=all` 的官方语义问题
  （包内含架构二进制）需要真机验证应用中心是否放行，不行就退化为双渠道双包；
- **模块白名单**（业界共识 + 本项目结构适配）：
  - **编**：`app/services/*`、`app/parsers/*`、`app/utils/*`（业务算法与解析器，
    保护价值最高、且是纯函数式调用，不参与框架反射）；
  - **留 .py**：`app/main.py`、`app/api/*`（FastAPI 依赖运行时内省函数签名、
    `Annotated`、`Depends`——Cython 化后签名提取易碎）、`app/schemas/*`
    （pydantic v2 模型依赖类创建期的元类行为，能编但不值得冒险）、`app/config.py`、
    `app/db/*`（SQLAlchemy declarative 的类装配 + 本项目重迁移逻辑，调试价值也高）；
  - 余下模块用方案 A 的 `.pyc` 兜底，形成「核心 .so + 外围 .pyc」的分层形态；
- 回归护栏就是现有测试套件：PoC 已证明整套 pytest 可以跑在无源包上，Cython 阶段
  同样「编译 → 在产物上跑全量测试」作为门禁；
- 零授权成本（Cython 是 Apache-2.0），构建时长增加（百模块级 Cython + C 编译在
  CI 上约 +5~15 分钟）。

### D. Nuitka —— 不推荐

module 模式与 Cython 同类但构建慢得多、报错信息更晦涩；standalone/onefile 自带解释器，
与「依赖系统 python312 + 现场 venv」的 fnOS 应用形态冲突（§3.1），排除。

### E. 自研加密加载器（加密字节码 + 运行时解密 import hook）—— 不推荐

解密密钥必须随包分发（在 shim 里），攻击者单步跟一次就能提走密钥批量解密；
实现却要自己维护 import hook 与工具链兼容性。强度 ≈ 方案 A，成本与风险远高于 A。放弃。

### F. 不需要处理的部分

- 前端：`app/static` 本来就是 minify 后的构建产物；
- `manifest`/`wizard`/`cmd/*`：shell 脚本与配置，不含业务逻辑（启动参数、回调流程
  属公开的 fnOS 规范形态），保持原样。

### 对比总表

| 方案 | 保护等级 | 许可成本 | 运行时依赖 | 架构问题 | 构建链改动 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| A 无源 .pyc | L1 | 0 | 无 | 无 | 小 | **第一期落地** |
| B PyArmor Pro | L2 | ~$78 + 绑定机器 | pyarmor_runtime .so | 有 | 中 | 备选 |
| C Cython .so | L2+ | 0 | 无（产物即 .so） | 有 | 中（双架构 CI） | **第二期按需** |
| D Nuitka | L2+ | 0 | — | 有 | 大 | 排除 |
| E 自研加载器 | ≤L1 | 0 | 自维护 hook | 无 | 大 | 排除 |

## 5. PoC 记录（2026-09-29 实测）

环境：Windows 11 + 本机 CPython 3.12.14（`~/.local/bin/python312.exe` 建 venv，
安装 `app/requirements.txt` + pytest + httpx）；脚本在 `.local_tmp/`（已 gitignore，
不入库）：`poc_pyc_build.py`（编译 150 模块 → 无源布局）、`poc_boot.py`（启动验证）。

| 步骤 | 结果 |
| --- | --- |
| 3.13 编译 → 3.12 导入 | ❌ `bad magic number`（印证 §4.A 版本一致性问题） |
| 3.12 编译 150 模块，包内 .py 残留 | ✅ 0 个 |
| 无源包启动 uvicorn（TestClient 走 startup） | ✅ `GET / → 200`、`/docs → 200`、业务接口 422 统一契约（路由/校验/中间件/DB 初始化全通） |
| 全量 pytest 跑在无源包上 | ✅ 1107 收集 / 1072 通过 |
| 失败 35 条定性 | 12 条读 `manifest`/`wizard`/`cmd`（暂存未拷，环境性）；23 条 `tests/security` 源码静态扫描（`inspect.getsource`/`read_text`，按设计不适用） |

结论：**无源 .pyc 形态对运行时零侵入**，现有测试体系可直接充当发布门禁。

## 6. 推荐路线与决策点

**第一期（半天工作量，纯构建期改动）**：方案 A。

1. 新增 `scripts/compile_app_pyc.py`：输入暂存目录，`py_compile` 全量 `.py → .pyc` 平铺，
   跳过 `static`/`ui`；显式断言编译解释器为 3.12（`sys.version_info[:2] == (3, 12)`），
   版本不符直接报错——把 PoC 踩到的 magic number 坑固化成门禁；
2. `scripts/build_fpk.sh`（与 `build_fpk.bat`）：暂存段改为「先拷源码 → 编译 → 删 `.py`」，
   顺序放在 `sync_version.py` 之后、fnpack 之前（版本号写入 `app/config.py` 需在编译前）；
3. `scripts/fpk_selfcheck.py`：期望清单 `.py` → `.pyc`（`app/main.py` 断言同步改），
   新增「包内不得存在 `.py`」的反向断言；
4. CI（`.github/workflows/*` 与 `ci_build.sh`）：构建 Python 固定 3.12；
5. dev 渠道保持明文（测试包无需保护、且便于真机排查），仅 release 渠道编译——
   用 `BUILD_CHANNEL` 分叉，成本为零。

**第二期（观察第一期后的实际泄露情况再启动）**：方案 C，把 `services`/`parsers`/`utils`
编译为双架构 `.so`，其余维持 `.pyc`。

**待决策**：

| # | 决策点 | 建议 |
| --- | --- | --- |
| 1 | AI 提示词在 .pyc 中仍可被 `strings` 提取，是否需要把提示词外置为混淆资源或保持现状 | 保持现状：提示词本身无隐私数据，且效果不构成壁垒 |
| 2 | 第二期是否值得为 ARM 版 fnOS 维护双架构构建 | 等 ARM 用户量起来再说；第一期无此问题 |
| 3 | 是否购买 PyArmor Pro 换取更低实现成本 | 不建议：Cython 免费、强度更高，只是 CI 多花半天 |
| 4 | release 包加密后，用户报障的 traceback 是否够用 | `.pyc` 保留文件名与行号，`app.log` 排查能力不变；dev 包仍明文可对照 |

## 7. 风险与回退

| 风险 | 缓解 |
| --- | --- |
| CI 编译解释器版本漂移（3.13/3.14）导致设备端 bad magic number | `compile_app_pyc.py` 硬断言 3.12 + CI 锁版本；发版自检跑 fpk_selfcheck |
| python312 系统应用未来升级小版本 | 关注 fnOS 更新日志；os_min_version 与发布说明注明「需重装/升级获取兼容包」 |
| 第三方库运行时反射依赖源码（当前未发现：全仓无 `inspect.getsource`/`__doc__` 依赖） | 上线前全量测试跑在无源包上（PoC 流程脚本化），失败即阻断 |
| 加密包引出线上问题需快速回退 | 加密是纯构建期开关，回退 = 关开关重打包发版；设备端升级链路（fpk 全量替换）不变 |
