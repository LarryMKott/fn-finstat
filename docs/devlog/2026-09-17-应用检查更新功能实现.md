## 1. 目标与边界

给「设置 → 关于」卡片加上「检查更新」：告诉用户**有没有新版本、新版改了什么、去哪里下载**。

**明确不做自动升级。** 飞牛第三方应用的安装与升级由系统应用中心完成（fpk 由平台解压到
`${TRIM_APPDEST}`），应用进程既无权也不应替换自身安装目录。所以本功能的终点是「引导下载」，
不是「一键升级」——这条边界写在服务层与组件的注释里，避免后来者误以为是没做完。

## 2. 数据源选型

用 **Gitee OpenAPI v5 的 Release 列表**：

```
GET https://gitee.com/api/v5/repos/<owner>/<repo>/releases?page=1&per_page=20
```

三个候选的取舍：

| 候选 | 结论 |
| --- | --- |
| `releases/latest` | ❌ 实测**不排除预发布**：仓库最新一条是 `v0.7.1-dev.2.g8c2979a`（`prerelease: true`），该接口照样返回它。正式版用户会被引导去下测试包 |
| `releases.atom` | ❌ 404，该项目未开这个 feed |
| **`releases`（列表）** | ✅ 匿名可用、无需 token，**由本端按渠道过滤后取最大版本**，不依赖返回顺序 |

> 实测确认列表接口无需 `access_token` 即可访问（发版前需重新确认一次——Gitee 收紧匿名
> 额度时这是最先失效的一环）。响应体的 `assets[].browser_download_url` 即 fpk 直链。

`owner/repo` 不在代码里重复书写：接口与页面地址都由 `config.APP_REPO_URL` 推导。

## 3. 渠道模型：由本机版本号推导，不设配置项

`sync_version.py` 给 dev 渠道产物追加 `-dev.N.gSHA` 预发布段，**运行中的版本号本身就是渠道标识**，
因此不需要（也就不会被配错）渠道设置：

| 本机版本 | 渠道 | 与哪些 Release 比对 |
| --- | --- | --- |
| `0.7.1` | `release` | 只比正式 Release —— 测试包绝不能推给正式用户 |
| `0.7.2-dev.3.g6e5ffc1` | `dev` | 与**全部** Release 比对 —— 正式版发布后测试用户也要收到提示 |

## 4. 版本比较：三个必须踩对的坑（零依赖实现 semver）

`app/services/update_service.py` 自行实现比较，不引入新运行时依赖。

1. **预发布版本小于同号正式版**（`0.7.1-dev.2` < `0.7.1`）。
   算反的后果：装了正式版的用户被反复提示「有新版本」，装了测试版的反而显示「已是最新」。

   > 实现期真实踩到：`_pre_parts("")` 写成 `"".split(".")` → `[(1, "")]`，
   > 把「没有预发布段」编码成了「一个空标识符」，于是整条大小关系反转。
   > 冒烟脚本立刻暴露（`0.7.1` vs `0.7.1-dev.2` 返回 -1），已修并补进参数化用例。

2. **预发布段内的数字标识符按数值比**（`dev.10` > `dev.2`）。按字符串比会得出相反结论，
   表现为「构建号涨到两位数后更新提示消失」。

3. **历史 tag 必须剔除**。仓库里有 `v`、`v23`、`v33`、`v37`、`v38`、`v39` 这批旧构建号 tag，
   若只要求 `major`，`v23` 会被解析成 `23.0.0` 并永远「最新」。因此版本号正则**要求三段齐全**，
   解析不了的 tag 直接跳过（返回 `None`，不可比较 ≠ 相同）。

## 5. 接口契约

```
GET /api/update/check?refresh=false   →  ApiResponse[UpdateCheckResult]
```

| 字段 | 说明 |
| --- | --- |
| `ok` / `message` | 结论与一句话说明；**失败也用 ok=false 表达，不抛错** |
| `current_version` / `channel` | 本机版本与推导出的渠道 |
| `latest_version` / `relation` | 远端版本与关系：`newer` / `same` / `older`（本机为未发布构建）/ `unknown` |
| `release_name` / `published_at` / `notes` | 版本名、发布时间、更新说明摘录 |
| `download_url` / `checksum_url` / `page_url` | fpk 直链、MD5 校验文件、Release 详情页 |
| `checked_at` / `cached` | 检查时间、本次结果是否来自后端缓存 |

权限：**普通账号即可**（`CurrentUser`）。只读远端公开信息、不读任何本机数据，故不进
`_ADMIN_RULES`；已在 `tests/test_permissions.py` 的策略矩阵里加两条（含带向导前缀）固定这个决定。

### 5.1 离线降级（离线部署是产品前提，不是异常）

无外网 / 限流 / 响应异常全部转成 `ok=false` + 可读 `message`，HTTP 仍为 200：

- 后端不抛错 → 设置页不会因为「查不到更新」而弹错误浮层或 500；
- 前端把「查不到」当**错误相位**处理（`failed: (r) => r.ok === false`），
  避免浮层弹绿勾却写着「无法连接更新服务器」。

### 5.2 结果缓存

后端进程内 5 分钟 TTL（`CACHE_TTL`），**失败结果同样缓存**——离线时每次进设置页都重试会白等一个
超时。用户手动点「重新检查」时传 `refresh=true` 绕过；自动检查复用缓存，避免反复进出设置页
把 Gitee 匿名额度耗光。

### 5.3 下载直链的优先级

`带版本号副本` → `裸名 fn-finstat.fpk` → 任意 `.fpk`。

刻意**不识别渠道别名**（`fn-finstat-latest.fpk` / `fn-finstat-dev.fpk`）：别名与同 Release 内其它
fpk 内容完全一致，为它在 app 侧再维护一份渠道词表，只会多一处需要与 `scripts/sync_version.py`
对齐的地方。带版本号副本是两个渠道流水线都硬断言存在的产物，也最能回答「下到的是哪次构建」。
（实测现状：`v0.7.0`/`v0.7.1` 这两个早期正式 Release 只挂了裸名与带版本号副本，没有 `-latest`。）

## 6. 前端接入

- `frontend/src/api/update.js`：`checkUpdate(refresh)`，显式 `timeout: 20_000`（后端查 Gitee 上限 10s）
- `frontend/src/components/settings/AppearanceAboutCard.vue`：更新块并入「关于」卡片
  - 进设置页**静默检查一次**（`runTask({ silent: true, rethrow: false })`），用户不必先点才知道有没有新版
  - 手动点击走 `runTask` 可见反馈 + 绕过后端缓存
  - 结论行按 `relation` 着色（有新版本→主色；已最新→中性；查不到→`--color-warn`）
  - 更新说明默认折叠（复用全局 `.note-toggle` 模式），展开后限高滚动
- `frontend/src/utils/datetime.js` 新增 `isoDate()`：ISO 串 → `YYYY-MM-DD`。
  **只切片不做时区换算** —— 后端返回的时间串自带发布方偏移，交给 `Date` 解析会按运行环境时区偏成前一天
- `frontend/src/components/AppIcon.vue` 新增 `refresh` 图标（复用 `restore` 会与「恢复」语义混淆）

## 8. 设备实测暴露的缺陷与修复（同日补）

版本号推进到 `0.7.3` 并发出测试包 `v0.7.3-dev.5.g4cc0a6f` 后，拿真实数据复核时发现：
**更新说明会被错标成 `v0.7.1` 的日志**。

实测证据（`_release_notes` 返回的首行 = `'## fn-finstat v0.7.1'`，含 v0.7.1、不含 v0.7.3）：

| 环节 | 事实 |
| --- | --- |
| Release 描述来源 | `.workflow/*.yml` 的 `description: CHANGELOG.md` |
| `CHANGELOG.md` 最新小节 | 停在 `## fn-finstat v0.7.1`（v0.7.2 提版本号时没跑 `--update-changelog`） |
| 原实现 | 无脑取正文**第一个** `## ` 段，隐含假设「CHANGELOG 最新版在最前」 |

该假设在上游数据陈旧时不成立，而 dev 渠道**每次 push 都发 Release**，所以「CHANGELOG 落后于
构建」是常态而非例外。后果是把上一个已发布版本的日志当作本次说明展示 —— 比「没有说明」更糟：
用户会以为那些变更就是本次的（项目自己的 REQ-RPT-001 就是不接受这种误导）。

**修复（两侧都做）**

1. **应用侧（`_release_notes(body, version)`）**：按**基版本**（去掉预发布段，`0.7.3-dev.5.g4cc0a6f`
   → `0.7.3`）匹配小节标题；测试包与同基线正式版共用同一份 CHANGELOG 小节，这是设计如此。
   匹配不上返回空串，界面隐藏说明区块。另加边界断言 `(?<![\d.])0.7.1(?![\d.])` 防 `0.7.1` 命中 `v0.7.10`。
   宁可少显示，不可错标。
2. **数据源**：跑 `gen_release_notes.py --update-changelog` 把 `CHANGELOG.md` 补到 `0.7.3`，
   并把「打测试包前也要更新 CHANGELOG」写进 `docs/发布流程与Release日志.md`（含排查项）。

**回归用例**：新增 3 例 —— dev 包匹配基线小节、CHANGELOG 落后时必须留空（即本次实测到的场景）、
`0.7.1` 不得命中 `v0.7.10`。全量 49 例通过。

## 9. 后续可选项（本次未做）

- **通知中心事件**：发现新版本时推一条应用内通知（`notify_service` 既有事件体系已就绪）
- **启动时静默检查**：目前只在进设置页时检查，可在应用启动后延迟检查一次
- **忽略此版本 / 跳过版本**：需要新增本地状态文件，暂按「用户自己不再点」处理
- **描述版本对不上时改读附件 `releaseNode.txt`**：该文件每构建一份，dev 渠道还带「🧪 测试版本」
  声明（正好补上官方描述里缺的那行）；代价是每次检查多一次请求
- **`description` 改为 `releaseNode.txt`**：当年因「文本 \| 文件路径」语法不生效才退回 CHANGELOG.md，
  若 Gitee Go 修好了该语法，描述就能天然跟随每次构建
