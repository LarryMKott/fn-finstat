## 1. 现象

用户反馈：「卸载时没有询问是否保留用户数据」。

进一步确认后的现场事实：

- 卸载入口是**应用中心 → 财务统计 → 卸载**；
- 卸载向导**确实弹出了**，标题「数据清理」，里面是一个默认关闭的开关「删除全部本地数据」。

也就是说机制是通的，问题出在**语义与可辨识度**：向导只问了「要不要删」，没有把
「保留 / 删除」作为一个显式二选一摆出来，用户容易看漏，也不符合「询问是否保留用户数据」的预期。

---

## 2. 排查过程与结论

排查花了不少功夫，结论值得记档，避免下次重复踩：

### 2.1 打包链路是干净的

| 检查项 | 结果 |
| --- | --- |
| `wizard/uninstall` 是否存在且已提交 | 存在，自 `c84e6d8`（v0.2.5）起就在 |
| 是否打进 FPK | 打进去了（外层 tgz 22 条目，`wizard/uninstall` 在列） |
| 文件名是否符合规范 | 符合。官方《应用框架》与《用户向导》都列 `wizard/uninstall` |
| 内容是否通过校验 | 通过。fnpack 的 `Verifying files...` 无告警 |
| 字段/环境变量约定 | 符合。官方约定 `field` 即环境变量名，自定义字段建议 `wizard_` 前缀 |

### 2.2 fnpack 确实会校验 wizard（实测）

用四组对照实验确认（在暂存目录里改坏后重跑 `fnpack build`）：

| 改动 | 结果 |
| --- | --- |
| `wizard/uninstall` 写成非法 JSON | `Packing failed. File "uninstall" is not valid...` |
| item `type` 写成未知值 | 同上 |
| `stepTitle` / `items` 置空 | 同上 |
| wizard 目录里多放一个无关文件 | **通过**（所以 `.gitkeep` 不是原因） |

### 2.3 顺带挖出的两个有价值的事实

1. **`disable_authorization_path` 不在 fnpack 二进制里** —— 说明它是飞牛系统侧读取的字段，
   与上一次修复（`2026-09-13-飞牛授权目录设置入口修复.md`）的判断一致。
2. **fnpack 打包失败时退出码仍是 0** —— 见第 4 节，这是一个真实缺陷。

## 3. 修复一：卸载向导改为显式二选一

`wizard/uninstall` 由「默认关闭的 switch」改为「radio 二选一」：

```json
{
  "type": "radio",
  "field": "wizard_purge_data",
  "label": "本地数据处理方式",
  "initValue": "false",
  "options": [
    { "label": "保留账单数据（推荐）", "value": "false" },
    { "label": "删除全部本地数据（不可恢复）", "value": "true" }
  ]
}
```

要点：

- **字段名保持 `wizard_purge_data` 不变**。官方《用户向导》明确要求「使用稳定的字段名，
  修改字段名会改变环境变量名」，改名会让回调读不到用户选择。
- **取值沿用 `false` / `true`**，语义与 `cmd/uninstall_callback` 原有解析完全一致，回调无需改判定逻辑。
- **默认 `false` = 保留**，两个选项同时可见，用户必须看到「保留」这个选项。
- 前后各保留一条 `tips`，第一条说明默认保留、重装可续用，第二条说明两种选择各自的影响范围。

`cmd/uninstall_callback` 同步加固：

- 记录原始取值到日志（`wizard_purge_data=xxx`），便于真机排障；
- 清除取值在原有 `true/1/on/yes` 之外补充 `purge/delete`；
- 其余任何取值（含空值）一律按保留处理，不会误删。

## 4. 修复二：fnpack 失败会静默放过（真实缺陷）

**实测**：`fnpack build` 在 `Packing failed` 时退出码是 **0**，只在 stdout 打印失败原因。

后果：`build_fpk.sh` 的 `set -e` 与 `build_fpk.bat` 的 `|| goto fail` **都抓不到**，
流程会继续跑权限修正与自检，最后打印「打包完成 / [OK] packaging done」——
而此时设备上的 `fn-finstat.fpk` 其实是**上一次的旧包**。

修复后的流程：

1. 打包前先删除旧产物 `fn-finstat.fpk`；
2. 捕获 fnpack 输出，匹配关键字 `Packing failed` 即中止；
3. 再校验产物文件确实生成（双重判定，防止 fnpack 改了提示文案）。

两个脚本（`.sh` / `.bat`）都改了，并加了回归测试锁定。

顺带：`wizard/.gitkeep` 不再打入包（它只是为了让空目录能入库，不该出现在设备的
`/var/apps/fn-finstat/wizard/` 里）。

---

## 5. 修复三：打包自检补上外层条目与向导校验

`scripts/fpk_selfcheck.py` 原来只校验 `app.tgz` 内部。考虑到「wizard 缺失」这类故障
在打包阶段完全静默、只在真机卸载时暴露，新增：

- `REQUIRED_OUTER`：外层 tgz 必须包含 manifest、两个图标、8 个 `cmd/` 生命周期脚本、
  `config/privilege`、`config/resource`、`wizard/install`、`wizard/uninstall`；
- `check_wizard()`：向导必须是非空步骤数组，`stepTitle` / `items` 非空，
  控件类型在 fnpack 支持集合内，`tips` 必须有 `helpText`，其余类型必须有 `field` / `label`，
  `radio` / `checkbox` / `select` 必须有 `options`。

## 7. 遗留事项

- fnOS 是否对 `wizard/uninstall` 有版本门槛（如最低系统版本）尚未验证；本项目
  `os_min_version=1.2.0401`，用户侧实测该版本下向导可正常弹出。
- fnpack 的失败退出码问题属工具缺陷，本项目只能在脚本侧兜底；若后续 fnpack 修正退出码，
  现有的「关键字 + 产物存在」双重判定仍然有效，无需回退。
