## 1. 设计

- **凭证形态**：`ffk_<32 位十六进制>`。服务端**只存 SHA-256 哈希**
  （唯一约束），明文仅在签发响应中出现一次——库泄露不等于凭证泄露。
- **恒为只读且非管理员**：Token 是「给脚本查数」的凭证，不是账号替代品。
  写方法与管理面一律拒绝，两层拦截：
  1. 权限中间件在路由分发前拦（写方法 403、管理面 403），请求不进业务层；
  2. `deps.get_identity` 解析身份时再拦一次写方法（纵深防御）。
- **身份解析优先级**：**网关可信头优先，Token 仅作无网关头请求的兜底**。
  带 `X-Trim-Userid` 的请求（浏览器 / 飞牛桌面）完全不走 Token 路径，
  Token 内容与有效性都不参与判定。
- **数据隔离不依赖 Token 层**：Token 解析出的身份仍只是一个 `user_id`，
  后续按既有 DAO 层 `user_id` 过滤取数，隔离机制零改动。

## 3. 评审发现并修复的两个缺陷

### 3.1 中间件 Token 分支缺「无网关身份」前置条件（可用性缺陷，已修）

**缺陷**：判定条件是 `if has_api_token(raw):`，只要请求头里出现
`Authorization: Bearer <任意值>` 或 `X-Api-Token`，**无论是否携带合法网关身份、
无论 Token 是否有效**，都会走进 Token 分支，从而整体跳过本中间件本该执行的
`access_rejection` 判定。

**后果**：带合法网关身份的**普通写请求被误判为「Token 只读请求」并回 403**，
文案为「API Token 仅支持只读访问」——而用户根本没在用 Token，报错完全误导。
任何给请求附加 `Authorization` 头的浏览器侧路径（代理、扩展、后续前端改造）
都会让写操作全线失效。

**修复**：加 `not user.user_id` 前置条件，与 `deps.get_identity` 的
「网关头优先」同语义——Token 只在**确实没有网关身份**时才参与判定。

**验证**：`tests/api/test_token_middleware.py`。该用例在修复前**确定性失败**
（实测返回 `{"code":10002,"msg":"API Token 仅支持只读访问"}`），修复后转绿；
同时覆盖「无网关身份 + 带 Token 仍走 Token 分支」与「无身份无 Token → 401」
两条边界，确保修复没有把 Token 通道整体关掉。

### 3.2 前端导入名与导出名不匹配（功能失效，已修）

**缺陷**：`TokenCard.vue` 导入 `deleteToken`，但 `api/tokens.js` 导出的是
`revokeToken` —— 命名不一致导致撤销功能在运行时失效。

**隐蔽性**：eslint 不检查模块导出是否存在；**Vite 构建同样不报错**
（实测 build 通过），错误只在运行时以 `deleteToken is not a function` 暴露。

**修复**：统一为 `revokeToken`（与后端「撤销」语义一致，`revoked` 字段命名对应）。

## 5. 提交历史的已知瑕疵（评估后决定不修）

本批 4 个提交中，`a262c15`（Token 主体）与 `65da017`（`get_identity`）之间的
中间提交点**严格说不可运行**：`a262c15` 的 `app/api/tokens.py` 已导入
`CurrentUser`，但同提交的 `app/api/deps.py` 尚未定义 `get_identity`，
该点导入即崩。成因是首轮提交时漏暂存 `deps.py`。

**处置决定：不改写历史（不做 squash），保留现状。** 依据：

1. **影响面为零**——这 4 个提交只存在于 `dev`，**尚未合入 `main`**
   （`origin/main` 仍在 `337ea01`），且为单人开发，无人在此基础上并行工作。
   `HEAD`（`65da017`）可运行、全量测试绿。
2. **风险收益比不划算**——修正它需要 force push，而本机 git 的改写类操作
   风险显著高于已实测翻车的 `stash` / `checkout -b`（见《工程踩坑与硬约束备忘》）。
   拿「仓库可能损坏」换「历史里少一个不优雅的点」，不值得。
3. **有机会自然抹平**——真正合入 `main` 时本就该走 merge / squash，
   该中间点届时自动消失，无需现在单独动历史。

**待办**：合 `main` 时若采用普通 merge，该中间提交点会一并进入 `main`；
若在意可运行性，届时用 `--squash` 合并即可。

## 6. 已知边界（不隐瞒）

- **Token 无过期时间**：只有「撤销」一个失效途径。长期有效的只读凭证在
  家庭共用场景下可接受（只读 + 可随时撤销），如需过期策略建议随 T-1.7
  的加密与凭据治理一并设计。
- **`last_used_at` 有 60s 节流**：高频调用下该字段是「大约最近使用」而非精确值，
  这是刻意的写放大控制；不影响撤销与鉴权语义。
- **管理面不开放给 Token**：设计如此。若后续需要「用 Token 做自动化运维」，
  必须新开一套带显式授权范围的凭证体系，不能放宽现有 Token。
