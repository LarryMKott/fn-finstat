## A1 🔴 `commit-msg` 钩子正则与日志脚本正则不一致

### 问题

`Git提交规范.md` 第 9.2 节给出的钩子正则，与 `scripts/gen_release_notes.py` 实际使用的 `COMMIT_RE` 是**两套不同的规则**：

| 规则来源 | 正则 | 校验目标 |
| --- | --- | --- |
| 规范钩子（第 9.2 节） | `^(security\|feat\|fix\|…\|revert)(\([^)]+\))?!?[[:space:]]*[:：][[:space:]]*.+$` | 只放行 12 个**标准 type** |
| 脚本 `COMMIT_RE`（第 81 行） | `^(?P<type>[A-Za-z]+)(?:\((?P<scope>[^)]*)\))?(?P<breaking>!)?\s*[:：]\s*(?P<subject>.+)$` | 放行**任意字母 type** + 别名表映射 |

实测结果（本机验证）：

| 提交标题 | 钩子 | 脚本 |
| --- | --- | --- |
| `feat(import): 差异报告支持导出 CSV` | ✅ 通过 | ✅ 识别 |
| `feat(api)!: 破坏性变更` | ✅ 通过 | ✅ 识别 |
| `feature: 别名提交` | ❌ **拦截** | ✅ 识别为 feat |
| `feat(): 空 scope` | ❌ **拦截** | ✅ 识别 |

**两处硬伤：**

1. **钩子会误伤规范明确允许的别名提交**。规范 2.2 节写着"脚本兼容的别名：`feature`、`features` → `feat`"，但钩子只放行 `feat`。开发者照着别名表写 `feature(xxx): ...` 提交，钩子直接 `exit 1` 拒绝——**规范自相矛盾**。
2. **钩子正则用了 `\([^)]+\)`（`+`）**，意味着空 scope `feat(): xxx` 被拒；而脚本用 `[^)]*`（`*`）是放行的。虽然空 scope 本来就该避免，但两者行为不一致会让开发者困惑。

此外钩子里的 `[[:space:]]` 是 **POSIX 字符类**，在 `[[ =~ ]]` 中能用，但直接粘贴到 `grep -E` 或其他语言环境会失效——规范作为"可复制的模板"存在这个隐患。

### 修改建议

把钩子正则改为与脚本一致的宽松版（钩子只做"形似"拦截，type 合法性交给日志脚本归组）：

```bash
# 与 scripts/gen_release_notes.py 的 COMMIT_RE 对齐：放行任意字母 type + 别名
PATTERN='^[A-Za-z]+(\([^)]*\))?!?[[:space:]]*[:：][[:space:]]*.+$'
```

如果坚持要拦截非法 type，则应**同时**在规范里声明"别名不推荐使用，钩子会拒绝"，消除 2.2 节与 9.2 节的矛盾。二选一，不能既说别名兼容又说别名被拒。

并且在 9.2 节加一句边界说明：

> 钩子只做最低限度的格式校验（防 `update VERSION.` 这类无 type 提交）。`type` 是否被正确归组、别名是否识别，以 `gen_release_notes.py` 的 `TYPE_ALIASES` 为准——两者规则不同，钩子更严格。

## A2 🔴 前端质量门禁不在 CI 中，规范却要求"提交前检查"

### 问题

`前端开发规范.md` 第 17 节"提交前检查清单"要求：

```
- [ ] npm run lint 无错误
- [ ] npm run format 已格式化
- [ ] npm test 通过
```

`编译与构建规范.md` 第 5.2 节"构建门禁清单"也列了 6 条门禁，**但没有一条是前端 lint / format / test**。

实测确认：

```bash
grep -n "npm test|npm run lint|eslint|prettier" scripts/ci_build.sh scripts/run_tests.sh
# → ❌ 无任何匹配：CI 完全没跑前端 lint / format / test
```

CI 对前端只做 `npm ci` + `npm run build`（`ci_build.sh` 第 134-141 行）。

**后果**：规范把 lint/format/test 定位为"提交前自查项"，即**全靠人自觉**。LLM 或新人在前端引入 lint 错误、忘记跑测试，CI 一律绿灯通过——因为这些门禁只在人脑里，不在流水线里。这正是"写了规范但没生效"的典型。

### 修改建议

在 `ci_build.sh` 第 3 步（前端构建）中，把 `npm ci` 与 `npm run build` 之间插入前端门禁：

```bash
cd frontend
npm config set registry "$NPM_REGISTRY"
npm ci --no-fund --no-audit || { ... }

# 前端质量门禁（与后端 ruff 对等）
echo "==> 前端 lint 门禁"
npm run lint || { echo "❌ ESLint 未通过"; exit 1; }
echo "==> 前端测试门禁"
npm test || { echo "❌ 前端测试未通过"; exit 1; }

npm run build
cd ..
```

同步在 `编译与构建规范.md` 第 5.2 节门禁清单补两条：

```
- [ ] `npm run lint` 通过（ESLint）
- [ ] `npm test` 通过（Node 原生 test runner）
```

> format 检查建议**不要**进 CI（Prettier 重排会产生噪音 diff），保持"编辑器保存时自动格式化"即可——但要在规范里明确写出这个取舍，而不是含糊地列在检查清单里。

## A3 🔴 `npm test` 只跑一个硬编码文件

### 问题

`frontend/package.json`：

```json
"test": "node tests/loading.test.mjs"
```

这是**硬编码单个文件名**，不是 glob。`frontend/tests/` 目录目前只有 `loading.test.mjs` 一个文件（11 个 `test()` 用例），所以现在看不出问题——但**只要有人新增 `xxx.test.mjs`，它就永远不会被执行**，`npm test` 依然只跑 loading 那一个文件，而且退出码依然是 0。

`前端开发规范.md` 第 15 节写着"`npm test` 跑 `tests/*.test.mjs`"——**文档描述的是 glob 行为，脚本实现的是单文件**。这是文档与实现不一致，且会静默吞掉新测试。

### 修改建议

package.json 改为真正的 glob：

```json
"test": "node --test tests/"
```

Node 22+ 的 `node --test <dir>` 会自动发现目录下所有 `*.test.mjs` / `*.test.js` / `test-*.js`。若需兼容更老版本：

```json
"test": "node --test tests/*.test.mjs"
```

同时更新 `前端开发规范.md` 第 15 节，明确"新增测试文件放在 `tests/`，命名 `*.test.mjs`，会被 `npm test` 自动收录"。

## A4 🟡 `black` 被列为强制项，但既不是依赖也不是门禁

### 问题

`后端开发规范.md` 第 1 节把 `black` 列为技术栈的"格式化"项，第 11 节检查清单要求 `black app tests scripts` 已格式化。`编译与构建规范.md` 第 6.1 节说"测试依赖（pytest、httpx、ruff）不进 requirements.txt"。

实测：

```bash
grep -n "black" app/requirements.txt   # → 无
grep -n "black" scripts/ci_build.sh    # → 无
cat pyproject.toml                     # → 只有 [tool.black] line-length = 88 配置块
```

**black 只在 `pyproject.toml` 里留了一段配置，但：**
- 不在 `app/requirements.txt`（合理，它不是运行时依赖）
- 不在 `ci_build.sh` 的门禁里（不合理——`ruff` 进来了，black 没进来）
- 不在 `run_tests.sh` 的自动安装列表里（第 34 行只装 `pytest httpx`）

结果是：**规范要求"已格式化"，但没有工具链保证、没有门禁拦截，开发者本地也不一定装了 black**。这条规范事实上处于"写了但不可执行"状态。

### 修改建议

两个方向，选一个并写清楚：

**方向一（推荐）——让 black 可执行**：与 `ruff` 对齐，加入 CI 门禁并纳入自动安装：

```bash
# ci_build.sh 测试门禁段
"$PYTHON" -m pip install ... ruff black
...
echo "==> 格式门禁：black --check"
black --check app cmd scripts tests || {
  echo "❌ 存在未格式化的文件，请本地执行 black app tests scripts"
  exit 1
}
```

并把 `编译与构建规范.md` 第 6.1 节的依赖说明改为"测试与工具依赖（pytest、httpx、ruff、black）不进 requirements.txt，由 CI 单独安装"。

**方向二——弱化 black**：若团队实际并不统一用 black，则删除第 11 节的 black 项与第 1 节的"格式化"行，改为"风格以 `ruff check --select F,E9` 为准"。不要保留一条无法执行的强制项。

## A6 🟡 `VERSION` 号称唯一版本源，前端 `package.json` 无人同步

### 问题

`编译与构建规范.md` 第 2 节与 `Git提交规范.md` 第 6 节都强调：

> **`VERSION` 文件是应用版本号的唯一真实来源**，不要直接改 `manifest` 或 `app/config.py`。

`sync_version.py` 确实同步了两处：

```python
# 1. manifest
# 2. app/app/config.py 的 APP_VERSION
```

**但遗漏了第三处：`frontend/package.json` 的 `version` 字段。** 实测当前两者恰好都是 `0.7.0`（人工保持一致），但下一个版本 `echo "0.8.0" > VERSION` 之后，`package.json` 会停在 `0.7.0`——**没有任何脚本或门禁会发现这个漂移**。

版本号漂移的实际影响：`package.json` 的 version 会进入 npm 生态（虽然私有包影响小），更重要的是它构成"同一个仓库里有两个自相矛盾的版本号"，违背了规范自己立的"单一来源"原则。

### 修改建议

在 `sync_version.py` 增加第三处同步（前端 `package.json` 在源码树中，不在暂存目录，需单独处理）：

```python
# 3. frontend/package.json 的 version（源码树，非暂存目录）
pkg = Path("frontend/package.json")
if pkg.exists():
    data = json.loads(pkg.read_text(encoding="utf-8"))
    data["version"] = version
    pkg.write_text(json.dumps(data, ensure_ascii=False, indent=2) + "\n", encoding="utf-8")
```

> ⚠️ 注意：`build_fpk.sh` 的暂存目录里没有 `frontend/`（前端源码不入包），所以这段要写成**独立于 `stage_dir` 的参数**，或在 `gen_release_notes.py --update-changelog` 同一步做。更稳的做法是在发版流程（`Git提交规范.md` 第 6 节 / `编译与构建规范.md` 第 4 节）里加一步校验脚本，比对 `VERSION` 与 `package.json version` 不一致就报错。

## A7 🟡 提交信息正则的实际行为严于文档描述

### 问题

`Git提交规范.md` 第 2.1 节写：

> 格式校验的真实正则（脚本实现）：`^[A-Za-z]+(\([^)]*\))?!?\s*[:：]\s*(.+)$`
> 也就是说：`type` 只能是英文字母，`scope` 内不能出现右括号 `)`。

这段描述是对的。但紧接着第 2.2 节说别名的定位是"**能识别但不推荐，请优先用标准 type**"——而实际脚本里：

```python
key = TYPE_ALIASES.get(ctype)
(buckets[key] if key else buckets[OTHER_TITLE]).append(commit)
```

别名和标准 type 走的是**完全相同的代码路径**，别名提交会正常进入 `feat`/`fix` 等分组，在 Release 日志里与标准 type 毫无区别。也就是说："不推荐"这个定位**只是文字上的劝导，实现上没有任何惩罚或提示**。

更需要注意的是：一个**不在 `TYPE_ALIASES` 表里的纯字母 type**（如 `xxx:`）会被脚本匹配成功（正则放行任意字母）但直接落入"📌 其他变更"——**正则匹配成功 ≠ 能被正确归组**。规范的重心全在"格式"，却没说清"格式对了但 type 不在表里，同样会掉进其他变更"。

本机实测三种情况：

| 提交标题 | 正则 | 归组 |
| --- | --- | --- |
| `xxx: 随便` | 放行 | 📌 其他变更 |
| `feature(x): 别名` | 放行 | ✨ 新功能（别名生效） |
| `chore2: 表外 type` | **拒绝** | — （含数字，正则只允许字母） |

注意第三行：正则 `[A-Za-z]+` **不允许数字**，所以 `chore2:` 这类会直接匹配失败。这意味着带数字的 type 会连同"其他变更"的归组机会一起丢失——它甚至进不了"格式合法但未分组"的路径，而是被判为格式非法。文档若想让人理解边界，需要把"字母"这个限制讲得更醒目。

### 修改建议

在 2.2 节别名表后补一段明确说明：

> ⚠️ 正则会放行**任意字母组成的 type**（为了让别名能通过），但只有上表列出的 type 与别名才会被分组。写一个表外的 type（如 `chore2:`）虽然格式合法，仍会落入「📌 其他变更」。**请只用本表内的值。**

并把别名的定位写得诚实一些：

> 别名与标准 type 在日志中**完全等价**，不存在优劣。之所以列出来，是为了让历史提交不因拼写差异而掉组，而不是鼓励使用——统一用标准 type 更利于全员一致。

## A9 🟡 破坏性变更判定与文档描述不符

### 问题

`Git提交规范.md` 第 2.5 节：

> 带 `!` 的提交会**单独进入 💥 破坏性变更 分组**并置顶，同时保留在原分组中。
> ⚠️ 重要：日志脚本**只扫描提交标题行**，不会去读正文里的 `BREAKING CHANGE:`。

前半句（`!` 的行为）正确。但实测脚本 `group_commits`：

```python
if breaking or "BREAKING CHANGE" in commit["subject"].upper():
    buckets[BREAKING_TITLE].append(commit)
```

**这是对 `subject`（标题行）做 `in` 判断**，不是对 `!` 标记的判断。也就是说，一条标题里**恰好包含 `BREAKING CHANGE` 字样的普通提交**（例如 `docs: 补充 BREAKING CHANGE 章节说明`）会被**误判为破坏性变更**，进入 💥 分组并置顶。

这属于典型的"子串匹配误伤"。规范文档只说了"不读正文"，没说"标题里出现该字样会被误判"。

### 修改建议

修正脚本逻辑，只保留 `!` 标记判定（与文档描述一致）：

```python
if breaking:
    buckets[BREAKING_TITLE].append(commit)
```

如果确实想兼容正文，应单独取 `%b`（正文）字段而不是拿 subject 做子串匹配。同时在规范第 2.5 节补一句当前真实行为说明，避免文档与实现再次脱节。

**误判复现**（本机实测）：

```
输入：docs: 补充 BREAKING CHANGE 章节说明
结果：💥 破坏性变更 组 ← 该条同时出现在这里（错误）
      📝 文档 组      ← 这里才是它该在的位置
```

> 附带：目前 `git log` 只取 `%s`（subject），确实拿不到正文。若真要支持 `BREAKING CHANGE:` 脚注，需要在 `collect_commits` 的 `fmt` 里加 `%b` 并解析——这是功能增强，非必须。

## A10 🟢 "无身份头 = 全量放行"缺前置条件

### 问题

`后端开发规范.md` 第 4.3 节末尾：

> 无网关身份头（`user_id` 为空串）= 本地开发/独立部署的单机唯一用户，**全量放行**，避免单机用户被锁死。

这句话本身是事实描述，但**紧跟在"双层防御"的语境后面**，读起来像一个普通特性。而它的安全含义是：**任何人只要能发一个不带 `X-Trim-Userid` 头的请求，就是管理员**。

结合 4.1 节已声明的"这些头被无条件信任，不做来源校验"，这条规则的真正前提是"服务绝不能暴露在不可信网络"。4.1 节有警告，但 4.3 节这条放行规则**孤零零地出现，没有重申这个前提**，容易被读者当成"设计上的便利"而非"必须靠网络隔离兜底的裸奔路径"。

### 修改建议

在 4.3 节该句后追加明确前置：

> ⚠️ 这条放行规则的**唯一安全前提是 4.1 节的网络隔离**（网关模式仅绑 Unix Socket、独立部署绑 `127.0.0.1`）。换句话说：**身份头缺失即等同管理员，安全性完全由"外部访问不到"保证，而非由代码保证。** 任何改变监听地址或增加反代的改动，都必须先重新评估此规则。

## A13 🟢 `releaseNode.txt` 中断残留风险

### 问题

`编译与构建规范.md` 第 4.6 节与 `发布流程与Release日志.md` 第 2.5 节都提到"日志生成失败不阻断发布"，并在 `ci_build.sh` 第 174-194 行做了三层兜底。但都没提一个边界：

`releaseNode.txt` 若**上一次构建残留**（CI 工作区复用、或本地连续跑两次），而本次 `ci_build.sh` 在生成前就异常退出，那么**上一轮的 `releaseNode.txt` 会被 release 阶段当成本次日志上传**——和 4.3 节专门防范的"fnpack 失败却把旧 FPK 当新产物"是同一类问题。

实测 `ci_build.sh` 第 178 行是 `if ! gen_release_notes.py ...; then 回退`，逻辑本身正确（会覆盖），但**没有先删除旧文件**，一旦脚本执行被中断（超时 kill、磁盘满），残留文件就会被误用。

### 修改建议

在 `ci_build.sh` 生成日志前加一行预清理，与 fnpack 的处理对齐：

```bash
# 先删除旧文件，避免残留被当成本次日志（与 fnpack 产物处理一致）
rm -f releaseNode.txt
echo "==> 生成 Release 说明"
```

并在 `编译与构建规范.md` 第 4.3 节"fnpack 的坑"附近，把这个同类风险一并写出，让"先删旧产物再新生成"成为整个构建链路的统一心智。
