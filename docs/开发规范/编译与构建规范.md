# 编译与构建规范

> 适用：全仓库构建链路
> 配套：[发布流程与Release日志.md](../发布流程与Release日志.md) · [Git提交规范.md](Git提交规范.md)
> 与 `scripts/build_fpk.sh`、`scripts/ci_build.sh`、`fpk_selfcheck.py`、`check_assets_refs.py` 严格对应

## 1. 构建链路

"编译"含**前端编译**与 **FPK 打包**两段，三条入口：

| 入口 | 用途 | 测试门禁 | 构建前端 | 构建渠道 |
| --- | --- | --- | --- | --- |
| `scripts/build_fpk.sh` | 本地一键打包（Linux/macOS/Git Bash） | ✅ | ❌ 需先手动构建 | `BUILD_CHANNEL`，默认 `release` |
| `scripts/build_fpk.bat` | 本地一键打包（Windows） | ✅ | ❌ 需先手动构建 | 同上 |
| `scripts/ci_build.sh` | CI 全流程 | ✅ | ✅ | `BUILD_CHANNEL=auto`，按分支判定 |

> **关键差异**：本地脚本**不构建前端**，只做硬门禁校验；CI 脚本会先跑 `npm ci && npm run build`。这是新 clone 打包白屏事故的根源。

**产物**（fpk 与校验文件均在 `.gitignore` 内）：

| 产物 | 说明 |
| --- | --- |
| `fn-finstat.fpk` | fnpack 原始输出，仅作构建证明与流水线制品，**不挂到 Release 附件** |
| `fn-finstat-{渠道别名}.fpk` | **稳定下载入口**：release → `fn-finstat-latest.fpk`，dev → `fn-finstat-dev.fpk`。同名覆盖，下载链接可长期不变 |
| `fn-finstat-v{版本}.fpk` | 带完整版本号的副本，回答"这是哪一次构建" |
| `MD5SUMS.txt` | 上面**两个交付产物**的 MD5 校验文件，`md5sum -c MD5SUMS.txt` 可校验下载完整性 |
| `app/static/` | 前端构建产物（整目录 gitignore，由 `frontend/` 构建生成） |

**校验文件（`MD5SUMS.txt`）**：由 `scripts/gen_checksums.py` 生成，每行
`<32 位小写 md5><两个空格><文件名>`，GNU coreutils 格式，可直接 `md5sum -c` 校验。三条硬约束：

- **只列交付产物**（渠道别名 + 带版本号副本）。裸名 `fn-finstat.fpk` 不上传，把它列进去只会让用户对着一个下载不到的文件发愁
- **任一产物缺失即失败**，绝不产出"部分校验"文件——残缺清单会让用户误判成自己下载坏了
- **固定 LF 换行**。Windows 下写出 CRLF 会让 `md5sum -c` 把 `\r` 当作文件名的一部分，于是每个文件都报 `No such file or directory`

> MD5 只用于**传输完整性**（下载是否残缺），不是防篡改手段；防篡改看 Release 日志里的 SHA-256。
> 生成顺序固定为「先产出交付副本 → 再算校验值」，中间不要插入任何修改产物的步骤。

### 1.1 构建渠道：release / dev

打包分两个渠道，渠道决定**产物版本号的形态**，进而决定文件名、包内版本号与 Release 标识：

| 渠道 | 触发来源 | 产物版本号 | 用途 |
| --- | --- | --- | --- |
| `release` | `main` 分支；本地默认 | `0.7.1` | 正式发布 |
| `dev` | `dev` 分支；本地显式指定 | `0.7.1-dev.42.g1a2b3c4` | 测试验证 |

dev 渠道追加 semver **预发布段** `-dev.{构建号}.g{短sha}`（本地没有 CI 构建号时形如 `-dev.geb01922`）。
测试版标识因此落在四处，拿到包的人在任何环节都能识别：

| 位置 | release | dev |
| --- | --- | --- |
| 渠道别名（稳定入口） | `fn-finstat-latest.fpk` | `fn-finstat-dev.fpk` |
| 带版本号副本 | `fn-finstat-v0.7.1.fpk` | `fn-finstat-v0.7.1-dev.42.g1a2b3c4.fpk` |
| 包内 `manifest` 的 `version=` | `0.7.1` | `0.7.1-dev.42.g1a2b3c4` |
| `app/config.py` 的 `APP_VERSION`（应用「关于」页） | `0.7.1` | `0.7.1-dev.42.g1a2b3c4` |
| Gitee Release | tag `v0.7.1`，正式 | tag `v0.7.1-dev.42.g1a2b3c4`，**预发布** |

> **渠道别名只出现在文件名里，绝不进版本号**：semver 中 `0.7.1-latest` 属于预发布段，
> 排序上小于 `0.7.1`，设备会把它当成比正式版更旧的版本从而拒绝升级。
> 别名由 `sync_version.py::channel_alias()` 统一给出（`CHANNEL_ALIASES` 单一来源），
> 不要在打包脚本里硬编 `latest` / `dev` 字符串。

> **`frontend/package.json` 永远只跟随 `VERSION` 原值**，不写派生版本——
> 否则源码树会留下带后缀的脏版本号，且与 `sync_version.py --check` 门禁冲突。

**为什么用预发布段，而不是 `+` 构建元数据**：

1. semver 规定预发布版本**小于**同号正式版本，设备端从 `0.7.1-dev.x` 能正常升级到正式 `0.7.1`；
   用 `+gsha` 则相反——semver 比较时忽略构建元数据，两者等值，升级路径不可预期；
2. `+` 在文件名与 URL 中需转义，会污染 Release 下载链接与 tag 名。

**本地打测试包**：

```bash
BUILD_CHANNEL=dev bash scripts/build_fpk.sh                    # → 0.7.1-dev.g<短sha>
BUILD_CHANNEL=dev BUILD_NUMBER=42 bash scripts/build_fpk.sh    # 显式指定构建号
```

> 渠道写错（如 `BUILD_CHANNEL=devel`）会**直接中止构建**，不会静默产出正式版包。
> 版本派生逻辑集中在 `sync_version.py::derive_version` 一处，并有单元测试覆盖。

**`fnpack` 不校验版本号格式**：实测 1.2.3 接受 `0.7.1-dev.42`、`0.7.1-dev.42+gsha`、
`0.7.1.dev42` 等写法并原样写进包内 `manifest`。也就是说**没有任何打包门禁能拦住格式错误的版本号**，
版本号的正确性完全依赖 `derive_version` + 单元测试这条链。

## 2. 版本号：`VERSION` 唯一真实来源

**只改根目录 `VERSION`**，不要手改 `manifest`、`app/app/config.py`、`frontend/package.json`。

打包时 `scripts/sync_version.py` 把 `VERSION` 覆写进：

- `manifest` 的 `version=`
- `app/app/config.py` 的 `APP_VERSION = "..."`
- `frontend/package.json` 的 `version`（源码树，不在暂存目录内，单独处理）

```bash
echo "0.8.0" > VERSION                      # 唯一需要改的地方
python3 scripts/sync_version.py --check     # 自检全仓库版本一致
python3 scripts/sync_version.py --sync-frontend  # 漂移时修复前端
```

> 三处的取值受**构建渠道**影响（见 §1.1）：`manifest` 与 `config.py` 写渠道派生版本，
> `frontend/package.json` 始终写 `VERSION` 原值。

版本派生与查询：

```bash
# 按渠道算出产物版本号（stdout 只有版本号本身，供 shell 捕获；诊断信息走 stderr）
BUILD_VERSION="$(python3 scripts/sync_version.py --print \
  --channel dev --build-number 42 --short-sha 1a2b3c4)"   # → 0.7.1-dev.42.g1a2b3c4

# 直接指定产物版本号（打包脚本用；避免"算一次、写一次"两处漂移）
python3 scripts/sync_version.py "$STAGE" --version "$BUILD_VERSION" --channel dev
```

> `manifest` 与 `config.py` 的版本号**允许滞后**，打包时以 `VERSION` 为准。
> 但 `frontend/package.json` **不允许滞后**——它不随打包被覆写（前端源码不进 fpk），CI 门禁会执行 `--check` 校验，不一致直接阻断构建。

**Release 的 tag 也源于 `VERSION`**（`v0.7.0`）：build 阶段写入 `GITEE_PARAMS`，release 阶段以 `${APP_VERSION}` 引用。改了 `VERSION` 就等于改了 tag，**忘改会让新包覆盖同名 Release**——`--check` 只校验一致性、不校验递增，无门禁兜底。

> 传参用 `echo 'APP_VERSION=x' >> GITEE_PARAMS`（Gitee Go 原生）。不要用 `##vso[task.setvariable]`，那是 Azure DevOps 语法，Gitee Go 不识别。

## 3. 前端构建

```bash
cd frontend
npm ci            # 必须用 ci，保证与 package-lock.json 严格一致
npm run build     # vite build → 输出到 ../app/static
```

### 3.1 产物归属（硬约定）

| 路径 | 性质 | 是否入库 |
| --- | --- | --- |
| `app/static/index.html` | vite 输入模板 | ✅ **必须入库** |
| `app/static/sw.js` | vite 输入模板 | ✅ **必须入库** |
| `app/static/assets/` | 内容哈希命名的产物 | ❌ **禁止入库**（`.gitignore` 已排除） |
| `app/static/icons/`、`manifest.webmanifest` | 静态资源 | ✅ 入库 |

### 3.2 Node 版本

| 场景 | 版本 |
| --- | --- |
| 本地开发 | 优先用全局 PATH 中的 Node（当前 24.x） |
| Gitee 流水线 | `.workflow/build-fpk.yml` 的 `nodeVersion: 24.18.0` |
| `ci_build.sh` 自举兜底 | `NODE_VERSION`（默认 24.18.0），仅环境缺 Node ≥ 18 时下载 |

Vite 8 要求 Node `^20.19.0 || >=22.12.0`。**本地与 CI 的 Node 大版本应一致**，避免产物出现难以复现的差异。

### 3.3 `sw.js` 版本号自动改写

`vite.config.js` 的 `bump-sw-version` 插件在 `closeBundle` 阶段把 `app/static/sw.js` 的 `SW_VERSION` 改写为构建时间戳。

- **不要手工修改 `SW_VERSION`** —— 历史上依赖手工递增，漏改会导致旧构建的 `/assets` 资源在浏览器缓存里永久堆积
- 改写失败只告警、不阻断构建

## 4. 打包与产物门禁

`scripts/build_fpk.sh` 流程：测试门禁 → 静态产物门禁 → 组装暂存目录 → 同步版本号 → fnpack → 权限修正 → 自检 → 清理

### 4.1 静态产物门禁（防白屏）

`app/static/assets/` 不入库，**新 clone 里没有产物**，直接打包会得到引用不存在 JS/CSS 的残缺 FPK，表现为**白屏**。因此打包前两道硬校验：

1. **目录非空**：`app/static/assets` 缺失或为空 → 中止并提示构建命令
2. **引用可解析**：`check_assets_refs.py` 校验 `index.html` 中**每个本地 `src`/`href` 引用**存在且**非空**

`check_assets_refs.py` 校验范围：

- 全部本地引用，不局限于 `assets/`（图标、manifest、sw.js 一并纳入）
- 外链（`http(s)://`、`//`、`data:`、`mailto:`、`tel:`、`#`）跳过
- 每个文件必须**存在且非空**——0 字节产物同样会让页面局部失效
- 额外检查 `icons/` 目录存在且非空

另有**产物过期提醒**：`frontend/src` 存在晚于 `app/static/index.html` 的源文件时告警。**仅警告不阻断**——`git clone/checkout` 会刷新 mtime，可能误报。

### 4.2 暂存目录组装

`fnpack` 打包时会**剥掉 `app/` 一级前缀**，平台把 `app.tgz` 解压到 `${TRIM_APPDEST}` 根目录。因此暂存目录需**嵌套一层 `app/app/`**：

```
阶段/
├── manifest  ICON.PNG  ICON_256.PNG  LICENSE
├── config/   cmd/   wizard/
└── app/
    ├── requirements.txt        # → 设备根目录
    ├── ui/                     # → 设备根目录
    └── app/                    # → 设备 ${TRIM_APPDEST}/app/
        ├── main.py  config.py
        └── api/ core/ db/ parsers/ schemas/ services/ utils/ static/
```

组装时排除：`venv`、`node_modules`、本地数据、前端源码、`__pycache__`、`wizard/.gitkeep`。

**入包清单是单一来源**：`fpk_selfcheck.py` 的 `PKG_FILES` / `PKG_DIRS` 必须与 `build_fpk.sh`（及 `.bat`）的 `cp`/`xcopy` 列表一致。新增 Python 包目录时**三处都要改**。

### 4.3 fnpack 的坑：失败仍返回退出码 0

> ⚠️ **fnpack 校验失败时退出码仍是 0**，只在 stdout 打印 `Packing failed`。仅靠 `set -e` 会静默放过，后续步骤会把上一次的旧 FPK 当成本次产物。

因此采用**三重判定**：

```bash
rm -f fn-finstat.fpk                    # 1. 先删旧产物，避免误用
FNPACK_OUT="$("$FNPACK" build --directory "$STAGE" 2>&1)"
# 2. 退出码 + 输出关键字任一命中即失败
# 3. 产物是否存在 + fpk_selfcheck 兜底
```

**新增打包步骤时不要破坏这个判定链。**

### 4.4 权限修正

Windows 版 fnpack 会把 `cmd/` 下的生命周期脚本权限位打成 `0666`，用 `scripts/fix_fpk_perm.py` 重写为 `0755`。

> 只有 Windows 打包会遇到；CI 与 Linux 打包是空操作，但**必须保留**——否则 Windows 产出的包装到设备上生命周期脚本不可执行。

### 4.5 打包自检

`scripts/fpk_selfcheck.py` 零依赖（仅标准库），`build_fpk.sh` 与 `build_fpk.bat` 共用：

1. **文件清单比对**：源码与 `app.tgz` 逐项比对，防漏打包
2. **外层 tgz 必需条目**：`manifest`、图标、`cmd/` 全部生命周期脚本、`config/privilege`、`config/resource`、`wizard/install`、`wizard/uninstall`
3. **向导 JSON 合法性**：控件类型必须在 fnpack 支持的集合内
4. **设备布局关键路径**：`requirements.txt` 与 `ui/` 在根，Python 包在 `app/` 子目录
5. **静态产物引用**：同 `check_assets_refs.py`

> **`REQUIRED_OUTER` 一项都不能少**：缺任何一项在真机上表现为**功能静默消失**。例如 `wizard/uninstall` 缺失时飞牛卸载流程不会询问数据去留；`cmd/uninstall_callback` 缺失时用户的选择不生效。

### 4.6 清理

打包成功后 `rm -rf` 暂存目录。**打包失败时不清理**，保留现场便于排查。

暂存目录留在 `.local_tmp/`（已被 `.gitignore` 排除）——不及时清理会被工作树级安全扫描当作源码反复误报。

## 5. CI 构建（Gitee Go）

两条流水线共用 `scripts/ci_build.sh`，差别只在 `BUILD_CHANNEL`：

| 流水线文件 | 触发分支 | 渠道 | Release |
| --- | --- | --- | --- |
| `.workflow/build-fpk.yml` | `main` | `release` | 正式 Release（`prerelease: false`） |
| `.workflow/build-fpk-dev.yml` | `dev` | `dev` | 预发布 Release（`prerelease: true`） |

> 两条流水线各自在 build step 里**显式传渠道**（`BUILD_CHANNEL=release|dev bash scripts/ci_build.sh`），
> 不依赖分支名推断——分支名推断只是 `ci_build.sh` 单独运行时的兜底（`BUILD_CHANNEL=auto`）。
> dev 流水线还会断言产物版本号必须含 `-dev`，防止渠道配置串了线却静默发出正式版包。

`scripts/ci_build.sh` 串行五步：

| 步骤 | 内容 |
| --- | --- |
| 1. 环境准备 | apt 换清华源、python3/pip 安装、`PIP_INDEX_URL` 加速 |
| 2. 渠道判定 | 定渠道与产物版本号，落盘 `.local_tmp/build-version.txt` 供 yml 读取 |
| 3. 测试门禁 | 后端：测试 + ruff + black + 版本一致性 |
| 4. 构建打包 | Node 自举 → `npm ci` → 前端 lint/测试门禁 → `npm run build` → fnpack → 产物重命名 |
| 5. 发布日志 | `gen_release_notes.py` 生成 `releaseNode.txt` |

> **版本号只在第 2 步算一次**（`sync_version.py`），随后落盘给 yml、通过环境变量传给
> `build_fpk.sh`、用作 Release tag。**不要让 yml 再 `cat VERSION` 自己算一遍**——
> dev 渠道下两处算法必然漂移，会出现"产物名带 -dev、tag 不带"这类不一致。

### 5.1 可用环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SKIP_TESTS` | `0` | 设为 `1` 跳过测试门禁（**仅限紧急调试，禁止发布**） |
| `BUILD_CHANNEL` | `auto` | 构建渠道：`release` / `dev` / `auto`；`auto` 按 `GITEE_BRANCH` 判定（`main`→release，其余→dev） |
| `NODE_VERSION` | `24.18.0` | Node 自举版本 |
| `FNPACK_VERSION` | `1.2.3` | fnpack 版本 |
| `NPM_REGISTRY` | `registry.npmmirror.com` | npm 镜像源 |
| `PIP_INDEX_URL` | 清华 TUNA | pip 镜像源 |

打包脚本（`build_fpk.sh` / `build_fpk.bat`）另认：

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `BUILD_CHANNEL` | `release` | 构建渠道（本地不写 `auto`，默认出正式版） |
| `BUILD_VERSION` | 由渠道派生 | 直接指定产物版本号；已设置时不再派生（CI 用它保证同源） |
| `CHANNEL_ALIAS` | 由渠道派生 | 产物别名 `latest` / `dev`；已设置时不再派生 |
| `BUILD_NUMBER` | 空 | 构建号，进入版本号的预发布段 |
| `SHORT_SHA` | `git rev-parse --short=7 HEAD` | 短提交号，进入版本号的预发布段 |

### 5.2 门禁清单

CI 中任一失败即中止构建，**不会发布**：

**后端（第 2 步）**

- [ ] 单元测试全量通过（`run_tests.sh`）
- [ ] `ruff check app cmd scripts tests --select F,E9` 通过
- [ ] `black --check app cmd scripts tests` 通过
- [ ] `sync_version.py --check` 通过

**前端（第 3 步）**

- [ ] `npm run lint` 通过
- [ ] `npm test` 通过
- [ ] `npm ci` 成功

**产物（打包后）**

- [ ] `fnpack` 退出码为 0 且无 `Packing failed`
- [ ] `fn-finstat.fpk`、`fn-finstat-{渠道别名}.fpk`、`fn-finstat-v{版本}.fpk` 均存在
- [ ] `MD5SUMS.txt` 非空，且与两个交付产物的实测值一致（CI 会在打包后无条件重算一遍）
- [ ] `releaseNode.txt` 非空
- [ ] 版本号与渠道相符：release 渠道为纯 `X.Y.Z`；**dev 渠道必须含 `-dev` 段**（两条流水线各自硬断言，渠道串线会直接失败）

> **`prettier --check` 不在门禁**：Prettier 重排倾向强，会让 CI 因纯格式差异变红，噪音大于收益，格式化交给编辑器。
> **`black --check` 在门禁**：black 配置全项目统一，且后端没有"编辑器自动格式化"的普遍保障，必须由 CI 兜底。

### 5.3 本地复现 CI 门禁

```bash
bash scripts/run_tests.sh
ruff check app cmd scripts tests --select F,E9
black --check app cmd scripts tests
cd frontend && npm ci && npm run lint && npm test && npm run build && cd ..
bash scripts/build_fpk.sh
```

打测试包（产物带 `-dev` 标识，可直接传上设备验证）：

```bash
BUILD_CHANNEL=dev bash scripts/build_fpk.sh
# 产物：fn-finstat.fpk
#      + fn-finstat-dev.fpk                     ← 稳定入口，给设备装这个
#      + fn-finstat-v0.7.1-dev.g<短sha>.fpk     ← 带版本号副本
#      + MD5SUMS.txt                            ← 上面两个文件的 MD5
```

> ⚠️ `npm ci` 严格按 `package-lock.json` 安装。**改过 `package.json` 依赖后必须提交更新后的锁文件**，否则 CI 会因 peer 冲突或锁文件不一致而失败。

## 8. 新增构建步骤的规范

1. **门禁优先**：新增校验应在打包**之前**失败，而非产出坏包后再发现
2. **单一来源**：文件清单、必需条目等常量集中定义（如 `PKG_FILES`），脚本间共用
3. **双平台同步**：改 `build_fpk.sh` 时必须评估是否同步改 `build_fpk.bat`（暂存清单、fnpack 判定、自检调用三处最易漏）
4. **不破坏 fnpack 三重判定链**（第 4.3 节）
5. **清理策略**：成功清理、失败保留现场；**生成产物前先删旧文件**（`releaseNode.txt`、`fn-finstat.fpk` 都适用），避免中断残留被当成本次产物
6. **零依赖优先**：构建期脚本尽量只用 Python 标准库（`sync_version.py`、`fpk_selfcheck.py`、`check_assets_refs.py` 是范例）
7. **关键脚本须有测试**：影响发布产物的脚本（`gen_release_notes.py`、`sync_version.py`、`fpk_selfcheck.py`）必须配套测试，放在 `tests/` 下——它们逻辑复杂且失败代价高（错误内容会直接出现在 Release 页面或安装包里）
8. **渠道感知**：任何涉及版本号或产物命名的改动都要同时考虑 release 与 dev 两个渠道。版本派生只允许有 `sync_version.py::derive_version` 一处实现、渠道别名只允许有 `channel_alias()` 一处实现，新增调用方一律走 `--print` / `--print-alias`，不要自己拼 `-dev` 后缀或 `latest` 字样
9. **产物完整性**：新增或改名交付产物时，同步评估 `gen_checksums.py` 要覆盖哪些文件。校验值必须在所有产物副本生成**之后**计算——任何"事后修补产物"的步骤都要重新生成校验值，否则用户校验的是旧产品

## 9. 常见问题排查

| 现象 | 原因与处理 |
| --- | --- |
| 打包报「前端构建产物缺失」 | `app/static/assets` 为空。执行 `cd frontend && npm ci && npm run build` |
| 装到设备后白屏 | `index.html` 引用的资源缺失/为空。跑 `python scripts/check_assets_refs.py` 定位 |
| 打包"成功"但产物是旧的 | fnpack 失败但退出码 0 被放过。检查输出是否有 `Packing failed` |
| CI 报 `npm ci` 失败 | `package-lock.json` 与 `package.json` 不一致。本地 `npm install` 后提交锁文件 |
| 设备上功能静默消失 | `fpk_selfcheck.py` 的 `REQUIRED_OUTER` 有缺失。查看自检输出 |
| 设备上生命周期脚本不可执行 | Windows 打包未做权限修正。确认 `fix_fpk_perm.py` 已执行 |
| 更新后浏览器仍加载旧资源 | Service Worker 缓存未失效。确认 `sw.js` 的 `SW_VERSION` 已被构建改写 |
| 预警"静态产物可能过期" | `frontend/src` 有晚于 `app/static` 的改动。重新 build（仅警告，`git checkout` 可能误报） |
| 版本号不一致门禁失败 | `frontend/package.json` 未跟随 `VERSION`。执行 `sync_version.py --sync-frontend` |
| 包内版本号莫名带 `-dev` | 走了 dev 渠道。CI 上确认是哪条流水线触发的；本地确认环境里没有残留 `BUILD_CHANNEL=dev` |
| dev 流水线报「版本号缺少 -dev 标识」 | 渠道没传进 `ci_build.sh`（build step 应显式 `BUILD_CHANNEL=dev bash scripts/ci_build.sh`） |
| 本地 Git Bash 打包报 `FileNotFoundError: \d\pj\...` | 把 MSYS 风格路径（`/d/...`）交给了原生 `python.exe`。打包脚本已改用相对路径，若自行新增脚本请勿传 `$ROOT/...` |
| 产物里出现 `fn-finstat-xxx.fpk` 这种陌生别名 | 环境里的 `CHANNEL_ALIAS` 被污染。合法别名只有 `latest` / `dev`，由 `sync_version.py::channel_alias()` 给出 |
| `md5sum -c MD5SUMS.txt` 报 `No such file or directory` 但文件明明在 | 校验文件被写成了 CRLF，`\r` 被当成文件名的一部分。确认 `gen_checksums.py` 的 LF 固定没被改掉 |
| MD5 与实测值不符 | 产物在校验值生成之后被改动。打包顺序是"先出交付副本 → 再算校验"，中间不要插入修改产物的步骤 |
| 校验文件里出现 `fn-finstat.fpk`（裸名） | 裸名不上传，列它会让用户找不着文件。传给 `gen_checksums.py` 的应是渠道别名与带版本号副本 |
