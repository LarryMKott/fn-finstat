# 编译与构建规范

> 适用：全仓库构建链路
> 配套：[发布流程与Release日志.md](../发布流程与Release日志.md) · [Git提交规范.md](Git提交规范.md)
> 与 `scripts/build_fpk.sh`、`scripts/ci_build.sh`、`fpk_selfcheck.py`、`check_assets_refs.py` 严格对应

## 1. 构建链路

"编译"含**前端编译**与 **FPK 打包**两段，三条入口：

| 入口 | 用途 | 测试门禁 | 构建前端 |
| --- | --- | --- | --- |
| `scripts/build_fpk.sh` | 本地一键打包（Linux/macOS） | ✅ | ❌ 需先手动构建 |
| `scripts/build_fpk.bat` | 本地一键打包（Windows） | ✅ | ❌ 需先手动构建 |
| `scripts/ci_build.sh` | CI 全流程 | ✅ | ✅ |

> **关键差异**：本地脚本**不构建前端**，只做硬门禁校验；CI 脚本会先跑 `npm ci && npm run build`。这是新 clone 打包白屏事故的根源。

**产物**：

| 产物 | 说明 |
| --- | --- |
| `fn-finstat.fpk` | 项目根目录，最终安装包（已在 `.gitignore`） |
| `fn-finstat-v{版本}.fpk` | 仅 CI 生成，带应用版本号的副本，供 Release 附件 |
| `app/static/` | 前端构建产物，输出到后端静态目录 |

## 2. 版本号：`VERSION` 唯一真实来源

**只改根目录 `VERSION`**，不要手改 `manifest`、`app/app/config.py`、`frontend/package.json`。

打包时 `scripts/sync_version.py` 把 `VERSION` 覆写进：

- `manifest` 的 `version=`
- `app/app/config.py` 的 `APP_VERSION = "..."`
- `frontend/package.json` 的 `version`（源码树，不在暂存目录内，单独处理）

```bash
echo "0.8.0" > VERSION                      # 唯一需要改的地方
python3 scripts/sync_version.py --check     # 自检全仓库版本一致
python3 scripts/sync_version.py --sync-frontend  # 漂移时修复前端
```

> `manifest` 与 `config.py` 的版本号**允许滞后**，打包时以 `VERSION` 为准。
> 但 `frontend/package.json` **不允许滞后**——它不随打包被覆写（前端源码不进 fpk），CI 门禁会执行 `--check` 校验，不一致直接阻断构建。

## 3. 前端构建

```bash
cd frontend
npm ci            # 必须用 ci，保证与 package-lock.json 严格一致
npm run build     # vite build → 输出到 ../app/static
```

### 3.1 产物归属（硬约定）

| 路径 | 性质 | 是否入库 |
| --- | --- | --- |
| `app/static/index.html` | vite 输入模板 | ✅ **必须入库** |
| `app/static/sw.js` | vite 输入模板 | ✅ **必须入库** |
| `app/static/assets/` | 内容哈希命名的产物 | ❌ **禁止入库**（`.gitignore` 已排除） |
| `app/static/icons/`、`manifest.webmanifest` | 静态资源 | ✅ 入库 |

### 3.2 Node 版本

| 场景 | 版本 |
| --- | --- |
| 本地开发 | 优先用全局 PATH 中的 Node（当前 24.x） |
| Gitee 流水线 | `.workflow/build-fpk.yml` 的 `nodeVersion: 24.18.0` |
| `ci_build.sh` 自举兜底 | `NODE_VERSION`（默认 24.18.0），仅环境缺 Node ≥ 18 时下载 |

Vite 8 要求 Node `^20.19.0 || >=22.12.0`。**本地与 CI 的 Node 大版本应一致**，避免产物出现难以复现的差异。

### 3.3 `sw.js` 版本号自动改写

`vite.config.js` 的 `bump-sw-version` 插件在 `closeBundle` 阶段把 `app/static/sw.js` 的 `SW_VERSION` 改写为构建时间戳。

- **不要手工修改 `SW_VERSION`** —— 历史上依赖手工递增，漏改会导致旧构建的 `/assets` 资源在浏览器缓存里永久堆积
- 改写失败只告警、不阻断构建

## 4. 打包与产物门禁

`scripts/build_fpk.sh` 流程：测试门禁 → 静态产物门禁 → 组装暂存目录 → 同步版本号 → fnpack → 权限修正 → 自检 → 清理

### 4.1 静态产物门禁（防白屏）

`app/static/assets/` 不入库，**新 clone 里没有产物**，直接打包会得到引用不存在 JS/CSS 的残缺 FPK，表现为**白屏**。因此打包前两道硬校验：

1. **目录非空**：`app/static/assets` 缺失或为空 → 中止并提示构建命令
2. **引用可解析**：`check_assets_refs.py` 校验 `index.html` 中**每个本地 `src`/`href` 引用**存在且**非空**

`check_assets_refs.py` 校验范围：

- 全部本地引用，不局限于 `assets/`（图标、manifest、sw.js 一并纳入）
- 外链（`http(s)://`、`//`、`data:`、`mailto:`、`tel:`、`#`）跳过
- 每个文件必须**存在且非空**——0 字节产物同样会让页面局部失效
- 额外检查 `icons/` 目录存在且非空

另有**产物过期提醒**：`frontend/src` 存在晚于 `app/static/index.html` 的源文件时告警。**仅警告不阻断**——`git clone/checkout` 会刷新 mtime，可能误报。

### 4.2 暂存目录组装

`fnpack` 打包时会**剥掉 `app/` 一级前缀**，平台把 `app.tgz` 解压到 `${TRIM_APPDEST}` 根目录。因此暂存目录需**嵌套一层 `app/app/`**：

```
阶段/
├── manifest  ICON.PNG  ICON_256.PNG  LICENSE
├── config/   cmd/   wizard/
└── app/
    ├── requirements.txt        # → 设备根目录
    ├── ui/                     # → 设备根目录
    └── app/                    # → 设备 ${TRIM_APPDEST}/app/
        ├── main.py  config.py
        └── api/ core/ db/ parsers/ schemas/ services/ utils/ static/
```

组装时排除：`venv`、`node_modules`、本地数据、前端源码、`__pycache__`、`wizard/.gitkeep`。

**入包清单是单一来源**：`fpk_selfcheck.py` 的 `PKG_FILES` / `PKG_DIRS` 必须与 `build_fpk.sh`（及 `.bat`）的 `cp`/`xcopy` 列表一致。新增 Python 包目录时**三处都要改**。

### 4.3 fnpack 的坑：失败仍返回退出码 0

> ⚠️ **fnpack 校验失败时退出码仍是 0**，只在 stdout 打印 `Packing failed`。仅靠 `set -e` 会静默放过，后续步骤会把上一次的旧 FPK 当成本次产物。

因此采用**三重判定**：

```bash
rm -f fn-finstat.fpk                    # 1. 先删旧产物，避免误用
FNPACK_OUT="$("$FNPACK" build --directory "$STAGE" 2>&1)"
# 2. 退出码 + 输出关键字任一命中即失败
# 3. 产物是否存在 + fpk_selfcheck 兜底
```

**新增打包步骤时不要破坏这个判定链。**

### 4.4 权限修正

Windows 版 fnpack 会把 `cmd/` 下的生命周期脚本权限位打成 `0666`，用 `scripts/fix_fpk_perm.py` 重写为 `0755`。

> 只有 Windows 打包会遇到；CI 与 Linux 打包是空操作，但**必须保留**——否则 Windows 产出的包装到设备上生命周期脚本不可执行。

### 4.5 打包自检

`scripts/fpk_selfcheck.py` 零依赖（仅标准库），`build_fpk.sh` 与 `build_fpk.bat` 共用：

1. **文件清单比对**：源码与 `app.tgz` 逐项比对，防漏打包
2. **外层 tgz 必需条目**：`manifest`、图标、`cmd/` 全部生命周期脚本、`config/privilege`、`config/resource`、`wizard/install`、`wizard/uninstall`
3. **向导 JSON 合法性**：控件类型必须在 fnpack 支持的集合内
4. **设备布局关键路径**：`requirements.txt` 与 `ui/` 在根，Python 包在 `app/` 子目录
5. **静态产物引用**：同 `check_assets_refs.py`

> **`REQUIRED_OUTER` 一项都不能少**：缺任何一项在真机上表现为**功能静默消失**。例如 `wizard/uninstall` 缺失时飞牛卸载流程不会询问数据去留；`cmd/uninstall_callback` 缺失时用户的选择不生效。

### 4.6 清理

打包成功后 `rm -rf` 暂存目录。**打包失败时不清理**，保留现场便于排查。

暂存目录留在 `.local_tmp/`（已被 `.gitignore` 排除）——不及时清理会被工作树级安全扫描当作源码反复误报。

## 5. CI 构建（Gitee Go）

`scripts/ci_build.sh` 串行四步：

| 步骤 | 内容 |
| --- | --- |
| 1. 环境准备 | apt 换清华源、python3/pip 安装、`PIP_INDEX_URL` 加速 |
| 2. 测试门禁 | 后端：测试 + ruff + black + 版本一致性 |
| 3. 构建打包 | Node 自举 → `npm ci` → 前端 lint/测试门禁 → `npm run build` → fnpack → 产物重命名 |
| 4. 发布日志 | `gen_release_notes.py` 生成 `releaseNode.txt` |

### 5.1 可用环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `SKIP_TESTS` | `0` | 设为 `1` 跳过测试门禁（**仅限紧急调试，禁止发布**） |
| `NODE_VERSION` | `24.18.0` | Node 自举版本 |
| `FNPACK_VERSION` | `1.2.3` | fnpack 版本 |
| `NPM_REGISTRY` | `registry.npmmirror.com` | npm 镜像源 |
| `PIP_INDEX_URL` | 清华 TUNA | pip 镜像源 |

### 5.2 门禁清单

CI 中任一失败即中止构建，**不会发布**：

**后端（第 2 步）**

- [ ] 单元测试全量通过（`run_tests.sh`）
- [ ] `ruff check app cmd scripts tests --select F,E9` 通过
- [ ] `black --check app cmd scripts tests` 通过
- [ ] `sync_version.py --check` 通过

**前端（第 3 步）**

- [ ] `npm run lint` 通过
- [ ] `npm test` 通过
- [ ] `npm ci` 成功

**产物（打包后）**

- [ ] `fnpack` 退出码为 0 且无 `Packing failed`
- [ ] `fn-finstat.fpk` 与 `fn-finstat-v{版本}.fpk` 均存在
- [ ] `releaseNode.txt` 非空

> **`prettier --check` 不在门禁**：Prettier 重排倾向强，会让 CI 因纯格式差异变红，噪音大于收益，格式化交给编辑器。
> **`black --check` 在门禁**：black 配置全项目统一，且后端没有"编辑器自动格式化"的普遍保障，必须由 CI 兜底。

### 5.3 本地复现 CI 门禁

```bash
bash scripts/run_tests.sh
ruff check app cmd scripts tests --select F,E9
black --check app cmd scripts tests
cd frontend && npm ci && npm run lint && npm test && npm run build && cd ..
bash scripts/build_fpk.sh
```

> ⚠️ `npm ci` 严格按 `package-lock.json` 安装。**改过 `package.json` 依赖后必须提交更新后的锁文件**，否则 CI 会因 peer 冲突或锁文件不一致而失败。

## 6. 依赖管理

**后端（`app/requirements.txt`）**：`fastapi` / `uvicorn[standard]` / `openpyxl` / `python-multipart` / `pydantic` / `python-dotenv` / `SQLAlchemy`

- 测试与工具依赖（`pytest`、`httpx`、`ruff`、`black`）**不进 requirements.txt**，由 `run_tests.sh` / `ci_build.sh` 单独安装
- 数据库驱动（PyMySQL / psycopg2）由设置页迁移时按需安装，**不预置**
- 安装优先国内镜像；已处理 PEP 668（`--break-system-packages` 回退）

**前端（`frontend/package.json`）**：

- **提交 `package-lock.json`**，CI 用 `npm ci`
- 新增依赖前评估体积：ECharts 已拆为独立 chunk（约 628KB），`chunkSizeWarningLimit` 设为 700，**超过即需拆分**

## 7. 设备端布局

```
${TRIM_APPDEST}/                    ← 平台解压 app.tgz 到此根目录
├── manifest  ICON.PNG  ICON_256.PNG  LICENSE
├── config/          privilege、resource
├── cmd/             生命周期脚本（main / install_* / uninstall_* / upgrade_* / config_*）
├── wizard/          install、uninstall 向导 JSON
├── requirements.txt
├── ui/              桌面入口（desktop_uidir=ui）
├── app/             Python 包：main.py、config.py、api/、core/、db/…
└── app.sock         统一网关 Socket

${TRIM_PKGVAR}/                     ← 持久化目录（升级/卸载可保留）
├── finance/         数据库与配置
├── venv/            运行时虚拟环境
├── app.log  app.pid  .ctl.lock
```

- `manifest` 声明 `install_dep_apps=python312`，`cmd/main` 中 `export PATH=/var/apps/python312/target/bin:$PATH` 引入运行时
- **fnOS 网关模式经 Unix Socket（`app.sock`）通信，不监听 TCP 端口**；`wizard_port`（默认 8090）仅用于独立部署/本地运行
- `TRIM_PKGVAR` 是持久化数据目录（数据库、配置、日志），`TRIM_PKGTMP` 是临时目录（系统可回收）

## 8. 新增构建步骤的规范

1. **门禁优先**：新增校验应在打包**之前**失败，而非产出坏包后再发现
2. **单一来源**：文件清单、必需条目等常量集中定义（如 `PKG_FILES`），脚本间共用
3. **双平台同步**：改 `build_fpk.sh` 时必须评估是否同步改 `build_fpk.bat`（暂存清单、fnpack 判定、自检调用三处最易漏）
4. **不破坏 fnpack 三重判定链**（第 4.3 节）
5. **清理策略**：成功清理、失败保留现场；**生成产物前先删旧文件**（`releaseNode.txt`、`fn-finstat.fpk` 都适用），避免中断残留被当成本次产物
6. **零依赖优先**：构建期脚本尽量只用 Python 标准库（`sync_version.py`、`fpk_selfcheck.py`、`check_assets_refs.py` 是范例）
7. **关键脚本须有测试**：影响发布产物的脚本（`gen_release_notes.py`、`sync_version.py`、`fpk_selfcheck.py`）必须配套测试，放在 `tests/` 下——它们逻辑复杂且失败代价高（错误内容会直接出现在 Release 页面或安装包里）

## 9. 常见问题排查

| 现象 | 原因与处理 |
| --- | --- |
| 打包报「前端构建产物缺失」 | `app/static/assets` 为空。执行 `cd frontend && npm ci && npm run build` |
| 装到设备后白屏 | `index.html` 引用的资源缺失/为空。跑 `python scripts/check_assets_refs.py` 定位 |
| 打包"成功"但产物是旧的 | fnpack 失败但退出码 0 被放过。检查输出是否有 `Packing failed` |
| CI 报 `npm ci` 失败 | `package-lock.json` 与 `package.json` 不一致。本地 `npm install` 后提交锁文件 |
| 设备上功能静默消失 | `fpk_selfcheck.py` 的 `REQUIRED_OUTER` 有缺失。查看自检输出 |
| 设备上生命周期脚本不可执行 | Windows 打包未做权限修正。确认 `fix_fpk_perm.py` 已执行 |
| 更新后浏览器仍加载旧资源 | Service Worker 缓存未失效。确认 `sw.js` 的 `SW_VERSION` 已被构建改写 |
| 预警"静态产物可能过期" | `frontend/src` 有晚于 `app/static` 的改动。重新 build（仅警告，`git checkout` 可能误报） |
| 版本号不一致门禁失败 | `frontend/package.json` 未跟随 `VERSION`。执行 `sync_version.py --sync-frontend` |
