## 三、P0 缺陷（已复现）

### M14-2 · 通配绑定时 Host 白名单整体失效

**复现证据**（`test_m14_2_*`，4 条用例）：

```
HOST_IS_WILDCARD=True  → GET /probe  Host: attacker.example.com  → 200 ✅ 放行（缺陷）
HOST_IS_WILDCARD=False → GET /probe  Host: attacker.example.com  → 403 ✅ 拦截（对照）
```

**危害路径已完整复现**（`test_m14_2_same_origin_attack_page_passes_all_checks`）：
攻击页面与伪造 Host 同为 `attacker.example.com` 时，Host 白名单因通配关闭、
Origin 校验因同源通过 → **双双失效，数据被读取**。

**环境确认**（`test_m14_2_production_env_dev_is_wildcard`）：
`.env.dev` 配置 `HOST=0.0.0.0`，即**默认开发部署天然处于白名单关闭状态**，
不是理论问题。

**关键补充**：`tests/core/test_source_guard.py::test_wildcard_host_disables_allowlist_keeps_origin_check`
把当前行为固化为「期望」，修复时须同步修改该测试。

**修复建议**：通配绑定时不应整体关闭白名单，改为「拒绝明显非本机的 Host」
或对带 `Origin` / `Sec-Fetch-*` 的浏览器请求额外约束来源。

### M5-2 / M5-3 · webhook 与 AI 通道无内网 / 云元数据地址黑名单

**准入校验实测**（`test_m5_2_*` / `test_m5_3_*`，11 条用例）—— 以下地址**全部放行**：

| 地址 | 危害 |
| --- | --- |
| `http://127.0.0.1:8090/api/settings/database` | 探测本机接口 |
| `http://127.0.0.1:1/` | 端口探测（连接拒绝 vs 超时可区分） |
| `http://[::1]:6379/` | 探测 IPv6 回环的 Redis |
| `http://169.254.169.254/latest/meta-data/` | **云实例凭证泄露** |
| `http://100.100.100.200/latest/meta-data/` | 阿里云元数据 |
| `http://metadata.google.internal/computeMetadata/v1/` | GCP 元数据 |
| `http://192.168.1.1/`、`http://10.0.0.1:3306/`、`http://172.16.0.1/` | 内网横向探测 |

**实链路验证**（`test_m5_2_webhook_really_sends_to_loopback`）：
用本机临时 HTTP 服务作「内网目标」，走完整 `send_webhook()` —— 请求**真实发出并命中**，
证明「可探测」不是纸面推论。

**AI 通道同源**（`test_m5_7_*`，2 条）：
校验点在 `app/api/ai.py:94`，与 webhook 完全同构（只校验 scheme）。
风险叠加：AI 通道会把 **API Key 以 Bearer 头发给该地址**。

**现状边界**（`test_m5_2_scheme_guard_still_works`）：
scheme 白名单本身有效，`file://` / `gopher://` 被拒；`_NO_REDIRECT` 禁用重定向跟随
（`test_m5_5_no_redirect_followed` 通过）。

**修复建议**：出站前解析目标 IP，拒绝 RFC1918 私网段、回环、链路本地
（169.254.0.0/16）与云元数据地址；对域名解析结果同样校验（防 DNS rebinding）。

## 四、P1 项验证结果

### M8-7 · CSV 公式注入 —— 部分成立，且 xlsx 分支风险更高

**已防护部分**（`test_m8_7_dangerous_prefixes_are_neutralized`，6 条）：
`=` / `+` / `-` / `@` 四种首字符前缀被加单引号 → 转为文本，防护有效。
走 `build_csv()` 完整链路的集成验证也通过。

**绕过条件已精确刻画**（`test_m8_7_leading_whitespace_control_bypass`，6 条）：
`csv_safe` 用 `str.startswith(("=", "+", "-", "@"))`，只认**第一个字符**。
以下载荷**原样写入、未被处理**：

```python
"\t=1+1"   # 前导 Tab
"\r=1+1"   # 前导 CR
"\n=1+1"   # 前导 LF
" =1+1"    # 前导空格
"\x0b=1+1" # 垂直制表
"\x0c=1+1" # 换页
```

另：`test_m8_7_dangerous_marker_after_comma_is_not_protected` 证明
`正常备注\n=1+1` 这类多段文本中的后续段不被检查。

**🆕 新增发现 · xlsx 分支未做任何转义**（`test_m8_7_xlsx_dangerous_cell_becomes_formula`）：

```python
# build_xlsx 直接 ws.append(row)，未调用 csv_safe
cell = ws.cell(row=2, column=4)          # 商户列
cell.value    == "=cmd|'/C calc'!A1"
cell.data_type == "f"                     # ← openpyxl 记为公式，Excel 打开即求值
```

方案只提了 CSV，但 **xlsx 分支完全没有转义**，且 `data_type == "f"` 由读回实测确认。
金额列（下标 4）刻意豁免转义，由 `test_m8_7_amount_column_is_exempt_by_design` 记录
（因 amount 在 schema 层为数值类型，不构成注入面）。

**修复建议**：
1. 前缀判定改为「剥离前导空白与控制字符后判定」；
2. `build_xlsx` 对文本列统一前置单引号或显式设置 `data_type='s'`。

### M13-4 / M13-5 · 认证与邀请码枚举无限流

**全量检索确认**（`test_m13_4_no_rate_limit_infrastructure_exists`）：
产品代码中 `rate_limit` / `ratelimit` / `RateLimit` / `too_many_requests` / `限流器`
**零命中** → 限流设施完全不存在。

**Token 面**（`test_m13_3_token_entropy_is_sufficient`）：
`ffk_` + `secrets.token_hex(16)` = **128 bit 熵**，暴力枚举不可行；
服务端只存 SHA-256 哈希，认证为单次哈希查表（`test_m13_4_token_auth_is_constant_cost_lookup`）。
**结论：熵足够，风险在「无限流」本身**。

**邀请码面**（`test_m13_5_invite_code_entropy_is_sufficient`）：
8 位 × 31 字符集 ≈ **40 bit**；500 次生成无碰撞；已排除易混淆字符 `0O1IL`。
`get_by_invite_code` 只做 `strip().upper()` + 查表，**无失败计数、无延迟**
（`test_m13_5_invite_lookup_has_no_attempt_limit`）。

**修复建议**：对认证失败与邀请码查找加失败计数 + 指数退避；
40 bit 空间在线枚举偏弱，建议提升到 10-12 位或将失败计数作为主防线。

### 10.2 关键实现决策

**为什么 SSRF 防线要做「DNS 解析 + 逐 IP 判定」而不是黑名单字符串匹配**

单看字面量拦不住 `localtest.me`（A 记录指向 127.0.0.1）。`validate_outbound_url`
解析后要求**每个** IP 都通过 `_is_disallowed_ip()`（覆盖 `is_private` /
`is_loopback` / `is_link_local` / `is_reserved` / `is_multicast` /
`is_unspecified`），且**解析失败 fail-closed** 拒绝。多 A 记录里只要有一条落在
禁止范围就整体拒绝（防「多记录绕过」）。

**为什么 AI 通道要做两道校验（保存侧 + 出站侧）**

保存侧（`api/ai.py`）只能拦住「走接口改配置」的路径。配置文件在磁盘上，
可被直接篡改，也可能残留旧版本写入的越界地址 —— 而 AI 通道会把
`Authorization: Bearer <API Key>` 发往该地址，一旦漏放即密钥外泄。
故在 `_chat()` 真正发包前再拦一道。

**为什么限流按 key 计数而非全局计数**

全局计数会让一个攻击者把所有人锁死（把限流变成拒绝服务工具）。
Token 认证按客户端 IP 计数（不信任 `X-Forwarded-For`，本应用不经可信反代），
邀请码按 `user_id` 计数（每个账号独立）。

**为什么测试要用 `outbound_guard_bypass` 而不是改产品代码加开关**

服务层单测（`test_ai_service` / `test_notify` / `test_no_redirect`）测的是
「请求体构造」「错误映射」「是否跟随重定向」，故意用不存在的假域名
（避免依赖真实网络）与 `127.0.0.1` 临时服务器（唯一可靠的 302 观测手段）。
它们与地址安全校验的关切**正交**。夹具采用显式 opt-in（非 autouse），
读用例签名即可看出「这条不验证地址安全」；SSRF 防线的有效性由
`tests/security/` 覆盖（那里跑真实实现）。产品代码中**没有任何测试后门**。

### 10.4 修复过程中新发现的假阳性修正

| 编号 | 原结论 | 复测结论 | 依据 |
| --- | --- | --- | --- |
| M6-7 | Windows 上 `Path.resolve()` 不跟随目录符号链接 → 越界未拦截 | **假阳性**。当时 `symlink_to(target_is_directory=True)` 创建失败（`os.path.islink()` 返回 False），把「链接没建成」误判为「resolve 不解析」。改用 junction 复测：`resolve()` 正确解析到目录外并**被祖先校验拦下** | 探针 `.local_tmp/probe_m67.py` |
| M16-3 | 更新包无完整性校验，仅依赖 HTTPS | **表述不准**。`update_service` 早已定义 `CHECKSUM_FILE = "MD5SUMS.txt"`、从 assets 提取 `checksum_url` 并经 schema 下发前端。校验动作在客户端（用户下机安装前 `md5sum -c`），后端只负责提供摘要 —— 符合「检查更新只告知、不自动安装」的设计 | 源码 + `parse_release` 实测 |

即便如此，M6-7 仍做了**纵深防御加固**：`_resolve_in_root` 增加「逐段
`islink`/`isjunction` 检测」，不依赖 `resolve()` 的平台实现细节 —— 万一条目
解析失败静默返回未解析路径，这层能兜住。链接一律按越界拒绝（账单目录
用于导入本机账单文件，业务上不需要链接跳转）。
